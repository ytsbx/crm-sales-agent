## 三、发现

### F04-01 P1：合并确认按钮不等影响清单加载成功，预览未回/失败也能提交

- **位置**：`CustomerDetailPage.tsx:186-191`（`mergePreviewQuery`）、`193-195`（`unresolvedConflicts`）、`1710-1713`（`onOk` / `okButtonProps`）、`1784-1789`（预览加载只显示“正在统计”）。
- **触发条件**：用户在“合并到其他客户”里选中目标客户后，影响清单请求还在加载，或请求失败（403/500/网络），此时点“确认合并”。
- **后果**：`mergePreview` 为 `undefined`，`blocking` 为空，`unresolvedConflicts.length === 0`；`okButtonProps` 只判 `!mergeTarget || unresolvedConflicts.length > 0`，所以按钮**可用**。合并是不可逆的：来源客户会被软删、全部关联改挂；用户可以在没看到“会跟着走多少条、有没有冲突”的情况下提交。若预览失败但实际无冲突，后端会直接合并，页面不会补上影响清单。
- **证据代码**：
  ```tsx
  const mergePreviewQuery = useQuery({
    queryKey: ['merge-preview', customerId, mergeTarget],
    queryFn: () => getCustomerMergePreview(customerId, mergeTarget!),
    enabled: mergeModal && Boolean(mergeTarget),
  }) // :186-190
  const unresolvedConflicts = (mergePreview?.blocking ?? []).filter(
    (key) => !mergeResolutions[key],
  ) // :193-195
  okButtonProps={{ disabled: !mergeTarget || unresolvedConflicts.length > 0 }} // :1713
  {mergePreviewQuery.isLoading && (<div>正在统计影响…</div>)} // :1786-1788
  ```
- **建议**：确认键改为 `disabled={!mergeTarget || mergePreviewQuery.isPending || mergePreviewQuery.isError || !mergePreview || unresolvedConflicts.length > 0}`；预览失败时在弹窗内给错误和“重试”，不允许提交；目标客户变更时清空旧预览状态。
- **测试覆盖**：**未覆盖**。没有前端合并预览门禁用例；后端也没有 `merge-preview`/`merge` 测试（`test_customer_duplicate_scope.py:9-47` 只覆盖撞单裁定的锁）。

### F04-02 P2：客户导入确认没有请求幂等，响应丢失后重新预览再导入会重复建客户

- **位置**：`CustomerListPage.tsx:341-355`（`confirmImport`）；`backend/app/modules/customer/io_router.py:261-276`、`445-455`；`backend/app/core/importing.py:605-626`。
- **触发条件**：确认导入的 POST 已在服务端提交并 commit，但响应超时/网络断开；`confirmImport` 进入 `catch`，`closeImportPreview()` 关闭预览并 Toast 失败。用户重新选择同一文件、重新预览、再确认。
- **后果**：后端导入没有 `request_key`，`finalize` 只校验 `preview_token` 的文件摘要/行计划；第一次已 commit 的客户在第二次预览里仍是“新增”（导入对疑似重复也照样建档），第二次确认会再建一遍客户，并可能再开一批待裁定撞单。B13-06 已确认“同一文件重试会重复建客户、重复开撞单”。
- **证据代码**：
  ```tsx
  const formData = new FormData()
  formData.append('file', importPreviewFile)
  formData.append('preview_token', importPreview.preview_token)
  const response = await axios.post('/api/v1/customers/import', formData, {
    headers: tokenHeader(),
  }) // :346-351
  ```
  后端签名只覆盖 `module/file_sha256/plan/baselines`，没有请求键；`preview_token` 不是一次性幂等键。
- **建议**：给导入加 `request_key`（同一次确认重试复用），后端在 `import_customers` 入口做幂等或按 `file_sha256 + preview_token` 记录已完成结果；前端在 `catch` 不直接关闭预览，先提示“结果未知，请先刷新确认，不要直接重导”。
- **测试覆盖**：**未覆盖**。`test_customer_import_dispute_report.py` 只测单行保存点失败时报告是否正确，不测重复 POST；B13-06 也标“未覆盖重复导入”。

### F04-03 P2：新建客户请求键在关闭弹窗后重开就换新，首次已建成但响应丢失时会重复建客户

- **位置**：`CustomerListPage.tsx:721-727`（打开弹窗生成新键）、`380-396`（提交/成功清键）、`1233`（`onCancel` 直接关闭，不判 `createMutation.isPending`）。
- **触发条件**：第一次“创建”已在服务端成功并 commit，但响应超时；用户看到 Toast 后关闭弹窗，再点“新建客户”重新填同一家公司。
- **后果**：`createRequestKeyRef.current = newRequestKey()` 在每次打开弹窗时执行；第一次的键已经丢了，第二次是全新键，后端幂等不会回放，直接再建一条客户。后端 `create_customer` 本身支持同键回放（`customer/router.py:141-171`），但前端键的生命周期没有覆盖“结果未知后关闭重开”。
- **证据代码**：
  ```tsx
  onClick={() => {
    // 每次打开"新建客户"都是一次新表单 → 换一把新的幂等键
    createRequestKeyRef.current = newRequestKey() // :721-723
    ...
  }}
  // onSuccess
  createRequestKeyRef.current = '' // :391
  // onCancel
  onCancel={() => setModalVisible(false)} // :1233
  ```
- **建议**：把“这一次填表”的键保留到明确成功或明确失败；关闭弹窗时若 `createMutation.isPending` 或最近一次是超时/网络错误，不要丢键；重开时若表单内容未变，复用旧键。更稳的是提交中禁止关闭，或关闭前提示“请求可能已成功，重开会重复建客户”。
- **测试覆盖**：**未覆盖**。后端有创建幂等，但没有前端“超时→关闭→重开”的用例。

### F04-04 P2：新建前查重失败被静默当成“没有重复”，用户仍可继续创建

- **位置**：`CustomerListPage.tsx:293-298`（`dedupMutation`）、`1261-1263`（名称失焦触发）、`1269-1286`（重复提示）。
- **触发条件**：名称失焦触发 `POST /customers/deduplicate`，接口 500/403/网络失败。
- **后果**：`onError: () => setDupMatches([])` 把查重结果清空，界面不显示任何错误；`dupMatches.length` 为 0，重复提示块不出现，用户会认为“没有重复”。后端 `create_customer` 只负责建档，不做重复拦截（`customer/service.py:610-651`），所以这条客户会直接落库，事后再靠撞单队列补发现。
- **证据代码**：
  ```tsx
  const dedupMutation = useMutation({
    mutationFn: () => deduplicateCustomers({ name: form.name }),
    onSuccess: (result) => setDupMatches(result.matches ?? []),
    onError: () => setDupMatches([]), // :297
  })
  ```
- **建议**：查重失败时保留“查重未完成”状态并在名称下方显示错误 + 重试；提交前若最近一次查重失败，要求用户显式确认“仍要创建”，不要用空数组冒充“无重复”。
- **测试覆盖**：**未覆盖**。`test_customer_dedup_scope.py:11-31` 测后端查重范围，不测前端失败态。

### F04-05 P2：合并专属价冲突只显示“有几对”，不显示具体价格/数量区间

- **位置**：`CustomerDetailPage.tsx:1830-1857`；`backend/app/modules/customer/tags.py:480-497`。
- **触发条件**：来源/目标客户存在同 SKU、数量区间与有效期都重叠但价格不同的专属价，合并预览返回 `customer_price` 冲突。
- **后果**：后端 `conflicts[].items` 里带 `sku_id/rule_ids/prices`（`tags.py:455-461、495`），但前端只渲染 `conflict.label`、`detail`（“N 对…价却不一样”）和两个选项，**不显示任何具体价格**。用户要在“保留目标客户的价格 / 改用来源客户的价格”之间做不可逆选择，却看不到两边到底差多少、涉及哪些 SKU/区间，容易把该保留的价归档掉。
- **证据代码**：
  ```tsx
  {mergePreview.conflicts.map((conflict) => (
    <div key={conflict.key}>
      <div>{conflict.label}</div>
      <div>{conflict.detail}</div>
      <Select value={mergeResolutions[conflict.key]} optionList={conflict.options...} />
    </div>
  ))}
  ```
  没有渲染 `conflict.items`。
- **建议**：在冲突块内渲染 `items`（SKU、数量区间、有效期、来源价/目标价），并且只在有 `price:view`/`price:manage` 时显示具体价格；无价格权限时至少显示“涉及 N 个 SKU、价格不同”，不要让用户盲选。后端已经有 `price:manage` 闸门（`tags_router.py:221-229`），前端展示可以同口径。
- **测试覆盖**：**未覆盖**。无合并预览/冲突展示测试。

### F04-06 P2：联系人接口失败时业务全景显示“0 条”、联系人表显示“还没有联系人”

- **位置**：`CustomerDetailPage.tsx:209-213`（`contactsQuery`）、`922`（业务全景联系人数字）、`1015`（联系人表空态）。
- **触发条件**：联系人接口 500/网络失败；客户详情本身已加载成功，头部 `customer.contact_count` 可能有值。
- **后果**：`(contactsQuery.data ?? []).length` 在失败时是 `0`，业务全景显示“0 条”；联系人表 `empty` 是固定字符串“这家客户还没有登记联系人”，不是 `emptyHint(contactsQuery.isError,...)`。用户会把“接口失败/无权查看”读成“这家客户没有联系人”，与头部 `contact_count` 也可能矛盾。
- **证据代码**：
  ```tsx
  { key: 'contacts', label: '联系人', value: (contactsQuery.data ?? []).length, ... } // :922
  <Table dataSource={contactsQuery.data ?? []} empty="这家客户还没有登记联系人..." /> // :1015
  ```
- **建议**：`contactsQuery.isError` 时数字显示 `—`（或错误图标），联系人表改用 `emptyHint(contactsQuery.isError, '还没有联系人', contactsQuery.error)` 并提供重试；不要把空数组当成功空态。
- **测试覆盖**：**未覆盖**。

### F04-07 P2：导入失败清单直接展示后端截断的底层异常原文

- **位置**：`CustomerListPage.tsx:1005`、`1115`（渲染 `item.reason`）；`backend/app/modules/customer/io_router.py:443`（`f"写入失败：{str(exc)[:160]}"`）。
- **触发条件**：导入某行触发数据库约束/类型/外键等异常，进入 `except Exception`。
- **后果**：后端把 `str(exc)[:160]` 放进失败原因，前端在预览/结果弹窗里原样显示。异常文本可能包含表名、列名、约束名、甚至具体值，属于内部细节泄露。B13-05 已确认这条后端问题，F04 是实际展示出口。
- **证据代码**：
  ```tsx
  <div style={{ color: 'var(--crm-error)' }}>{item.reason}</div> // :1005、:1115
  ```
  ```python
  report.failed_row(index, name, f"写入失败：{str(exc)[:160]}") # io_router.py:443
  ```
- **建议**：后端对 `Exception` 分类：业务校验给可读原因，未知异常记日志/审计并用“写入失败，请联系管理员（错误号 …）”替代；前端对 `reason` 再做一次技术信息过滤，至少不展示 `str(exc)` 原文。
- **测试覆盖**：**未覆盖**。B13-05 标“未覆盖错误信息内容”；现有 `test_customer_import_dispute_report.py` 只测失败行计数，不测错误文案。

### F04-08 P3：单个/批量转移负责人都不填原因，审计无法解释为什么转

- **位置**：`CustomerDetailPage.tsx:318-327`（单客户转移）；`CustomerListPage.tsx:279-291`（批量转移）；`shared/api/customer.ts:222-229、382-388`（API 支持 `reason`）。
- **触发条件**：用户执行“转移负责人”或“批量转移负责人”。
- **后果**：前端只传 `owner_id`，不传 `reason`；后端用默认文案（“负责人转移/批量转移”）进归属历史，审计 `before/after` 只有归属变化。B13-08 已确认“客户转移搬走单据，但审计只记客户 before/after，不记单据 ids/数量”；B14-05 已确认“批量转移审计只记请求的 customer_ids/owner_id，不记实际 affected/skipped”。一旦事后追责，无法回答“为什么转、谁批准的、哪些单据跟着走”。
- **证据代码**：
  ```tsx
  mutationFn: (owner: SystemUser) => transferCustomer(customerId, { owner_id: owner.id }) // :319
  mutationFn: ({ owner, ids }) => batchTransferCustomers({ customer_ids: ids, owner_id: owner.id }) // :280-281
  ```

- **建议**：转移弹窗增加“转移原因”（至少批量/放公海时必填），随 `reason` 提交；后端审计补 `documents.moved/skipped` 与实际 affected。单客户转移也建议保留原因，和客户归属历史对齐。
- **测试覆盖**：**未覆盖**。B13-08/B14-05 都没有审计内容用例。

### F04-09 P3：新建联系人没有请求键，弹窗还允许提交中关闭，超时重开可能多一条联系人

- **测试覆盖**：**未覆盖**。

### F04-10 P3：已裁定撞单的接手人只显示“员工编号 N”
