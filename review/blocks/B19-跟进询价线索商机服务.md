## 一、本块结论

- **P0：0**
- **P1：0**
- **P2：5**
- **P3：7**
- **待确认：2**

正面确认的关键点：

- 询价金额输入侧（数量、目标价、报价成本/报价、商机预计金额、商机明细目标价）基本都用了 `Decimal` + 与库列对齐的 `gt/ge/max_digits/decimal_places`，负数、0、超大值、小数位超限在请求模型这一层多数能挡住。
- 询价修订、删除、从询价发起报价都拿了链条首版行锁；线索转化拿了线索行锁 + 客户行锁；跟进创建有 `(owner_id, request_key)` 唯一约束和 PostgreSQL advisory lock 兜底；线索导入逐行 SAVEPOINT，坏行不拖死后续行。
- 线索导入的“无负责人登录名默认归导入人”不是无主池，但 `test_import_permissions_and_assignment` 已明确断言 `owner_id=1`，按现有测试口径属于设计行为，本次不记缺陷；若业务要求入池，需要改规则和该测试。
- 系统跟进“无来源仅凭 `followup:view` 可见”的候选不成立：当前 `record_system_event` 在 `customer_id` 为空时直接返回，正常写入口造不出“客户/线索/商机/报价/订单全空”的系统记录。

主要风险集中在五处：**询价对接报价员在草稿/修订链上丢失**、**删除跟进后第三时钟不刷新**、**询价/商机金额出口仍走 float**、**线索导入异常原文回显且吞权限错误**、**询价锁报价来源时未过滤私密草稿，泄露报价号并阻断正常报价**。

### B19-P1 待确认 `copy_items_from` 的 `replace` 只改数量、不校验来源币种

**位置**
- `backend/app/modules/opportunity/service.py:727-738`（`reject_foreign_currency` 只对 `on_conflict == "add"` 或目标不存在的新行生效）
- `backend/app/modules/opportunity/service.py:745-748`（`replace` 只写 `current.quantity = row.quantity`，不改 `target_price/currency/specification`）

**触发条件**：源商机明细是外币/不同目标价，目标商机已有同 SKU，`on_conflict="replace"`。

**后果**：目标行的数量被源行覆盖，但目标价、币种、规格保留目标原值；如果业务预期“整条替换”，这会产生“数量来自源、价格来自目标”的混合行。`test_opportunity_links.py:97-131` 明确断言替换后 `target_price/currency/specification` 不变，说明当前行为是测试固定下来的；是否业务上正确待确认。

**证据代码**
```python
reject_foreign_currency(
    *(row.currency for row in source_rows if on_conflict == "add" or row.sku_id not in existing),
    label="商机需求明细",
)
...
if current is not None and on_conflict == "replace":
    current.quantity = row.quantity
```

**建议**：明确 `replace` 的语义：只替换数量（当前测试）还是整行替换；若是整行，补 `target_price/currency/specification` 并做币种校验；若只替换数量，接口/文案要写清“只改数量”，避免用户以为价格也复制了。

### B19-P2 待确认 `create_manual_followup` 无条件使用 PostgreSQL advisory lock

**位置**
- `backend/app/modules/followup/mutations.py:79-80`（`SELECT pg_advisory_xact_lock(...)`）

**触发条件**：带 `request_key` 创建跟进，且运行库不是 PostgreSQL（SQLite 测试/开发库）。

**证据代码**
```python
if payload.request_key:
    await session.execute(text("SELECT pg_advisory_xact_lock(hashtextextended(:key, 0))"),
                          {"key": f"followup:{user.id}:{payload.request_key}"})
```

**建议**：按方言分支（PG 用 advisory lock，其它库依赖唯一约束 + 捕获冲突），或明确项目只支持 PG 并在启动时校验；测试侧若要覆盖幂等，需给 SQLite 提供等价锁或 monkeypatch。

**测试覆盖**：未覆盖。`test_followup_plan.py` 是纯 schema 测试，没有带 `request_key` 的创建用例；项目测试大量使用 SQLite。
