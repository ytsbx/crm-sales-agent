## 三、逐条证据与建议

### B12-01（P2）审计 JSON 的 Decimal 被转成 float

**位置**：`backend/app/core/audit.py:50-51`。

**触发条件**：任何 `write_audit(before/after=...)` 里带 `Decimal`，例如报价金额、单价、成本、回款金额、合同金额。

**后果**：`json_safe` 把 `Decimal` 统一 `float(value)`；四位单价或大额金额在 JSON 里变成二进制浮点近似，导出/复算时可能与库里的 Decimal 差 1 分或更多。审计是事后取证依据，金额留痕失真比页面展示失真更严重。B01-11 已发现报价路由局部 `float(...)`；这里是所有审计的统一根因。

**证据代码**：
```python
if isinstance(value, Decimal):
    return float(value)
```
`write_audit` 直接把它写入 `AuditLog.before_data/after_data`。

**测试覆盖**：`test_request_idempotency.py:200` 只验证 `complete` 的 payload 能 JSON 化，不校验 Decimal 的精度；没有审计金额保真用例。

**建议**：审计金额统一用 `format(value, "f")` 字符串（保留原小数位），或 `{amount: "...", currency: "CNY"}` 结构；前端展示再格式化。不要用 float 作为审计存储格式。

### B12-02（P2）参数校验错误回显原始 input，包含密码

**位置**：`backend/app/core/errors.py:191-210`。

**触发条件**：请求体字段触发 pydantic 校验失败，例如 `POST /auth/login` 的 `password` 超过 128 字符、`POST /users` 的密码超过 72 字节、或其他带敏感值的字段类型错误。

**后果**：`_validation_error` 为每个错误生成 `"input": str(error.get("input"))` 并放进响应 `data.details`。密码超长时，响应体里会出现用户刚提交的密码原文；浏览器网络面板、前端错误上报、代理访问日志都可能把它留存。即使是提交者本人，也不应把密码回显到响应。

**证据代码**：
```python
"input": (
    None if error.get("input") is None else str(error.get("input"))
),
```
`LoginRequest.password` 只有 `max_length=128`，超长会走 `string_too_long`，`input` 就是原始密码。

**测试覆盖**：没有校验错误响应字段的测试；`test_signature_input_boundaries.py` 只覆盖签名类错误。

**建议**：响应里只保留 `type/loc/msg/hint`，去掉 `input`；如确需排障，对 `password/token/secret/code` 等字段名统一打码，并只把原始输入写服务端受控日志（且不写密码）。

### B12-03（P1）通用上传/挂载的 category 不校验，可伪造“已签署原件”

**位置**：`backend/app/modules/file/router.py:98-100`（上传 `category` Form）、`146-153`（写入 BusinessFile）、`681`（挂载 `category` Query）、`742-747`（挂载写入）；`contract/service.py:1045`（按 `category=="signed"` 列签署原件）。

**触发条件**：拥有 `file:manage` 且对目标合同有写权限的账号（业务员默认有 `file:manage` 和 `order:manage`），调用 `POST /files/upload` 传 `business_type=contract`、`category=signed`，或对已有文件调用 `POST /business/contract/{id}/files?category=signed`。

**后果**：`BusinessFile.category` 直接落库为 `signed`；`list_signed_files` 只按 `category=="signed"` 查，合同详情会把这份文件当“签署原件”展示，尽管合同状态仍是草稿/审批中，也没有走 `sign_document` 的 `_ensure_signable_source`、OA approved、原稿排除、生成稿排除等闸门。反过来，客户端把文件标成 `generated/contract_original` 还会进入 `PROTECTED_CATEGORIES`，让通用删除/解绑被永久拦住。这是签署证据链的伪造/绕过，属于流程错误。

**证据代码**：
```python
category: str | None = Form(default=None),
...
BusinessFile(..., category=category)
```
挂载同理：
```python
category: str | None = None,
...
link = BusinessFile(..., category=category)
```
`list_signed_files`：
```python
.where(BusinessFile.business_type == "contract",
       BusinessFile.business_id == doc_id,
       BusinessFile.category == "signed")
```
`sign_document` 有完整校验，但通用入口没有调用它。

**测试覆盖**：没有 `category=signed`/`generated`/`contract_original` 的越权用例；`test_file_access_authorization.py` 只测可见性。

**建议**：把 `category` 改为“按 business_type 的枚举 + 服务端受控映射”；通用上传/挂载只允许普通类别（如 `attachment/supplement/...`），`signed/generated/contract_original` 只能由合同签署、合同生成、导入等专用服务写入；对客户端传入的受保护类别直接 422。

### B12-04（P2）删除文件等锁后不再复查数据范围

**位置**：`backend/app/modules/file/router.py:500-509`。

**触发条件**：用户调用 `DELETE /files/{file_id}`；第 500 行 `can_access_file` 通过后，第 505 行 `SELECT ... FOR UPDATE` 因另一事务持锁而等待；等待期间客户/订单负责人改派，当前用户已不在数据范围。

**后果**：拿到锁后只查 `inspect_file_usage`，不再调用 `can_access_file`；删除继续执行。用户可以在“已经失去访问权”的状态下删除文件，造成跨范围数据丢失。`rename_file` 在锁后做了第二次 `can_access_file`（`router.py:449-450`），删除路径漏了这一步。

**证据代码**：
```python
if not await can_access_file(session, user, file_id):
    raise AppError(...)
record = (await session.execute(
    select(FileRecord).where(FileRecord.id == file_id).with_for_update()
)).scalars().first()
...
usage = await service.inspect_file_usage(session, file_id)
```
锁后没有 `can_access_file`。

**测试覆盖**：没有并发改派/等锁删除用例；文件权限测试是同步布尔判断。

**建议**：拿到文件锁并重读 `record` 后，再执行一次 `can_access_file`；若已失去范围，回滚/不删除。与 `rename_file` 保持同一顺序。

### B12-05（P2）公共询价图片 URL 不校验询价状态/软删，7 天内仍可读

**位置**：`backend/app/modules/file/router.py:39-60`；生成端 `backend/app/modules/dingtalk/router.py:331-337`。

**触发条件**：一张询价图片曾生成过签名 URL（有效期 7 天），之后询价被软删或撤回/取消（`BusinessFile` 关联仍在）。

**后果**：`public_inquiry_image` 只检查签名、过期、文件存在、MIME 是 image、存在任意一条 `business_type=="inquiry"` 的 `BusinessFile`；不检查 `CustomInquiry.deleted_at/status`，也不检查当前用户/客户范围。链接作为 bearer capability 在 7 天内继续返回图片。若链接从钉钉/OA/聊天记录泄漏，已删除询价的图纸仍可被下载。

**证据代码**：
```python
if expires < int(time.time()) or not hmac.compare_digest(...):
    raise AppError(...)
record = await session.get(FileRecord, file_id)
...
linked = (await session.execute(select(BusinessFile).where(
    BusinessFile.file_id == file_id, BusinessFile.business_type == "inquiry"
))).scalars().first()
path = storage.absolute_path(record.object_key)
if linked is None or not path.is_file():
    raise AppError(...)
```
没有查 `CustomInquiry` 的状态/软删。

**测试覆盖**：`test_signature_input_boundaries.py` 覆盖坏签名/非 ASCII/过期；没有覆盖“询价已删/已撤回仍 200”。

**建议**：签名 URL 除了 `file_id/expires`，再绑定 `inquiry_id` 或在查询时反查 `CustomInquiry`，要求 `deleted_at IS NULL` 且状态不是 withdrawn/cancelled；缩短有效期（如 1 小时/按需刷新），并允许在询价关闭时主动失效（记录版本号/一次性 token）。

### B12-06（P3）上传元数据未按列宽前置校验，超长先写盘再 500

**位置**：`backend/app/modules/file/router.py:132-140、146-150`；列定义 `backend/app/modules/file/model.py:23-25、41-44`。

**触发条件**：上传文件的 `filename` 超过 255 字符、`content_type` 超过 128 字符，或 `category` 超过 32 字符。

**后果**：`storage.save_upload` 已把文件写到磁盘，随后 `FileRecord/BusinessFile` 的 `flush` 撞 `varchar(n)` 报错；`except Exception` 走 `discard_unregistered_upload` 清理，用户仍得到 500，而不是“文件名/类型/类别太长”的 422。不会留下孤儿文件，但每次都要写盘再删，且错误不可读。

**证据代码**：
```python
record = FileRecord(... file_name=file.filename or "未命名文件",
                    mime_type=file.content_type, ...)
...
BusinessFile(..., category=category)
```
`FileRecord.file_name` 255、`mime_type` 128、`BusinessFile.category` 32。

**测试覆盖**：没有超长 filename/MIME/category 的上传用例。

**建议**：在 `save_upload` 之前校验 `file.filename` 长度、规范化/截断 `content_type`、按业务类型校验 `category` 长度；超限直接 422，不要先写盘。

## 四、补充维度检查

### 1. 负数 / 0 / 超大值 / 小数位

- B12 没有金额计算入口；`CustomerDuplicateCase.score` 是 `Numeric(6,2)`，写入方在 B13。
- 文件大小有 `max_upload_mb` 上限，`size` 是累计字节；`BigInteger` 足够。
- `expires` 是整数，签名保护；没有上限但需要有效 HMAC。
- `page/page_size`、批量 `business_ids` 上限 500、`audit` 分页 200 都有边界。
- 未发现新增的负数/0/超大金额入口。

### 2. 事务边界

- `upload_file`：先写盘，再 DB 登记，失败/取消都调 `discard_unregistered_upload`；补偿先 rollback 再核对登记，避免误删已提交文件。
- `delete_file`：先提交 DB 删除，再删磁盘；磁盘删失败只留孤儿文件，不回滚库删除。
- `attach_file`：文件锁 → 二次可见性 → 建关联 → 审计 → commit；锁顺序为 sample 单据锁 → 文件锁，和删除一致。
- `write_audit` 不 commit，调用方统一提交；B12-01 的 float 转换发生在写入前。
- 未发现“订单建了明细没建”等半成品；文件上传的补偿是完整的。

### 3. 异常 / 日志 / 敏感信息

- 未处理异常只回通用 500，完整堆栈进日志；`logger.exception` 不打印请求体。
- **B12-02** 会把密码原文放进校验错误响应；这是本块最直接的敏感信息出口。
- `file` 上传失败日志记录 object_key、异常栈，不含文件内容；`delete_file` 磁盘清理失败记录 file_id/object_key。
- `audit` 不记录 token/password；但 B12-01 的 float 会让金额失真。
- `public_inquiry_image` 失败统一 403/404，不泄露文件是否存在。

### 4. 审计

- 上传/改名/删除/挂载/解绑都有 `write_audit`；文件删除审计在 DB commit 前，磁盘清理失败不回滚。
- 失败路径：上传登记失败不回滚审计（因为审计也在同一失败事务里）；删除磁盘清理失败不写“清理失败”审计，只写 warning；公共图片读取无审计。
- 审计金额的 Decimal→float 是 B12-01；`audit:view` 的范围口径见第 17 文件记录的“待确认”。

- 已覆盖但只到单层/同步：`test_archive_file_access.py` 覆盖 department/department_and_sub 的两层部门；`data_scope` 三层递归由其他用例覆盖，本块未见三层以上测试。

## 六、结论

- P0：0；P1：1（B12-03 通用 category 可伪造签署原件）；P2：4（B12-01/02/04/05）；P3：1（B12-06）。
- 最高优先级：B12-03 是签署证据链绕过，虽然不直接改合同状态，但会让“签署原件”清单混入任意文件；B12-02 是密码回显；B12-01 是审计金额失真；B12-04/05 是文件范围与长期链接的越权窗口。
- 本块没有把“审计 `audit:view` 是否应按数据范围过滤”写成结论，因为默认只授给 admin，是否允许自定义角色全局查看属于业务口径。
