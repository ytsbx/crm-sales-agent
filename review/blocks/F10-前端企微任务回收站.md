## 二、发现清单

### F10-01｜P0｜企微归一页把“看客户候选”和“建客户/绑客户”都绑在 `wecom` 权限上，绕开客户查看/创建/分配权限

- 文件:行号：
  - `frontend/src/modules/wecom/WeComPage.tsx:125-126`、`188-192`、`780-807`、`810-835`
  - 后端证据 `backend/app/modules/wecom/router.py:253`、`265`、`294`；`backend/app/modules/wecom/service.py:566-569`、`606-613`、`643-651`
- 触发条件：
  - 用户只有 `wecom:view`，没有 `customer:view`，打开企微页面并选中一条待确认联系人；`candidatesQuery` 会请求 `/unbound-contacts/{id}/candidates` 并把候选客户名、等级、地区、负责人、匹配分/原因渲染在右栏。
  - 用户只有 `wecom:manage`，没有 `customer:create`/`customer:assign`，点“创建新客户”或“关联已有客户”；前端 `canManage` 只判断 `wecom:manage`，后端路由也只要求 `wecom:manage`。
- 后果：
  - **读侧越权**：`unbound_candidates` 在服务层明确“故意不做数据范围过滤”，只在全库匹配；路由只要求 `wecom:view`，前端也不按 `customer:view` 隐藏。只有企微查看权限的人可以借候选列表看到全公司客户名称、等级、地区、负责人及匹配理由，绕过客户数据范围。
  - **写侧越权**：`create-customer` 只要求 `wecom:manage`；`create_customer_from_contact` 在未指定负责人时把 `owner_id` 设为当前用户（`customer/service.py:628-630`）。一个没有 `customer:create` 的人可以创建客户并成为负责人；`bind-customer` 也只要求 `wecom:manage`，可以把联系人挂到任意客户 id。
  - 与导入路径不一致：导入预览/确认明确要求 `wecom:import` + `customer:create` + `customer:assign`（`WeComPage.tsx:136`；`test_wecom_customer_import.py:194-215`），但单条建客/绑客却只要 `wecom:manage`，形成“批量要三把钥匙、单条只要一把”的绕过口。
- 证据代码：
  - `const canManage = can('wecom:manage')`（125 行）；`const canSearchCustomers = canManage && can('customer:view')`（126 行）只约束手工搜索，不约束候选列表。
  - `candidatesQuery` 只按 `activeId` 启用（188-192 行），没有 `can('customer:view')` 或 `canManage` 门；候选卡片无条件渲染 `candidate.name`/`score`/`reasons`（780-800 行）。
  - “关联已有客户”“搜索已有客户”“创建新客户”整组按钮在 `canManage` 下（801-835 行），没有 `customer:create`/`customer:assign`。
  - 后端候选路由：`Depends(require_permission("wecom:view"))`（router.py:253）；建客/绑客：`require_wecom_action("wecom:manage")`（router.py:265、294）。
  - 服务层注释明确“这里**故意不做数据范围过滤**……结果本身不直接对业务员开放：进待归一，由有 `wecom:manage` 的人确认”（service.py:566-569），但实际路由把候选开放给了所有 `wecom:view`，前端也没有按 `wecom:manage` 隐藏。
- 建议：
  - 后端候选接口至少同时要求 `customer:view`，并按调用者数据范围过滤；如果归一匹配必须全库比，返回给无 `customer:view` 的角色时只给“存在同名/同税号候选”的计数或脱敏摘要，不给客户名/负责人/等级。
  - 建客/绑客路由加 `customer:create`（建客）和 `customer:assign`/`customer:view`（绑客）校验；前端按钮同步按这些权限显示，不能再只用 `wecom:manage`。
  - 这是一个业务取舍点：归一匹配需要全库，但“看得见候选身份”和“能改归属”必须分层；建议由主人拍板是“全库匹配 + 脱敏返回”还是“按数据范围匹配”。
- 测试覆盖：**未覆盖**。`test_wecom_operation_permissions.py:18-46` 只测离职交接的权限/部门；`test_wecom_customer_import.py:194-215` 只测批量导入的三权限；没有 `unbound_candidates`、`bind-customer`、`create-customer` 的权限矩阵，也没有前端权限渲染测试。
- 备注：B15-02/B15-01 已从后端记录同一根因（B15 原按接口面记 P1）。本块按本轮“越权可见 = P0”的统一标尺记为 P0；建议验收时与 B15 条目合并定级，避免同一漏洞两个级别。

### F10-02｜P2｜待确认联系人列表查询失败时显示“没有待确认客户”，用户会把接口故障当成已清空

- 文件:行号：`frontend/src/modules/wecom/WeComPage.tsx:170-175`、`605-607`
- 触发条件：`/integrations/wecom/unbound-contacts` 返回 403/500/超时；或后端字段变更返回 422。
- 后果：
  - `listQuery.isError` 没有被消费；`rows = listQuery.data?.items ?? []` 变成空数组，`Empty description={listQuery.isLoading ? '加载中…' : '没有待确认客户'}` 显示“没有待确认客户”。
  - 操作者会以为企微联系人已经全部归一/清理完，不再处理；实际待确认队列可能还有大量记录。三栏页的中栏/右栏也会因为没有 `active` 显示“请先选择联系人”，进一步强化“没有数据”的错觉。
  - 页面没有“重新读取”入口；只有切换/刷新浏览器才会重试。
- 证据代码：
  ```tsx
  const listQuery = useQuery({
    queryKey: ['wecom-unbound', { keyword, page }],
    queryFn: () => listUnboundContacts({ keyword, page, page_size: 20 }),
  })
  const rows = listQuery.data?.items ?? []
  ```
  605-607 行只判 `isLoading`，不判 `isError`。
- 建议：列表空态改成 `emptyText(listQuery, '没有待确认客户', ...)` 或显式 `listQuery.isError` 分支 + “重新读取”；错误时保留搜索框和表头，不要显示“没有待确认客户”。
- 测试覆盖：**未覆盖**。前端无测试；后端也没有“列表接口 500 时前端空态”的用例。

### F10-03｜P2｜新建任务没有请求键，弱网超时后重试会在任务列表里多出一条重复任务

- 文件:行号：`frontend/src/modules/task/TaskListPage.tsx:130-144`、`634-642`；`frontend/src/shared/api/task.ts:79-81`；后端 `backend/app/modules/task/router.py:485-492`
- 触发条件：点“新建任务”填写标题/优先级/截止时间，点“创建”；请求已在后端提交成功，但客户端超时/断网没收到响应；用户再次点“创建”。
- 后果：
  - `createTask` 没有 `request_key`/幂等键；后端 `POST /tasks` 也没有请求幂等记录（`router.py:485-492` 直接 `TaskCreate` 落库）。
  - 第二次请求会再建一条同样的任务；两条任务都会出现在列表/提醒/统计里。任务本身不是金额，但会造成重复待办、重复提醒和交接清单重复项。
  - 第一次失败后弹窗仍开着（`onError` 只 Toast，不清表单/不关弹窗），用户最自然的动作就是再点一次。
- 证据代码：
  ```tsx
  const createMutation = useMutation({
    mutationFn: () => createTask({ title: form.title, due_at: ..., priority: form.priority }),
    onSuccess: () => { Toast.success('任务已创建'); setCreateVisible(false); ... },
    onError: (error: Error) => Toast.error(error.message),
  })
  ```
  `createTask` 只发 `title/due_at/priority`（task.ts:79-81），没有请求键；后端建任务路由也没有 `request_key` 字段。
- 建议：任务创建接 `requestKey`（页面打开时生成，提交带上，成功后重置）；后端按 `(user_id, request_key)` 去重并返回第一次结果。或者在响应丢失时让用户先刷新列表确认是否已建，再允许重试。
- 测试覆盖：**未覆盖**。`test_request_idempotency.py` 覆盖的是 `customer:create`，不是任务创建；没有任务重复创建用例。

### F10-04｜P2｜批量完成/批量交接的勾选跨页、跨筛选保留，用户会把屏幕上看不见的任务一起提交

- 文件:行号：`frontend/src/modules/task/TaskListPage.tsx:107-109`、`236-243`、`558-571`、`581-589`、`158-159`
- 触发条件：
  - 在“待处理”页勾选几条任务，切到“已完成/已取消”或“只看我的/只看逾期”，或翻到第二页；原勾选仍在 `selectedVersions` 里，批量完成按钮仍显示“已选 N 条”。


- 建议：切换状态/负责人/逾期/页码/每页条数时清空选择；或在提交前把 `selectedIds` 与当前 `query.data.items` 求交集，并明确提示“已选 N 条，其中 M 条不在当前视图”。如果要做跨页批量，界面必须显示完整已选清单，不能只显示数量。

### F10-06｜P2｜企微单条建客/绑客没有请求键，响应丢失后重试会返回“已经归一过了”，用户无法判断是否已成功

  - 前端 `bindMutation`/`createMutation` 没有请求键，也没有“先查一次是否已成功”的补偿；用户看到的是失败 Banner，可能以为第一次没成功，转而去客户中心手工再建一个客户，反而造成真正的重复客户。

### F10-08｜P3｜回收站线索窄屏表把“删除人待核实”显示成 `—`

- 文件:行号：`frontend/src/modules/recycle/RecycleBinPage.tsx:203-210`
- 触发条件：窗口宽度 <1200（`compact=true`），线索回收站里有 `deleted_by_pending=true` 的历史记录。
- 后果：
  - 宽屏分支用 `renderDeletedBy(v, record.deleted_by_pending)`，待核实时显示“待核实”；窄屏分支直接 `record.deleted_by_name ?? '—'`，没有看 `pending`。
  - 历史操作人未知的记录会显示成 `—`，与“本来就没有删除人”混在一起；用户可能放弃追溯，或误判为系统没记录。
- 证据代码：
  ```tsx
  compact ? (
    <span>{record.deleted_by_name ?? '—'}</span>
  ) : (
    renderDeletedBy(v, record.deleted_by_pending)
  )
  ```
  产品/SKU/客户表窄屏都用了 `record.deleted_by_pending ? '历史操作人待核实' : ...`，只有线索表漏了。
- 建议：窄屏分支也走 `renderDeletedBy` 或显式判断 `deleted_by_pending`。
- 测试覆盖：**未覆盖**。前端无测试；没有窄屏删除人展示用例。
