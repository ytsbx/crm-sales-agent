## 三、发现

### F02-01 P1：回款登记幂等键在关闭/重开表单后重置

- **位置**：`OrderDetailPage.tsx:936-945`、`2494-2500`、`519-527`；后端幂等语义见 `backend/tests/test_payment_consistency.py:258-280`。
- **触发条件**：用户点“登记回款”时 `paymentKeyRef.current = newRequestKey()`；首次提交已经在服务端落库，但响应超时/断网；用户关闭弹窗（`onCancel` 只 `setPaymentTarget(null)`，不清键），再打开同一期，重新生成新键并再次提交。
- **后果**：后端把两次提交当成两笔真实回款（测试明确：同额同日、不同键必须保留两行），产生两笔 `pending`。财务若都确认，`received_amount` 与应收分配被重复计入，形成重复入账。
- **证据代码**：
  ```tsx
  // 打开表单：每次打开都换一把新键
  setPaymentTarget(record)
  paymentKeyRef.current = newRequestKey()        // :936-945

  // 关闭：只清目标，不清键；下次打开又会覆盖成新键
  onCancel={() => setPaymentTarget(null)}         // :2494-2500

  // 只有成功才清空
  paymentKeyRef.current = ''                      // :519-527
  ```
  后端测试 `test_same_amount_same_day_with_different_keys_keeps_two_rows` 明确断言不同键会保留两行；`test_same_request_key_creates_one_row_and_replays` 证明同键才会回放。
- **建议**：把键按“应收期 + 表单会话”保存；关闭弹窗不丢键，重开同一期复用；只有成功、或用户明确“重新登记一笔”时才换键。也可以让后端对“同一期 + 同额 + 同日 + 短时间”做二次确认，但不能只靠金额去重。
- **测试覆盖**：**部分覆盖**。后端同键重放/不同键两行有测试；前端“关闭重开换键”没有测试。

### F02-02 P1：手工建单把数量/单价 `Number()` 后提交，16 位边界丢精度

- **位置**：`OrderListPage.tsx:201-208`、`170-174`；`shared/api/order.ts:217-234`；后端约束 `backend/app/modules/order/schema.py:117-119`。
- **触发条件**：主管使用“手工建单”，数量或单价接近后端允许的 16 位精度边界。后端 `OrderItemInput.quantity` 是 `Numeric(16,3)`、`unit_price` 是 `Numeric(16,4)`，前端却先 `Number()`。
- **后果**：JS 双精度在 16 位边界丢末位，提交的数量/单价已经不是用户输入的值，后端按错误值算 `line_amount` 和订单总额，后续应收计划全部跟着错。
- **证据代码**：
  ```tsx
  createMutation.mutate({
    items: enteredItems.map(({ item }) => ({
      quantity: Number(item.quantity),       // :204
      unit_price: Number(item.unit_price),   // :205
    })),
  })
  ```
  Node 实测：
  ```text
  Number('9999999999999.999') => 9999999999999.998
  ```
  这不是显示误差，提交的 JSON 就是 `9999999999999.998`；后端 schema 明确允许 16 位、3 位小数。
- **建议**：`createOrder` 的金额/数量明细改成 `string` 或 `quantity_exact`/`unit_price_exact`，提交原始字符串；预览合计同样用 BigInt/十进制定点，不要先转 number。后端已按 Decimal 计算，前端不要提前降精度。
- **测试覆盖**：**未覆盖**。`test_batch14_order_safety.py` 只测文本字段长度，没有测前端 number 化后的 16 位精度。

### F02-03 P1：手工建单没有 `request_key`，超时重试重复建正式订单

- **位置**：`OrderListPage.tsx:175-214`；`shared/api/order.ts:217-234`；后端路由 `backend/app/modules/order/router.py:100-175`。
- **触发条件**：手工建单 POST 已在服务端提交成功，但响应在弱网/超时中丢失；`createMutation` 报错，弹窗不关闭；用户再点“创建订单”。
- **后果**：后端没有请求幂等，第二次 POST 再建一张正式订单（以及后续应收），成交额、业绩、发货计划都多一份。B04-02 已确认“手工单重复”是后端缺口，这里前端也没有提供任何键。
- **证据代码**：
  ```tsx
  const createMutation = useMutation({
    mutationFn: createOrder,   // :175-176
    ...
  })
  ```
  `createOrder` 的 payload 类型只有客户/明细/负责人等，没有 `request_key`；后端 `create_order` 也没有 `idempotency.reserve`。
- **建议**：给手工建单加 `request_key`（打开弹窗生成、成功才清），后端用通用幂等表；或者至少让后端按“客户 + 明细 + 金额 + 短时间”要求二次确认。不要只靠按钮 `confirmLoading`。
- **测试覆盖**：**未覆盖**。`test_opportunity_links.py` 只调用 `orders.create_order`，没有重复 POST 用例。

### F02-04 P1：人工履约状态可直接选“已发货/已签收”，绕过发货批次

- **位置**：`OrderDetailPage.tsx:2283-2300`、`789-793`；后端 `backend/app/modules/order/service.py:563-650`。
- **触发条件**：订单还没有任何发货批次，或实发量为 0；有 `order:manage` 的用户打开“人工更新履约状态”，选择 `shipped` 或 `delivered`。
- **后果**：订单状态直接变成“已发货/已签收”，但发货批次、实发数量仍是 0；看板、交期偏差、客户跟进都按错误状态展示。后端 `change_status` 只对 `completed` 校验未发量，对 `shipped`/`delivered` 没有闸门；前端也只拦 `completed`。这不是单纯 UI 问题，是状态机缺流转矩阵。
- **证据代码**：
  ```tsx
  // 前端只拦 completed
  const completionBlocked = completingDelivery && ... Number(remainingToShip) > 0
  const statusBlocked = targetStatus ? completionBlocked : '先选择...'

  optionList={[
    { value: 'pending', ... },
    { value: 'in_production', ... },
    { value: 'shipped', ... },     // 未发货也能选
    { value: 'delivered', ... },   // 未签收也能选
    { value: 'completed', ... },
  ]}
  ```
  后端同样只在 `new_status == 'completed'` 时查 `all_shipped`；`shipped`/`delivered` 直接落状态。
- **建议**：前端按“实际发货批次/实发量”控制选项：未发货不能选 shipped，未全部签收不能选 delivered；后端 `change_status` 增加同样的流转矩阵，不能只信前端。已完成回退也不能只靠 remark。
- **测试覆盖**：**未覆盖**。没有状态流转矩阵测试；B04-03 已记录后端缺口。

### F02-05 P1：订单取消后，未回款应收期仍显示“删除”，后端也能删掉已取消订单的应收历史

- **位置**：`OrderDetailPage.tsx:892-901`、`904-910`；后端 `backend/app/modules/payment/router.py:475-520`。
- **触发条件**：订单取消后，未回款的应收节点被置为 `cancelled`；用户有 `payment:manage`，打开“应收计划”，该行 `has_payment_record=false`。
- **后果**：`canDelete = canPayment && !hasPayment` 没有排除 `planCancelled`，所以已取消订单的行仍显示“删除”。后端删除只查“有没有回款/分配”，不查节点或订单是否已取消，删除会成功；已取消订单的应收历史被删掉，`sync_payment_milestones` 还会按剩余应收重算跟单节点。虽然写审计，但原始财务记录已经丢失。
- **证据代码**：
  ```tsx
  const planCancelled = record.status === 'cancelled' || order.status === 'cancelled'
  const canRegister = record.status !== 'paid' && !planCancelled && canRegisterPayment
  const hasPayment = Boolean(record.has_payment_record)
  const canDelete = canPayment && !hasPayment      // 没有 !planCancelled
  ```
  下面的 `if (!canRegister && !canDelete)` 只有在两者都 false 时才显示“订单已取消，这一期不再收款或删除”；只要 `canDelete` 为 true，就会走到删除入口。
- **建议**：`canDelete = canPayment && !hasPayment && !planCancelled && !orderCancelled`；后端 `delete_receivable` 也要拒绝 `plan.status == 'cancelled'` 或 `order.status == 'cancelled'`，让前端和后端同一把尺子。
- **测试覆盖**：**部分覆盖**。`test_payment_consistency.py:574-582` 只测“有回款不能删”，没有测“已取消节点不能删”。

### F02-06 P2：生成应收的 `request_key` 每次提交新建，后端同键回放被绕过

- **位置**：`OrderDetailPage.tsx:459-477`；后端 `backend/tests/test_payment_consistency.py:542-557`。
- **触发条件**：用户点“生成应收计划”，首次请求已提交但响应超时；再点一次，`mutationFn` 内又执行 `newRequestKey()`。
- **后果**：两次提交的键不同，后端“同键回放第一次结果”的能力完全没用上。当前后端还有“该订单已有应收计划”的闸门，第二次通常报冲突而不是重复落库；但用户会把“已成功”误判成“失败”，且一旦闸门被绕过/未来改成允许追加，就会重复生成应收。
- **证据代码**：
  ```tsx
  const created = await generateReceivables(orderId, {
    ...
    request_key: newRequestKey(),   // :476，每次调用都新键
  })
  ```
  后端 `test_generate_with_request_key_replays_instead_of_conflict` 明确要求同键第二次回放，不是冲突。
- **建议**：和回款一样，键在打开“生成应收计划”弹窗时生成，失败重试复用，成功后才清；不要写在 `mutationFn` 里。
- **测试覆盖**：**部分覆盖**。后端同键回放有测试；前端“每次换键”没有测试。

### F02-07 P2：排发货批次的请求键关闭弹窗即重置，超时重开可重复排计划批次

- **位置**：`OrderDetailPage.tsx:1703-1708`、`1843`、`603-620`；后端 `backend/app/modules/order/router.py:1277-1300`。
- **触发条件**：首次“保存批次”已在服务端提交，但响应超时；用户关闭弹窗（`onCancel` 只 `setCreateShipmentVisible(false)`），再打开同一单，重新生成键并提交相同数量。
- **后果**：后端按新键再建一批。因为首批只占部分未计划量时，第二批仍能通过“计划量不得超过未计划量”的校验，最终同一批生产被排两次；这不是金额错误，但会让生产/发货计划重复。
- **证据代码**：
  ```tsx
  // 每次打开都换键
  shipmentKeyRef.current = newRequestKey()        // :1705

  // 关闭只隐藏，不清键；下次打开又覆盖
  onCancel={() => setCreateShipmentVisible(false)} // :1843

  // 成功才清空
  shipmentKeyRef.current = ''                      // :618
  ```
  后端 `create_shipment` 明确支持 `request_key` 并在同键时回放；前端重开换键使这个能力失效。
- **建议**：键按“订单 + 批次表单会话”保存，关闭不丢；重开同一单复用；只有成功或明确“重新排一批”才换键。
- **测试覆盖**：**未覆盖**。后端有键实现，没有前端重开换键的用例。

### F02-08 P2：“已完成”回退理由固定传“在订单详情页更新”，后端必须填理由的闸门被架空

- **位置**：`OrderDetailPage.tsx:419-420`；后端 `backend/app/modules/order/service.py:638-650`。
- **触发条件**：订单已 `completed`，用户打开“人工更新履约状态”，选择 `pending`/`in_production`/`shipped`/`delivered` 回退。
- **后果**：后端明确要求“已完成回退必须填理由，理由进状态变更留痕”；前端没有理由输入，却固定传 `remark='在订单详情页更新'`。后端只判 `remark.strip()` 非空，于是回退一路放行，审计里只有一句无意义的固定文案，事后无法回答“为什么把已完成改回去”。
- **证据代码**：
  ```tsx
  mutationFn: () => changeOrderStatus(orderId, targetStatus!, '在订单详情页更新')  // :420
  ```
  后端：
  ```python
  if order.status == "completed" and new_status != "completed":
      if not (remark or "").strip():
          raise AppError(... "必须填写理由" ...)
  ```
  固定文案让 `strip()` 永远非空。
- **建议**：回退时弹一个必填“回退理由”，把真实理由传给后端；后端校验不能只判非空，最好拒绝固定占位文案或要求最小长度/原因码。
- **测试覆盖**：**未覆盖**。没有 completed 回退理由测试。

### F02-09 P3：回款金额只判 finite 且 >0，没有 2 位小数/16 位上限

- **位置**：`OrderDetailPage.tsx:2501-2505`；后端 `backend/app/modules/payment/schema.py:145-149`。
- **触发条件**：用户在“实际到账金额”输入 `1.234`、`9999999999999999` 等。
- **后果**：前端放行，提交到后端才因 `decimal_places=2`/`max_digits=16` 报 422；错误信息直接显示，用户不知道是“位数超了”还是“金额不对”。不会写错账，但把校验完全推给后端。
- **证据代码**：
  ```tsx
  if (!paymentForm.amount.trim() || !Number.isFinite(Number(paymentForm.amount)) || Number(paymentForm.amount) <= 0) {
    Toast.warning('请填写大于 0 的实际到账金额。')
    return
  }
  ```
  没有 `^\d+(\.\d{1,2})?$` 或长度检查；后端 schema 明确 `gt=0, max_digits=16, decimal_places=2`。
- **建议**：复用 `paymentCents` 做前端预校验，明确提示“最多两位小数、最多 16 位”；不要把原始字符串直接发出去等后端报错。
- **测试覆盖**：**未覆盖**。后端 schema 有边界，前端金额校验没有测试。

### F02-10 P3：404/403/500/超时统一成“订单不存在或无权查看”，多处直接回显后端 error.message

- **位置**：`OrderDetailPage.tsx:749-763`、`2318`、`2384`、`2419`、`2470`；`OrderListPage.tsx:92`、`131`、`139`、`190`；`OrderDraftsPage.tsx:125`、`169`、`275`、`287`。
- **触发条件**：订单详情查询返回 500/网络超时；或任何 mutation 返回后端错误。
- **后果**：详情页把 500/超时也显示成“订单不存在或无权查看”，用户会误以为订单被删/自己没权限，不会重试；列表/草稿/弹窗多处直接 `Toast.error(error.message)` 或 `<p>{error.message}</p>`，把后端校验细节、内部字段名原样展示。
- **证据代码**：
  ```tsx
  if (!order) {
    return <EmptyState title="订单不存在或无权查看" hint="可能链接里的编号有误..." />
  }
  ```
  `OrderDraftsPage` 还有：
  ```tsx
  {list.error && <p>{list.error.message}</p>}
  ```
- **建议**：按 HTTP 状态/错误码分流：404 显示不存在，403 显示无权限，5xx/网络显示“读取失败，请重试”并保留重试按钮；错误文案统一走脱敏映射，不直接展示 `error.message`。
- **测试覆盖**：**未覆盖**。

### F02-11 P3：确认/驳回回款、状态变更使用固定审计说明，钱操作原因不可区分

- **位置**：`OrderDetailPage.tsx:532-539`、`419-420`；`OrderListPage.tsx:125-140`。
- **触发条件**：财务在订单详情或回款中心确认/驳回；订单负责人更新履约状态。
- **后果**：确认固定传“财务核对通过”，驳回固定传“金额或凭证有误”，状态变更固定传“在订单详情页更新”。审计有记录，但原因字段是固定文案；事后无法区分“金额错”“凭证缺”“重复付款”等不同驳回原因，也无法解释状态变更。
- **证据代码**：
  ```tsx
  const confirmMutation = useMutation({ mutationFn: (id) => confirmPayment(id, '财务核对通过') })
  const rejectMutation = useMutation({ mutationFn: (id) => rejectPayment(id, '金额或凭证有误') })
  ```
- **建议**：驳回弹窗增加原因选择/必填说明；确认可保留默认但允许补充备注；状态变更（尤其回退）必须填真实理由。审计记录应保存用户输入，不要用固定占位。
- **测试覆盖**：**部分覆盖**。确认流程有测试，未测审计原因内容；`test_batch15_financial_lifecycle.py:214` 只测取消随单驳回的固定 comment。

### F02-12 P3：订单草稿保存/确认无 `request_key`，弱网重试会 409 卡住

- **位置**：`OrderDraftsPage.tsx:93-113`；`shared/api/order.ts:651-652`。
- **触发条件**：草稿保存/确认已在服务端成功，但响应超时；用户再点。
- **后果**：保存用旧 `revision`，确认用旧 revision/status；后端乐观锁会返回冲突，不会重复建单，但用户无法判断“第一次到底成功没有”，只能刷新。不是金额错误，是流程卡顿。
- **证据代码**：
  ```tsx
  const save = useMutation({ mutationFn: () => updateOrderDraft(draftId, {
    revision: query.data!.revision, ...   // 无 request_key
  })})
  const confirm = useMutation({ mutationFn: ({ id, revision, versionId }) =>

  ```

- **建议**：保存/确认也加 `request_key`；或者后端对“同 revision + 同 payload”的重复请求回放成功结果，而不是一律 409。
- **测试覆盖**：**部分覆盖**。stale/converted 有测试，弱网重试无测试。

### F02-13 P3：订单明细数量展示走 `number.toLocaleString()`，没有 `quantity_exact`

- **位置**：`OrderDetailPage.tsx:825`；`shared/api/order.ts:64`。
- **触发条件**：订单明细数量接近 `Numeric(16,3)` 上限，后端 JSON 把它作为 number 返回。
- **后果**：`quantity` 没有 exact 字符串，`v.toLocaleString('zh-CN')` 只能显示已经 number 化的值；数量与金额行可能对不上。金额本身走了 `amount_exact`，所以这是展示/核对问题，不是金额计算入口。
- **证据代码**：
  ```tsx
  { title: '数量', dataIndex: 'quantity', width: 64, render: (v: number) => v.toLocaleString('zh-CN') }
  ```
  `OrderItem` 只有 `quantity: number`，没有 `quantity_exact`。
- **建议**：后端出参补 `quantity_exact`，前端优先用它；至少在大数量时不要用 number 做展示。若 API 实际返回字符串，应修正 TS 类型，避免 `toLocaleString` 的隐式转换掩盖问题。
- **测试覆盖**：**未覆盖**。

## 四、补充维度核对（负数/0/超大值、事务、异常、审计、测试）

| 维度 | 本块看到的事实 | 结论 |
|---|---|---|
| 金额是否全程 Decimal | `OrderDetail` 的订单金额、应收、回款展示优先用 `*_exact`；`AllocationAdjustModal` 用 `paymentCents` BigInt；`OrderDrafts` 的数量/单价用字符串提交。**但 `OrderListPage` 手工建单把数量/单价 `Number()` 后提交**，`OrderDetail` 数量展示也没有 `quantity_exact` | 展示大体走 exact，**手工建单提交路径是明确缺口**（F02-02、F02-13） |
| 负数、0、超大值、小数位超限 | 手工建单：数量 >0、单价 >=0，但未限制 16 位/3 位、16 位/4 位；回款：只判 finite 且 >0，未限制 2 位小数/16 位；分配：`paymentCents` 已限制非负、最多 2 位；发货：`requiredQuantityText` 限制 3 位小数，实发允许 0 但整批至少一项 >0；草稿：后端 schema 兜底，前端不预校验 | 负数/0 基本有拦；**超大值/小数位超限主要靠后端 422**（F02-02、F02-09） |
| 事务边界（中途失败留半成品） | 生成应收已改成“整份计划一次 POST”，注释明确后端同事务；回款分配是整份替换；手工建单/草稿保存/批次创建都是单请求；前端没有“先建头再逐条补明细”的写路径 | 前端未发现半成品写路径；实际回滚依赖 B04/B05 的后端事务，本块未重审 |
| 异常是否被吞 | `OrderDetail` 的 `statusMutation`、`generateMutation`、`dueMutation` 没有 `onError`，但弹窗内有 `mutation.error` Banner；`cancelMutation.onError` 只刷新回款，错误 Banner 在 `!cancellationBlocked` 时显示；`AllocationAdjustModal` 保存失败有 Banner；`OrderDrafts` 保存/需求单有 Toast，确认失败有 Banner | 没有发现“完全无提示”的吞异常；但存在**错误被错误态覆盖**和直接回显原始文案（F02-10） |
