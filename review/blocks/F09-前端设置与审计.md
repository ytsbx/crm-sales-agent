### F09-04｜P2｜审批分档金额上限用 JS `Number` 解析，16 位两位小数会丢分、可能把报价分到下一档

- 文件:行号：`frontend/src/modules/settings/SettingsPage.tsx:2596`、`2659-2704`；后端证据 `backend/app/modules/settings/service.py:491-508`
- 触发条件：在“报价审批分级”的金额上限填 16 位有效数字（报价表 `Numeric(16,2)`，最大 99,999,999,999,999.99），例如 `99999999999999.99`。
- 后果：
  - `Number(text)` 在 1e14 量级已无法表示分位，可能变成 `100000000000000` 或 `99999999999999.98`；`prevMax` 也是 number，逐档递增比较同样有误差。
  - 保存到后端的是这个已丢失精度的 number；`_strict_amount` 只校验字符串格式，不会恢复原始文本。最终审批上限可能与管理员输入的金额差 1 分以上，边界报价可能落到下一档，找错审批角色。
  - 这是审批路由阈值，不是报价金额本身；影响流程，不改报价金额。
- 证据代码：
  - `const AMOUNT_TEXT_PATTERN = /^\d+(\.\d{1,2})?$/`（2596 行）允许任意长度数字。
  - `const parsed = Number(text)`（2689 行）；`prevMax = parsed`（2702 行）；`max_amount: parsed`（2704 行）。
  - 后端 `_strict_amount(raw, ...)` 接受 `int/float/str`，`Decimal(str(raw).strip())`（service.py:503-504）；JSON 里已经是 JS number，无法恢复原文。
- 建议：金额上限保持原始字符串传给后端（后端已有 `_strict_amount` 支持 str），前端比较用十进制字符串/BigInt 分单位；或者至少限制到 `Number.MAX_SAFE_INTEGER` 内并说明不支持 16 位；同时补一个上限（如不超过报价 `Numeric(16,2)` 最大值）。
- 测试覆盖：`backend/tests/test_settings_number_bounds.py:167` 只验证 `approval_levels` 不被通用数值规则误拦，没有 16 位精度/上限测试；前端无测试；**未覆盖**。

### F09-05｜P2｜公海规则“天数”和“启用”并发保存会用旧值互相覆盖

- 文件:行号：`frontend/src/modules/settings/SettingsPage.tsx:767-775`、`1952-1970`、`1978-1983`
- 触发条件：管理员把某档“未跟进天数”从 30 改成 60，输入框失焦触发保存；在请求返回前又点了同行的“启用/停用”开关。
- 后果：
  - 失焦请求发送 `{ days: 60, enabled: record.enabled }`；开关请求发送 `{ days: record.days（旧的 30）, enabled: 新值 }`。两个 PATCH 都带全字段，后端按最后到达的请求覆盖。
  - 最终可能保存成 `days: 30, enabled: 新值`，管理员刚改的 60 天被静默回退；两个 Toast 都提示“公海规则已保存”，没有冲突提示。
  - 公海回收天数直接决定客户何时进入回收候选；回退会改变业务节奏。
- 证据代码：
  - `poolRuleMutation.mutate({ id: record.id, days: next, enabled: record.enabled })`（1968 行）。
  - Switch：`poolRuleMutation.mutate({ id: record.id, days: record.days, enabled: value })`（1982 行）。
  - `updatePublicPoolRule(id, { days, enabled })`（768-769 行）每次发全字段；mutation 没有 per-row pending/串行。
- 建议：每行维护一个 draft（days/enabled 一起提交），或只发送本次变更的字段（后端 Patch 支持 `exclude_unset`），或在保存中禁用该行两个控件；至少要在响应后以服务器值回填，不能用旧 query 覆盖。
- 测试覆盖：没有公海规则前端测试/并发测试；**未覆盖**。

- 后果：
  - `next <= 0` 或非整数时只 `Toast.warning('公海回收天数须为正整数')` 并 `return`，没有把 `event.target.value` 回填成 `record.days`。
  - 输入框（`defaultValue` 非受控）仍显示非法值；用户看到“0 天”但数据库仍是旧值，容易误以为已经保存，或下次刷新才“跳回去”。
- 证据代码：`defaultValue={String(days)}`（1954 行）；`if (!raw || !Number.isInteger(next) || next <= 0) { Toast.warning(...); return }`（1963-1965 行）；合法时才 `poolRuleMutation.mutate`。
- 建议：校验失败时 `event.target.value = String(days)` 或改成受控输入 + 本地 draft；错误提示要说明“已恢复为原值，未保存”。
- 测试覆盖：无前端测试；**未覆盖**。

## 三、补充维度检查

### 负数、0、超大值、小数位超限

- 审批金额上限：`AMOUNT_TEXT_PATTERN` 拦负数、科学计数法和超过 2 位小数，但没有上限，且用 `Number` 解析 16 位金额会丢分（F09-04）。
- 公海天数：前端要求正整数，但 0/负数/小数只弹 Toast 不回填（F09-10）；没有上限，后端 `settings/service.py` 的池回收规则有自身校验。
- 自动任务天数：`^\d+$` + `Number.isSafeInteger`，拦住负/小数；没有 36500 上限，超大值保存后运行时后端会按规则报错/跳过，属于配置可错但不会生成错误金额。
- 未分级规则：前端限制 1～36500，开关打开但空值有明确提示；未发现前端漏校验。
- 标签/角色/部门名称：没有金额；前端主要靠后端 400/422，未做统一长度/必填内联校验（P3 体验，不单独升级）。

### 事务边界

- 设置页的写操作基本是“一次 PATCH 一个 key/一个资源”，后端单事务；不存在“订单建了但明细没建”的前端多步事务。
- `NotificationSettingsPanel` 的保存是两步：先 `updateLevelPolicy`，再 `updateNotificationSettings`；第二步失败时第一步已提交，代码保留 channelDraft 并提示“发送方式已保存，通知渠道未保存”，属于**明确告知的部分成功**，不是静默半成品。
- 公海规则天数/开关并发是两个独立 PATCH，会互相覆盖旧值（F09-05），属于配置层的并发事务问题。
- 审计页只读；补发通知由后端 `requeue_for_redispatch` 行锁 + `skip_locked` + 状态 pending 防重复选中，前端重复点击不会重复入账。

### 异常吞掉 / 错误信息泄露 / 日志敏感信息

- F09-01、F09-06、F09-08 都是“读取异常被空态吞掉”；这是本块最多的异常处理问题。
- 设置页 mutation 的 `onError` 多处直接 `Toast.error(error.message)`，后端返回 AppError 文案；没有看到 SQL/堆栈，但也没有按状态码分类。
- 审计明细原始 JSON（F09-07）是“技术信息展示”而非日志泄露；前端没有 `console.log` 打印密码/token。
- `PersonalAccountPanel` 的密码输入是 `mode="password"`，没有明文回显；错误提示不包含密码内容。

### 关键钱操作审计

- 本块没有报价/订单/收款金额写入；关键配置（审批分级、公海规则、自动任务、通知设置、标签、用户/角色）在后端都有 `write_audit`，前端只发起请求。
- `saveSetting`、`updatePublicPoolRule`、`updateTaskRule`、`retry_failed_notifications`、`run_auto_tasks` 后端均写审计；本块未发现“改了钱相关配置但不留痕”的路径。
- 但审计查看端把原始 JSON 摊开（F09-07），这是“怎么看审计”的问题，不是“有没有写审计”的问题。

### 对照 `backend/tests`

- `backend/tests/test_settings_number_bounds.py:167` 只验证 `approval_levels` 不被通用数值规则误拦，不验证 16 位审批上限精度。
- `backend/tests/test_audit_exclusion.py:44` 覆盖 `/audit-logs` 的排除/分页；`test_audit_search.py` 覆盖中文搜索，不覆盖前端错误态或明细展示。
- 没有标签状态、角色创建状态、公海规则并发、部门层级前端测试；前端无测试目录。
- 以上只是“用例是否覆盖触发条件”的静态对照，没有运行测试。

## 五、结论

F09 没有发现 P0/P1。最重的是配置/权限控制层的“控件看起来生效、实际没提交或提交错值”：标签状态、角色创建状态、审批分档金额上限、公海规则并发覆盖；其次是设置页/审计页把读取失败伪装成空数据，以及审计明细违反已确认的原始 JSON 展示约束。建议优先修 F09-02、F09-03、F09-04、F09-05、F09-06、F09-07。
