### B13-01 客户 360 的订单金额汇总把取消单算进“累计成交”

- **严重度：P1**
- **文件:行号：** `backend/app/modules/customer/service.py:287-307`（`order_base` 与 `func.sum`）
- **触发条件：** 客户名下有 `status="cancelled"` 的 `SalesOrder`，当前用户有 `customer:view` 且 `order:view`，打开客户 360 或调用 Agent 客户摘要。
- **后果：** `counts.order_amounts` 按币种汇总时把取消单的 `total_amount` 一起 SUM；看板/摘要的“累计成交”金额虚高。`pending_receivable` 已正确把取消单置 0，说明取消单不应进入财务口径，但订单金额汇总没有同样排除。
- **证据代码：**

```python
order_base = scoped(
    select(SalesOrder).where(SalesOrder.customer_id == customer_id), SalesOrder
)
order_total = await count_of(order_base)
order_sub = order_base.order_by(None).subquery()
amount_rows = (
    await session.execute(
        select(order_sub.c.currency, func.sum(order_sub.c.total_amount))
        .group_by(order_sub.c.currency)
        .order_by(order_sub.c.currency)
    )
).all()
```

`order_base` 只有 `customer_id` 条件，没有 `SalesOrder.status != "cancelled"`；`func.sum` 直接汇总全表符合条件的金额。

- **建议：** 在订单金额汇总（以及若 `counts.orders` 语义是“成交订单数”）加 `SalesOrder.status != "cancelled"`；如果仍要展示“全部订单数”，拆成 `orders_total` 与 `effective_orders_total`，并在响应里明确字段语义。前端/Agent 摘要改用有效订单口径。
- **测试覆盖：** `backend/tests/test_customer_summary_precision.py:27-44` 只测金额精度、权限和 scope；`backend/tests/test_agent_scope_and_receivables.py:266-300` 只测 `pending_receivable` 排除取消单，且明确期望 `orders` 列表包含取消单；没有用例断言 `order_amounts` 排除 `cancelled`。**部分覆盖，关键缺口未覆盖。**

### B13-02 合并税号冲突只校验非空，任意字符串可绕过“必须确认”

- **严重度：P1**
- **文件:行号：** `backend/app/modules/customer/tags.py:660-671`、`backend/app/modules/customer/tags.py:500-515`；入参 `backend/app/modules/customer/tags_schema.py:58`
- **触发条件：** 来源/目标客户税号不同，调用 `POST /customers/merge` 时传 `resolutions={"tax_no": "anything"}`（不需要是界面上的 `confirm`）。
- **后果：** `unresolved` 只检查 `given.get(key)` 是否为真；税号冲突只有 `confirm` 一个合法选项，却没有像 `customer_price` 那样校验值。调用方拼错/伪造一个非空字符串，就能把两家不同法律主体合并；来源税号丢失，`conflicts_applied` 还会把伪造值写进审计。合并本身不可逆。
- **证据代码：**

```python
conflicts = await _detect_conflicts(session, source=source, target=target)
given = resolutions or {}
unresolved = [row for row in conflicts if not given.get(row["key"])]
if unresolved:
    raise AppError(...)
conflicts_applied = {row["key"]: given[row["key"]] for row in conflicts}
```

税号冲突定义：

```python
if source.tax_no and target.tax_no and source.tax_no != target.tax_no:
    conflicts.append({
        "key": "tax_no",
        "label": "协议主体（纳税人识别号不一致）",
        "options": [
            {"value": "confirm", "label": "确认是同一家、继续合并（税号保留目标客户的）"}
        ],
        ...
    })
```

同一文件的价格冲突分支明确校验 `choice not in ("keep_source", "keep_target")`；税号分支没有对应校验。

- **建议：** 对所有 `conflicts` 统一按 `options` 做白名单校验；`tax_no` 只接受 `confirm`，否则 422。更稳妥的做法是税号不同时要求显式布尔确认/二次确认令牌，并在审计里记录确认人、时间和两个税号快照。
- **测试覆盖：** `backend/tests` 中没有 `merge_customers` 的税号冲突用例；`test_seventh_round_imports.py` 只覆盖开案，`test_customer_duplicate_scope.py` 只覆盖列表可见性。**未覆盖。**

- **测试覆盖：** `test_seventh_round_imports.py` 覆盖部分导入失败场景，但没有断言响应里不出现 SQL/约束原文。**未覆盖错误信息内容。**

### B13-07 客户 360 商机预计金额、订单总额、客户报价当前版本金额仍以 float 出参

- **严重度：P2**
- **文件:行号：** `backend/app/modules/customer/service.py:24-26`（`_f`）、`388`（`expected_amount`）、`411`（`total_amount`）；`backend/app/modules/customer/router.py:762`（`current_version_amount`）
- **触发条件：** 商机预计金额、订单总额或报价当前版本总额包含超过 2 位小数/大额值（如 `99999999999999.99`、`123.445`），前端或 Agent 直接使用 float 字段。
- **后果：** `float(Decimal)` 丢失精度；`expected_amount` 只有 float、没有 `_exact`；客户报价列表的 `current_version_amount` 只有 float，没有 `current_version_amount_exact`。订单总额虽有 `total_amount_exact`，但仍有调用方可能只用 `total_amount`。这会让客户 360/报价列表显示的分位与大额失真。
- **证据代码：**

```python
def _f(value) -> float | None:
    """Decimal/None → float/None。序列化 Numeric 字段时统一走这里。"""
    return None if value is None else float(value)
```

```python
"expected_amount": _f(row.expected_amount),
...
"total_amount": _f(row.total_amount),
"total_amount_exact": str(row.total_amount) if row.total_amount is not None else None,
```

```python
"current_version_amount": float(version.total_amount) if version else None,
```

- **建议：** 所有金额出参统一给“精确字符串/Decimal 序列化”字段（`*_exact`），float 仅作兼容；`expected_amount_exact`、`current_version_amount_exact` 补齐；前端/Agent 一律读 exact。若接口契约要求数字类型，至少用字符串承载金额，不要让 float 参与前端计算。
- **测试覆盖：** `test_customer_summary_precision.py:27-44` 覆盖 `order_amounts.amount_exact` 与订单 `total_amount_exact`；没有覆盖商机 `expected_amount`、客户报价 `current_version_amount`。**部分覆盖。**

### B13-11 标签创建/更新撞唯一约束时在 service 内回滚整个 session

- **严重度：P3**
- **文件:行号：** `backend/app/modules/customer/tags.py:118-125`、`145-150`
- **触发条件：** 两个请求并发创建/更新同名标签，后到请求在 `flush()` 时撞唯一约束。
- **后果：** `except IntegrityError` 里直接 `await session.rollback()`，回滚的是整个 session，不只这条标签的 INSERT/UPDATE。当前路由在标签写入后只写一条 audit，回滚后 audit 也不会提交，影响有限；但一旦未来把 `create_tag/update_tag` 复用到批量导入、设置初始化或更大的事务中，同事务的其他写入会被一起回滚，且调用方难以察觉。
- **证据代码：**

```python
try:
    await session.flush()
except IntegrityError as exc:
    await session.rollback()
    raise AppError(ErrorCode.DUPLICATE, f"标签「{name}」已存在", 409) from exc
```

`update_tag` 的 `except` 同样 `session.rollback()`。

- **建议：** 用 `async with session.begin_nested():`（SAVEPOINT）包住 `flush()`，只回滚标签写入；或者把唯一约束冲突的翻译放到一个独立的 unit-of-work，由调用方决定事务边界。至少不要在 service 层无提示地回滚整个 session。
- **测试覆盖：** 未找到并发同名标签的用例；现有标签测试是串行。**未覆盖。**
