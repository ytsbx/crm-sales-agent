### F08-02｜P2｜工作台/团队/趋势金额契约全是 `number`，后端用 float 汇总，`exactMoney` 并不能“精确”

- 文件:行号：`frontend/src/shared/api/analytics.ts:16-36`、`38-43`、`66-84`、`292-315`；`frontend/src/modules/workbench/WorkbenchPage.tsx:42-43`、`51-55`、`218`、`237`、`245`、`254-256`、`397`、`458`、`476`、`558-562`、`691`；后端证据 `backend/app/modules/analytics/service.py:84-85`、`533-543`、`605-621`、`2307-2313`
- 触发条件：订单/回款/商机金额达到 16 位有效数字附近，或趋势/团队汇总累计多笔金额；后端 `_f(value)` 先 `float(value or 0)`，趋势再用 `dict[str, float]` 累加。
- 后果：
  - `DashboardSummary` 的 `month_won_amount`、`month_order_goods_amount`、`month_order_logistics_amount`、`month_order_other_charge_amount`、`month_order_discount_amount`、`month_received_amount`、`month_received_by_arrival_amount`、`pending_receivable_amount` 都经过 float；`TeamSummary.team_won_amount_this_month`、`TeamMemberRow.won_amount_this_month` 同样。
  - `exactMoney` 只是 `(value ?? 0).toLocaleString(..., { maximumFractionDigits: 2 })`，输入已经是丢失精度的 number，无法恢复原始 Decimal；页面写“本月团队成交额”但可能比真实值少/多 1 分甚至更多。
  - 趋势接口 `order_amount`/`received_amount` 在 Python 侧用 float 累加后 `round(..., 2)`，近 6 个月合计再用前端 float 相加，展示的“近 6 个月订单合计/已确认回款”会继承误差。
- 证据代码：
  - 类型：`open_opportunity_amount: number`、`month_won_amount: number`、`month_received_amount: number`、`pending_receivable_amount: number`（16-35 行）；`TrendRow.order_amount: number`、`received_amount: number`（38-43 行）；`TeamMemberRow.won_amount_this_month: number`、`TeamSummary.team_won_amount_this_month?: number`（292-315 行）。
  - 后端：`def _f(value) -> float: return float(value or 0)`（84-85 行）；`"month_won_amount": _f(month_won_amount)` 等（533-543 行）；`orders: dict[str, float]`、`payments: dict[str, float]`、`orders.get(key, 0.0) + _f(amount)`（605-621 行）；`"team_won_amount_this_month": _f(won_amount)`（2307 行）。
  - 前端：`const exactMoney = (value?: number) => ... maximumFractionDigits: 2`（43 行）；`value: exactMoney(team.team_won_amount_this_month)`（397 行）；`exactMoney(member.won_amount_this_month)`（458 行）；`money(trend.reduce((sum, row) => sum + row.order_amount, 0))`（558 行）。
- 建议：后端 dashboard/team/trend 改为 Decimal 聚合，并返回 `*_exact` 字符串（与 `SalesUserStat`/`SalesTargetRow` 现有 exact 约定一致）；前端 `DashboardSummary`/`TeamSummary`/`TrendRow` 增加可选 exact 字段，`exactMoney` 接受字符串并优先使用 exact；图表可继续用 number，但 tooltip/表格/团队成交额必须走 exact。
- 测试覆盖：`backend/tests` 中没有 dashboard summary/team/trend 的金额精度测试；`test_customer_summary_precision.py` 只测客户汇总，`test_order_finance_summary_precision.py` 只测订单财务汇总。**未覆盖**。

### F08-03｜P3｜图表金额格式器按整元/万字取整，tooltip 与轴标签会抹掉分位

- 文件:行号：`frontend/src/shared/components/charts/options.ts:31-44`、`100`；`frontend/src/shared/components/charts/DonutLegend.tsx:78-80`；调用点 `frontend/src/modules/workbench/WorkbenchPage.tsx:89-90`
- 触发条件：金额不是整元，或达到万/亿级；例如 `123.45` 经 `asMoney` 显示 `¥123`，`1,999,999` 经 `compactMoney` 显示 `¥200万`。
- 后果：
  - 图表 tooltip、轴标签、柱端/环图图例显示的是取整后的金额，不是账户/订单金额；工作台趋势、分析页环图等场景会让业务人员按错误量级判断。
  - `compactMoney` 在 `>= 10 万` 时 `toFixed(0)`，会把 `199,999` 显示成 `20 万`；`DonutLegend` 的百分比也 `Math.round` 到整数，合计可能显示 99% 或 101%。
  - 这是展示层口径问题，不会回写数据库，但会降低“图表与台账对得上”的可信度。
- 证据代码：
  - `export const asMoney: ValueFormat = (value) => \`¥${Math.round(value).toLocaleString('zh-CN')}\``（33-34 行）。
  - `compactMoney`：`if (abs >= 10_000) return \`¥${(value / 10_000).toFixed(abs >= 100_000 ? 0 : 1)}万\``（39-44 行）。
  - `donutChartOption` 的 `format` 原样使用调用方传入的 `asMoney`（`options.ts:369` 的 tooltip）；`DonutLegend` `{format(item.value)}` 与 `Math.round((item.value / total) * 100)`（78-80 行）。
- 建议：图表 tooltip 改用 `formatMoney`/exact 文本（最多 2 位）；`compactMoney` 只用于轴刻度，并在 tooltip 中提供精确值；`DonutLegend` 百分比保留 1 位或显示原始比例；如果确实要整元概览，明确标注“约”。
- 测试覆盖：没有图表格式化测试；无前端自动化测试。**未覆盖**。

### F08-04｜P3｜KPI 卡整卡点击不可键盘操作，且 key 用 label 可能冲突

- 文件:行号：`frontend/src/shared/components/KpiStrip.tsx:53-58`、`50`、`54`

- 建议：有 `onClick` 时改用 `<button type="button">` 或补 `role="button"`/`tabIndex={0}`/`onKeyDown`（Enter/Space）；key 用稳定 id 或索引，不要用展示文本。
- 测试覆盖：无组件测试/可访问性测试。**未覆盖**。

## 三、补充维度检查

### 负数、0、超大值、小数位超限

- F08 页面本身没有金额输入框，唯一的写操作是“完成任务”，不涉及金额；金额来自 dashboard/team/trend 接口。
- `money` 对 `undefined` 兜底为 0，把“请求失败”和“真实 0”混在一起（F08-01）；负数会显示 `¥-123`，没有额外处理。
- `asMoney`/`compactMoney` 对超大值没有上限提示，`1e16` 级别会因 JS number 丢分位（F08-02/F08-03）。
- `DonutLegend` 对 `total === 0` 有保护，不会除零；没有对负数扇区做校验（当前数据源不应出现负数）。

### 事务边界

- `WorkbenchPage` 除 `completeTask` 外全是查询，不存在“订单建了但明细没建”的前端事务问题。
- `completeTask` 调后端 `POST /tasks/{id}/complete`；后端 `task/router.py:690-724` 先 `_visible_task(..., for_update=True)`，再 `_guard_task_field` 做乐观锁，已完成/已取消会拒绝，未发现重复完成造成二次写入。
- 前端 `completingId` 防连点，失败后 `finally` 重取任务和 summary；没有本地乐观改成“已完成”。

### 异常是否被吞掉 / 错误信息泄露 / 日志敏感信息

- F08-01 是“查询异常被空态吞掉”的主要问题；`refreshWorkbench` 只给 Toast，不落到区块。
- `completeTask` 的 `catch` 直接 `Toast.error((error as Error).message || ...)`（628-629 行）；后端返回的是 AppError 文案，当前未见 SQL/堆栈，但和其他页面一样没有按状态码分类，未单独升级。
- 前端没有 `console.log`/`logger` 输出金额或 token；本块未发现日志敏感信息。

### 关键钱操作审计

- F08 没有收款、改价、作废等钱操作；`completeTask` 后端写 `write_audit(action="complete", business_type="task")`，不涉及金额。
- 工作台只读展示，不产生审计缺口。

### 对照 `backend/tests`

- `test_task_dashboard_drilldown.py:19` 覆盖 dashboard active tasks 的数据范围，不覆盖工作台查询失败/金额精度。
- `test_analytics_issue_fixes.py` 覆盖审批摘要脱敏，不覆盖 dashboard/team/trend 金额。
- 前端没有测试目录/用例；F08 四条发现均无前端自动化覆盖。
- 以上只是“用例是否覆盖触发条件”的静态对照，未运行测试。

## 五、结论

F08 没有发现 P0/P1。工作台的主要风险不是“算错钱”，而是“接口失败被伪装成零/空”，以及“概览金额契约没有 exact、后端 float 汇总”。图表层是展示取整问题，KPI 卡是可访问性问题。四条发现都已在台账登记，建议先修 F08-01 和 F08-02；F08-03/F08-04 可随后处理。
