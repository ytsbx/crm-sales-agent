正面确认的关键点：

- `sample/router.py` 的所有写入口先 `svc.get_visible_or_404(for_update=True)`，把软删、修订版冻结、数据范围、钉钉可编辑性收在同一个门里；明细 `_get_item_or_404` 同时校验 `sample_id` 与 `item_id`，能挡住“拿自己单子的 id 改别人明细”。
- `task/router.py` 的 `_visible_task` 不只判存在，确实调 `ensure_in_scope`；`for_update=True` 使用 `populate_existing=True`，并在 `_guard_task_field` 里把客户端版本直接放进 UPDATE 的 WHERE，不是事后比较；完成/取消/改期/改派/转交共用同一份终态守卫。
- `task/refs.normalize_task_refs` 的“存在 → 数据范围 → 同一客户”三关是统一的，普通建任务与历史跟进补建共用一份；跳过说明只写类别/编号/原因，不写受限对象名称。
- `task/locking.py` 按客户 id 排序取锁，`task/router.py` 在批量交接/批量完成前先锁客户再锁任务，锁序方向一致。
- `timeline/router.py` 对客户/商机/线索/报价/订单都补了 `ensure_in_scope`；`timeline/service.py` 把任务/跟进先按权限与 owner 范围过滤再 `LIMIT`，并只按来源模块权限决定是否返回来源对象。
- `settings/numbering.py` 用 `number_sequences` 行锁 + 唯一键防并发重号，计数器单调不回收；`on conflict do nothing` 处理首次并发插入；`generate_for` 用“库里已有最大号”播种并探测已占用号。

主要风险：**打样单负责人可被指到数据范围外、打样本地审批可自批、已批准打样单还能改打样费/工时而不重审**；其次是任务负责人跨范围改派、批量交接通知不投递、修订版漏字段；其余是幂等、审计、边界值和宽泛吞异常。

### B22-01 P1 打样单负责人/制作负责人可被指到数据范围外的 active 用户

**位置**
- `backend/app/modules/sample/router.py:329-335`（创建时 `owner_id` 取值 + `_assert_active_owner`）

- `backend/app/modules/sample/service.py:222-228、285-324`（列表/单条可见性只按 `SampleRequest.owner_id` 的 `scoped_owner_ids`）

**触发条件**：一个有 `sample:manage`、但 `data_scope` 不是 `all` 的用户，在 `POST /samples` 或 `PATCH /samples/{id}` 里把 `owner_id`/`production_owner_id` 填成自己部门/范围外的 active 用户 id。

**后果**：`owner_id` 一旦改成范围外用户，打样单立刻归到该用户名下。该用户即使看不到对应客户/商机，也能通过打样列表/详情看到这张单上的客户名称、联系人、商机、打样费用/明细；原负责人则可能因为“已不归我”而看不到。`production_owner_id` 虽不决定打样单的可见 owner，但也会被挂到一个范围外账号，详情/导出/通知会把单子信息带给该账号。数据范围被一次正常的“指派”动作绕过，符合“改 ID 看到别人的数据”的越权形态。

**证据代码**
```python
async def _assert_active_owner(session, owner_id, field):
    if owner_id is None:
        raise AppError(ErrorCode.REQUIRED_FIELD_MISSING, f"{field}不能为空", 422)
    target = await session.get(User, owner_id)
    if target is None:
        raise AppError(ErrorCode.NOT_FOUND, f"{field} id={owner_id} 不存在", 404)
    if target.status != "active":
        raise AppError(ErrorCode.PARAM_ERROR, f"{field}「{target.name}」已停用", 422)
    # 没有 scoped_owner_ids / ensure_in_scope
```
```python
owner_id = payload.owner_id or (opportunity.owner_id if opportunity else None) or user.id
await _assert_active_owner(session, owner_id, "负责人")
```

**建议**：新增 `_assert_owner_in_scope`，在 `_assert_active_owner` 之后用 `scoped_owner_ids` 校验目标（管理员/`all` 放行）；`production_owner_id` 若业务允许跨部门，至少要在响应/审计里标明“跨范围指派”，并限制接收人只能看到生产所需字段，不能看到客户联系方式与价格。

**测试覆盖**：未覆盖。`test_sample_revision_privacy.py` 只测修订版子单可见性；`test_sample_delete_policy.py`、`test_sample_application_form.py` 都没有“把 owner 指到范围外”的用例。

### B22-02 P1 打样本地审批无申请人/审批人分离，任何 `sample:manage` 可自批

**位置**
- `backend/app/modules/sample/router.py:305-400`（创建入口，同样只要 `sample:manage`）
- `backend/app/modules/sample/router.py:600-642`（审批入口，只 `require_permission("sample:manage")`）

**触发条件**：一个同时有 `sample:manage`（能建单）的用户创建打样单，随后自己调到 `POST /samples/{id}/approve`，`approved=true`。

**后果**：申请人自己批准自己，主管审批这一档被绕开；之后寄样、登记制作、客户确认都可以继续走。若 `sample_fee` 等费用在审批后被改（B22-03），等于“自己定价、自己批、自己改”，审批链失去独立复核意义。项目固定口径是“管理员可审批自己提交的 CRM 内部审批，非管理员仍按原规则”，这里没有区分管理员与非管理员。

**证据代码**
```python
async def approve_sample(...):
    user: CurrentUser = Depends(require_permission("sample:manage")),
    sample = await svc.get_visible_or_404(session, user, sample_id, for_update=True)
    from app.modules.sample.dingtalk import ensure_local_review
    ensure_local_review(sample)   # 只挡“外部审批流程”，不挡本人
    target = "approved" if payload.approved else "rejected"
    svc.ensure_transition(sample.status, target)
```

**建议**：本地审批增加“申请人不得自批”规则：`sample.created_by == user.id` 且非 `admin` 时 403；或拆出 `sample:approve` 权限，建单与审批不再共用一把钥匙。管理员自批按项目口径放行，但审计要单独记 `self_approved=true`。

**测试覆盖**：未覆盖。`test_oa_sample_inquiry_flow.py` 只测外部 OA 流程；没有“创建人自己审批本地单”的用例。

**后果（若业务允许无客户联系人）**：联系人姓名/职务/审计内容对全体 `customer:view` 可见；若这类联系人本不应存在，则是脏数据放大。是否构成越权取决于“无客户联系人”的业务口径，先列待确认，不当结论。

**建议**：B13/B23 确认联系人是否允许无客户；若允许，给它一个明确的“公共联系人”范围/权限；若不允许，路由对 `customer_id is None` 直接 404 或要求 `customer:contact_full`。

**测试覆盖**：未覆盖。`test_timeline_visibility.py` 的联系人都有 `customer_id=1`；没有孤立联系人用例。
