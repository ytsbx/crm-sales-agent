### B14-01 合并/批量转移/公海指派：路由先判可见，服务锁内不复核数据范围

- **严重度：P1**
- **文件:行号：**
  - `backend/app/modules/customer/tags_router.py:210-211`（合并 source/target 的 `get_visible_customer`）、`386-397`（批量转移逐客户 `assert_customer_visible` 后调 `transfer_customer`）；
  - `backend/app/modules/public_pool/router.py:148-157`（公海指派 `get_visible_customer` + `before_owner` + `transfer_customer`）；
  - 服务侧：`backend/app/modules/customer/service.py:715-736` 只锁客户行，不再 `assert_customer_visible`。
- **触发条件：** A 用户先用当前数据范围读到客户（或合并的 source/target），随后在进入 `merge_customers` / `transfer_customer` 行锁前，B 用户把该客户转移给范围外的人（或放入/移出公海），A 的请求继续执行。
- **后果：** A 可以合并/转移一个在锁定时已不属于自己范围的客户；批量转移会把范围外客户改给目标负责人，公海指派同理。`public_pool` 的 `before_owner` 在锁外捕获，若并发已改主，审计 `before` 与 `CustomerOwnerHistory` 的实际旧值不一致。这是并发窗口下的越权写入，不是普通读泄露。
- **证据代码：**

```python
# tags_router.py（合并）
source = await svc.get_visible_customer(session, user, payload.source_customer_id)
target = await svc.get_visible_customer(session, user, payload.target_customer_id)
...
result = await tag_svc.merge_customers(session, source=source, target=target, ...)
```

```python
# tags_router.py（批量转移）
customer = await session.get(Customer, customer_id)
...
await svc.assert_customer_visible(session, user, customer)
...
documents = await svc.transfer_customer(session, user, customer, payload.owner_id, ...)
```

```python
# public_pool/router.py
customer = await customer_service.get_visible_customer(session, user, customer_id)
...
before_owner = customer.owner_id
await customer_service.transfer_customer(session, user, customer, payload.owner_id, ...)
```

```python
# customer/service.py transfer_customer 锁内

    select(Customer).where(Customer.id == customer.id)
    .with_for_update().execution_options(populate_existing=True)
)).scalars().first()
if locked is None:
    raise AppError(ErrorCode.NOT_FOUND, "客户不存在", 404)
# 只按 only_from_owner_id 复核，未调用 assert_customer_visible
```

`merge_customers` 同样只检查 `deleted_at`，不复查 source/target 的 owner/数据范围。

- **建议：** 在服务层拿到行锁后、任何写入前调用 `assert_customer_visible(session, user, locked)`（`merge_customers` 需要同时复核 source/target）；或者各路由改为 `get_visible_customer(..., for_update=True)` 后再调用服务。`public_pool` 的 `before_owner` 应在锁内重读后取，不要用锁外对象值。若“已经提交的转移”不允许被后来者覆盖，还应在锁内比较入口传入的 owner 快照，变化则 409。
- **测试覆盖：** `test_customer_duplicate_scope.py`/`test_pool_protection_filter.py` 只覆盖静态数据范围和履约保护，没有并发转手后仍能合并/批量转移的用例。**未覆盖并发时序。**

### B14-02 合并价格权限预检查在锁外，锁内新增价格冲突可绕过 `price:manage`

- **严重度：P1**
- **文件:行号：** `backend/app/modules/customer/tags_router.py:221-235`；`backend/app/modules/customer/tags.py:660-671`（锁内 `_detect_conflicts`）
- **触发条件：** 用户只有 `customer:update`、没有 `price:manage`；先请求合并（此时 `price_conflict_exists` 为假，路由不拦），在 `merge_customers` 获得客户行锁前，另一请求给 source/target 新增一条重叠且价格不同的专属价；攻击者在同一个合并请求里预先带上 `resolutions={"customer_price":"keep_target"}`。
- **后果：** 路由的 `price:manage` 检查只看预检查时点，服务锁内重新 `_detect_conflicts` 已经出现 `customer_price` 冲突，但服务没有 actor/权限参数，也不复查价格权限；它会按攻击者给的 resolution 归档另一边的生效价。结果是无价格权限的人完成了一次价格裁决，且合并不可逆。
- **证据代码：**

```python
# tags_router.py
if "admin" not in user.roles and not user.has("price:manage"):
    if await tag_svc.price_conflict_exists(session, source=source, target=target):
        raise AppError(ErrorCode.FORBIDDEN, "...需要价格维护权限...", 403)

result = await tag_svc.merge_customers(
    session, source=source, target=target, operator_id=user.id, ...
)
```

```python
# tags.py merge_customers 锁内
conflicts = await _detect_conflicts(session, source=source, target=target)
...
conflicts_applied = {row["key"]: given[row["key"]] for row in conflicts}
```

`merge_customers` 没有 `user`/`can_manage_price` 参数；`customer_price` 分支只校验 `keep_source/keep_target`，不校验调用者权限。

- **建议：** 把价格权限判断移进 `merge_customers`，在锁内 `_detect_conflicts` 之后、任何归档前执行；或者服务返回“存在价格冲突”并要求带 `price_approval_token`/二次授权，路由不能只做一次锁外预检查。更稳妥的口径是：任何 `customer_price` 冲突的合并都要求 `price:manage`，不接受“预检查时没有冲突”的短路径。
- **测试覆盖：** 未找到合并价格权限竞态用例；`test_customer_duplicate_scope.py` 只覆盖撞单可见性。**未覆盖。**

### B14-04 `WeComSyncJob.event_fingerprint` 模型没有唯一索引，只有迁移有

```python
    # 企微回调的密文指纹：独立列并加唯一索引，避免并发回调绕过 JSON 查询去重。
    event_fingerprint: Mapped[str | None] = mapped_column(String(64), nullable=True)
```

迁移：

```python
op.execute(
    "CREATE UNIQUE INDEX IF NOT EXISTS uq_wecom_sync_event_fingerprint "
    "ON wecom_sync_jobs (event_fingerprint) WHERE event_fingerprint IS NOT NULL"
)
```

- **建议：** 在模型 `__table_args__` 声明部分唯一索引（`postgresql_where=text("event_fingerprint IS NOT NULL")`），与迁移一致；CI 加一条“模型 metadata 与迁移唯一索引一致”的检查。若生产只走 Alembic，至少在模型注释里标注“仅迁移保证”，不要让读者以为 `create_all` 也安全。
- **测试覆盖：** `test_wecom_contact_events.py` 测回调事件/job 创建，但没有断言唯一索引存在，也没有并发相同指纹用例；`test_wecom_response_format.py` 不建该表。**部分覆盖回调路径，唯一索引未覆盖。**

### B14-07 access_token 进程内缓存无锁，密钥轮换后旧 token 仍缓存

- **严重度：P3**
- **文件:行号：** `backend/app/modules/wecom/client.py:61、147-159`
- **触发条件：** 多个协程同时首次调用 `access_token`；或运行中更换 `WECOM_*_SECRET` 后不重启进程。
- **后果：** 并发首次取 token 会各自请求 `gettoken`，多打一次企微接口（通常返回同一 token，不一定致命）；缓存键只含 corp id + ext/contact，不含 secret 版本/指纹，密钥轮换后旧 token 仍被返回直到过期（最长约 2 小时）。如果企微侧旧 secret 被禁用，请求会用旧 token 失败，排查时容易误判。
- **证据代码：**

```python
_token_cache: dict[str, tuple[str, float]] = {}
...
cache_key = f"{settings.wecom_corp_id}:{'ext' if external else 'contact'}"
cached = _token_cache.get(cache_key)
if cached and cached[1] > time.time():
    return cached[0]
...
_token_cache[cache_key] = (token, time.time() + _TOKEN_TTL)
```

- **建议：** 用 `asyncio.Lock` per cache key 做单飞；缓存键加入 secret 的短哈希（不要存 secret 本身）或配置版本号，密钥变更后强制重取。至少加“token 失效/密钥轮换”运维说明。
- **测试覆盖：** `test_wecom_response_format.py` 测 token 响应格式，不测并发或密钥轮换。**部分覆盖格式，并发/轮换未覆盖。**
