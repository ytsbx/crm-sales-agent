### B20-01 P2 商机漏斗/看板/360 概览金额仍以 float 出口

**位置**
- `backend/app/modules/opportunity/router.py:365`（漏斗 `float(amount or 0)`）
- `backend/app/modules/opportunity/router.py:423`（看板列头 `float(amount or 0)`）
- `backend/app/modules/opportunity/router.py:700`（360 概览 `version_amounts[...] = float(amount or 0)`）
- `backend/app/modules/opportunity/router.py:715`（360 概览 `item_quantity` 用 `float(sum(...))`）

**触发条件**：商机 `expected_amount` 有分位/多位小数，或报价版本 `total_amount` 有分位；前端用漏斗/看板/概览数字做汇总、导出、与报价/订单对账。

**后果**：`expected_amount` 是钱，`QuoteVersion.total_amount` 是报价总额，`item_quantity` 是数量；全部转 float 后，前端二次汇总会与 Decimal/HALF_UP 结果出现分/厘差。概览里的 `current_version_amount` 直接拿去和订单/回款比，可能差一分。与 B17-02/B18-02/B19-03 同类，但这是商机聚合入口，之前没覆盖。

**证据代码**
```python
# 365
stats = {int(sid): (int(count), float(amount or 0)) for sid, count, amount in rows}
# 423
stats = {int(sid): (int(count), float(amount or 0)) for sid, count, amount in rows}
# 700
version_amounts[int(version_id)] = float(amount or 0)
# 715
"item_quantity": float(sum(item["quantity"] for item in items)),
```

**建议**：聚合 SQL 继续用 Decimal，响应增加 `amount_exact`/`item_quantity_exact`（字符串或 Decimal 序列化），原有 float 字段只做展示；前端汇总、导出、对账一律用 exact。不要把 `expected_amount` 的 float 当作可复算金额。

**测试覆盖**：未覆盖。`test_external_review_confirmed.py:150` 只构造 `expected_amount=Decimal("100.25")`，没有调用漏斗/看板/概览并断言精度；没有 `funnel`/`board-stats` 用例。

- 对照 `backend/app/modules/opportunity/router.py:1090-1110`（失单入口明确查 `live_orders` 并阻断）

**触发条件**：商机已成交并生成订单（未取消），或商机下有有效报价；有 `opportunity:manage` 的人调用 `DELETE /opportunities/{id}`。

```python
opportunity = await svc.get_visible_opportunity(session, user, opportunity_id, for_update=True)

await session.commit()
```
`lose_opportunity` 则先查：

```python
live_orders = (... SalesOrder.opportunity_id == opportunity_id,

if live_orders:
```

**测试覆盖**：未覆盖。`test_opportunity_links.py` 只测克隆/复制/停用产品，没有“有订单的商机删除”用例；没有删除后订单仍可读/关系断开的断言。

### B20-03 P2 商机负责人可被清空，清空后普通范围用户自己也会失去访问

**位置**
- `backend/app/modules/opportunity/schema.py:107-111`（`OpportunityAssign.owner_id: int | None`）
- `backend/app/modules/opportunity/router.py:1448-1452`（`assert_owner_active(None)` 直接通过，`opportunity.owner_id = None`）
- `backend/app/core/data_scope.py:155-169`（非 all 范围遇到 `owner_id is None` 默认拒绝）

**触发条件**：有 `opportunity:manage` 的人调用 `POST /opportunities/{id}/assign`，传 `owner_id: null`（或只传 remark）。

**后果**：商机变成无负责人。对 `data_scope != all` 的用户（包括刚操作的人自己），之后 `get_visible_opportunity` 会以“没有负责人，无法判定可见范围”403；列表按 `owner_id.in_(scope)` 也永远不包含它。等于把一个商机从普通业务员手里“半软删”，且没有专门的“放入无主池”入口/提示。除非业务明确只允许管理员这样收回，否则这是数据可见性/流程错误。

**证据代码**
```python
# router.py:1448-1452
opportunity = await svc.get_visible_opportunity(session, user, opportunity_id, for_update=True)
await svc.assert_owner_active(session, payload.owner_id)  # None 直接 return None
before_owner = opportunity.owner_id
opportunity.owner_id = payload.owner_id
```
```python
# data_scope.py:155-169
if owner_id is None:
    if allow_unowned:
        return
    raise AppError(ErrorCode.DATA_SCOPE_DENIED,
        f"该{label}没有负责人，无法判定可见范围，已拒绝访问；请先补齐归属", 403)
```

**建议**：`OpportunityAssign.owner_id` 改成必填 `int = Field(ge=1)`；如果确实要“退回无主”，新增专门动作/权限，并在响应里明确“此后普通范围用户不可见”，不要和“改派给某人”共用入口。`assert_owner_active` 对 None 的放行只应服务于创建时的“继承客户负责人”，不应服务改派。

**测试覆盖**：未覆盖。没有 `assign owner_id=null` 后当前用户/同范围用户 403 的用例；`test_opportunity_links.py` 不测改派。

### B20-04 P2 跨客户复制商机需求，目标价/规格会跟着来源客户进目标商机

**位置**
- `backend/app/modules/opportunity/router.py:1386-1397`（只校验两个商机各自可见，没有 `customer_id` 相等校验）
- `backend/app/modules/opportunity/service.py:685-735`（`copy_items_from` 只按 `opportunity_id` 取源/目标明细，不校验客户）
- 对照 `backend/app/modules/opportunity/router.py:1385` 注释“同客户重复采购时最常用”

**触发条件**：两个商机分属不同客户，但当前用户的数据范围同时能看到；调用 `POST /opportunities/{target}/items/copy-from/{source}`，`on_conflict="add"` 或源 SKU 在目标不存在。

**后果**：来源客户的 `quantity/target_price/currency/specification/remark` 被原样写进目标客户商机。目标价是客户的价格预期，跨客户复制会把 A 客户的底价/规格带进 B 客户，既污染 B 的报价基础，也可能造成价格信息在内部错配。当前没有客户相等校验，注释和接口语义却是“同客户重复采购”。属于数据范围/业务归属错误。

**证据代码**
```python
# router.py:1386-1390
await svc.get_visible_opportunity(session, user, opportunity_id)
await svc.get_visible_opportunity(session, user, source_opportunity_id)
if opportunity_id == source_opportunity_id:
    raise AppError(..., "不能从自己复制需求明细", 422)
# service.py:700-714
source_rows = (... OpportunityItem.opportunity_id == source_opportunity_id ...)
...
session.add(OpportunityItem(opportunity_id=target_opportunity_id, sku_id=row.sku_id,
    quantity=row.quantity, target_price=row.target_price, currency=row.currency, ...))
```

**建议**：入口要求 `target.customer_id == source.customer_id`，不同客户 422 并提示“只能从同一客户的商机复制需求”；若业务确实允许跨客户复制模板，必须显式参数并清空/重填 `target_price`（不能把来源客户目标价直接带过去）。

**测试覆盖**：未覆盖。`test_opportunity_links.py:73-107` 用 `opportunity_id=1/2` 但没有建客户关系，也没有跨客户断言；只覆盖空选择、`replace` 数量、外币 `add` 被拒。

### B20-05 P2 SKU CSV 导入绕过统一数字边界，超大/超小数位到 DB 才失败或静默舍入

**位置**
- `backend/app/modules/product/io.py:91-109`（`_decimal` 只判有限数，不判 `max_digits/decimal_places`）
- `backend/app/modules/product/io.py:112-129`（`_int` 不判 `BigInteger` 上限）
- `backend/app/modules/product/io.py:191-210`（`sku_fields_from_row` 直接把 Decimal/int 放进返回 dict）
- `backend/app/modules/product/field_rules.py:50-58`（`Numeric(12,3/4)`、`BigInteger` 的统一规则）

## 六、结论

B20 没有 P0/P1：商机权限、成交幂等、整批替换前的校验、主数据“外部值不自动写回”这些核心机制是扎实的。需要优先处理的是 **B20-02（删除商机不查下游）**、**B20-03（负责人清空后普通用户失去访问）**、**B20-04（跨客户复制需求）** 三条数据/权限流程问题，以及 **B20-01（商机金额聚合 float）**、**B20-05（SKU 导入绕过统一数字边界）**、**B20-06（主数据文本无长度）** 三条精度/边界问题；其余为审计、并发、配置和悬空引用。
