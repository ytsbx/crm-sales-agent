### 1. `backend/app/modules/order/service.py`（1,229 行，已读全文）

我检查了什么：

- 报价转订单：是否锁报价/版本、是否校验当前版本、是否只允许已接受版本、是否按版本冻结总额与组成、是否检查“接受后金额被改”、转单幂等与并发兜底。
- 手工建单：是否由明细算总额、数量是否按库精度归一、逐行/整单金额是否越界、客户/负责人/商机范围、币种闸门、重复提交。
- 状态流转：合法状态集合、是否允许跨状态回退、`shipped`/`delivered`/`completed` 是否有履约依据、取消是否只能走专用流程。
- 发货批次：排批次/实发/取消的锁顺序、累计实发是否超订购、整批为 0、未来发货日、部分明细提交的默认值、批次号取号。
- 已收金额：只统计 `confirmed`，取消后是否归零展示。
- 外部映射与上下文：`erp_order_id`/`ExternalMapping` 幂等、客户/负责人/回款汇总。

结果如何：

- 转单先锁商机 → 报价 → 版本，`ensure_current_version` 拦旧版本，`version.approval_status == approved`、`quote.status == accepted`、`accepted_at/sent_at/declined_at` 都有校验；`quote_version_id` 唯一索引 + `IntegrityError` 兜底，一版一单的幂等成立。
- 但总额直接取 `version.total_amount`，**没有“客户接受时的金额快照”可比对**；B02-01 允许接受后改运费，这里会把改后的金额原样写进正式订单（B04-01，P0）。
- 手工建单逐行 `line_amount`、逐行与整单都做 `_assert_money_in_range`，数量用 `normalized_quantity` 按 `Numeric(16,3)` 先归一，金额与落库数量一致；这部分没有发现金额算错。
- 手工建单**没有请求键/幂等占位**，双击或重试会生成两张订单号不同的正式单（B04-02）。
- `change_status` 只校验“状态名在白名单里”，没有流转矩阵；`shipped`/`delivered` 不要求任何发货批次，`pending → delivered`、`in_production → pending`、`shipped → pending` 都放行；只有 `completed` 做了“未发量必须为 0”的闸门（B04-03）。
- 发货：排批次、实发、取消都按“先订单、后批次”锁；实发先整批算完再落数量，累计超订购、负数、整批为 0、未来发货日都拦住了；批次号取全部批次最大值，避免复号。
- `ship_shipment_batch` 的 `items` 只给部分明细时，未给的行默认按**计划量全发**（B04-07）。
- 取消订单：已确认回款、已签合同直接拒绝；待确认回款驳回、未回清应收取消、未发货批次取消，财务副作用比普通状态接口完整。
- `record_external_order_id` 直接插 `ExternalMapping`，没有唯一键/幂等（B04-15，B06 复核后已关闭：模型与迁移已有唯一约束；该函数现无调用点）。

## 二、发现清单

### B04-01｜P0｜转单金额直接取“当前版本总额”，与客户接受时的金额没有比对

- **位置**：`order/service.py:295-302`、`order/router.py:270-276`；`quote/model.py:80-85`、`157-160`
- **触发条件**：报价已被客户接受后，通过 B02-01 的“锁版后仍可改运费/其他费用”把 `version.total_amount` 改掉，再转订单；或用户在 `confirm=false` 的预览里看到金额 A，随后另一人改费用，`confirm=true` 时实际按金额 B 建单。
- **后果**：正式订单总额、货款/运费/其他费用快照与客户接受的那一版不一致；订单是履约与收款依据，后续应收也按这个错误总额生成。系统里没有“客户接受时金额”的快照，事后无法证明客户同意的是哪个数。
- **证据代码**：
  ```python
  # service.py:295-302
  total_amount=version.total_amount,
  goods_amount=version.subtotal_amount,
  logistics_amount=version.logistics_amount,
  other_charge_amount=version.other_charge_amount,
  discount_amount=version.discount_amount,
  ```
  ```python
  # quote/model.py: 只有时间，没有接受金额快照
  accepted_at: Mapped[datetime | None] = mapped_column(DateTime(timezone=True), nullable=True)
  ```
  `convert_to_order` 的确认文案读 `version.total_amount`，实际建单再由 service 重读，二者之间没有校验。
- **建议**：客户接受时把 `total_amount` 与四项组成写入 `accepted_*` 快照；转单前要求“当前总额 == 接受快照”，不一致必须重新接受/新建版本。若业务确实允许接受后改运费，则每次改动后重新走客户确认并更新快照，不能直接转单。

### B04-02｜P1｜手工建单没有请求键，双击/重试会生成两张正式订单

- **位置**：`order/router.py:99-206`；`order/schema.py:124-140`；`order/service.py:453-560`
- **触发条件**：主管手工建单时双击提交、网关重试、前端超时后重发。`OrderCreate` 没有 `request_key`，也没有 `idempotency.reserve`，每次都会取新 `order_no` 并插入。
- **后果**：同一笔线下签约生成两张订单，业绩/成交额重复计入；如果后续两张都推 ERP，会在外部系统建两张单；两张单各自可以排批次、做发货，履约数量被重复占用。
- **证据代码**：
  ```python
  # schema.py:133
  items: list[OrderItemInput] = Field(min_length=1)   # 没有 request_key
  ```
  ```python
  # router.py:158
  order = await svc.create_order(...)
  # 没有 idempotency.reserve / request_key
  ```
  `create_order` 内只有 `order_no` 唯一，不构成业务幂等。
- **建议**：照发货批次的写法，`OrderCreate` 加可选 `request_key`，路由先 `idempotency.reserve(action="order:create_manual", payload=...)`，重放返回原 `order_id/order_no`；至少要求前端提交幂等键。

### B04-03｜P1｜状态机没有流转矩阵，可在没有任何发货的情况下改成“已发货/已签收”

- **位置**：`order/service.py:573-587`、`588-643`；`order/router.py:860-892`
- **触发条件**：`POST /orders/{id}/status` 传 `status="shipped"` 或 `"delivered"`，订单仍是 `pending`、没有任何发货批次；或从 `in_production` 回退到 `pending`、从 `shipped` 回退到 `pending`。
- **后果**：订单页/看板显示“已发货/已签收”，但实发量为 0；交付准时率、未发量、客户跟进全部基于这个假状态。`completed` 有未发量闸门，但 `shipped`/`delivered` 没有，等于从低一级状态绕过了履约校验。
- **证据代码**：
  ```python
  # service.py:573-587
  if new_status not in ORDER_STATUS_LABEL: ...
  if new_status == "cancelled" and not allow_cancel: ...
  if order.status == new_status: ...
  if order.status == "cancelled": ...
  # 之后直接到 completed 的检查；shipped/delivered 没有任何批次/实发量判断
  ```
  ```python
  # router.py:890-892
  await svc.change_status(session, order, new_status=payload.status, ...)
  ```
- **建议**：建立显式流转表（`pending → in_production → shipped → delivered → completed`，另加有理由的纠错边）；`shipped` 必须至少有一条已发货批次且 `all_shipped` 或明确“部分发货”；`delivered` 必须已 `shipped`；回退必须填理由并留审计。普通状态接口不应允许手工写 `shipped/delivered`，这两个状态应由发货/签收事实推进。

### B04-04｜P2｜转移订单负责人只校验权限，不校验目标负责人的数据范围

- **位置**：`order/router.py:361-383`；对照 `order/router.py:143-144`
- **触发条件**：持有 `order:assign` 的主管把订单 `owner_id` 改成另一个部门/范围外的在职用户。
- **后果**：订单从此对目标负责人的部门可见，而创建/原部门按 `scoped_owner_ids` 看不到；等于用“转移负责人”把单据移出原数据范围。创建订单时对 `owner_id` 有 `ensure_in_scope`，改单时没有，两个入口口径不一致。
- **证据代码**：
  ```python
  owner = await session.get(User, data["owner_id"])
  if owner is None: ...
  if owner.status != "active": ...
  # 没有 ensure_in_scope(session, user, owner_id=owner.id, label="负责人")
  ```
- **建议**：改单时对目标负责人复用 `ensure_in_scope`；若业务确实允许跨部门交接，把“全局 assign”写成明确口径，并在审计里记录跨部门转移原因。

### B04-05｜P2｜已完成订单仍可走交期变更，历史履约基准被改写

- **位置**：`order/schedule.py:191-192`、`257-258`
- **触发条件**：订单 `status == completed`，发起并确认一张交期变更单（只拦了 `cancelled`）。
- **后果**：已完成订单的 `delivery_date`、`delivery_kind`、`transit_days`、未发货批次计划日都会被改；交付准时率、最后一批偏差等历史指标跟着变，等于用今天的计划覆盖已完成事实。`update_order` 明确禁止直接改交期，交期变更却对 completed 放行。
- **证据代码**：
  ```python
  # create_change
  if order.status == "cancelled": raise ...
  # confirm_change
  if order.status == "cancelled": raise ...
  ```
  两处都没有 `completed` 分支。
- **建议**：`completed` 订单禁止交期变更；确需纠错时走“完成状态纠错”并要求理由，或只允许改备注、不改计划日。

### B04-06｜P2｜`order:view` 用户可通过 ERP 刷新改订单状态

> B06 复核（2026-11-21）：`erp/router.py:351-361` 仍只要求 `order:view`；`erp/service.py:718-832` 的 `refresh_status` 在拉取成功后确实调用 `order_service.change_status` 并写 `order_status_history`。只读权限能间接写状态，本条成立。

- **位置**：`order/router.py:209-227`；`erp/service.py:802-817`
- **触发条件**：只有 `order:view` 的用户对已推送 ERP 的订单调用 `POST /orders/{id}/refresh-status`，ERP 返回 `shipped`/`delivered` 等状态。
- **后果**：一个只读权限的账号能触发订单状态写入（`change_status`），且这条路径没有业务审计，只有 IntegrationLog；结合 B04-03，可在没有批次的情况下把订单改成已发货。
- **证据代码**：
  ```python
  # router.py:212
  user: CurrentUser = Depends(require_permission("order:view"))
  ...
  result = await erp_service.refresh_status(session, order=order, operator_id=user.id)
  ```
  ```python
  # erp/service.py:810
  await order_service.change_status(session, order, new_status=new_status, ...)
  ```
- **建议**：刷新并回写状态要求 `order:manage`；或拆成“只读拉取”和“应用状态”两个动作，后者单独授权并写审计。

### B04-07｜P2｜实发明细只传部分行时，未传的行默认“计划量全发”

- **位置**：`order/service.py:1066-1071`；`order/schema.py:193-203`
- **触发条件**：`ShipmentBatchShip.items` 只包含本批部分明细（例如只想把 A 行改成实发 1），其余行不传。
- **后果**：未传的 B/C 行按 `planned_qty` 全发，系统记录“整批按计划发完”；前端以为只改了 A，实际把 B/C 也登记成已发货，库存/未发量/订单完成判断全部受影响。
- **证据代码**：
  ```python
  qty = (
      ship_inputs.get(row.order_item_id, _d(row.planned_qty))
      if ship_inputs is not None
      else _d(row.planned_qty)
  )
  ```
- **建议**：当 `items` 非空时，要求覆盖本批全部 `order_item_id`（缺一个就 422），或增加显式 `mode="partial"` 并把未传行视为 0；不要把“没传”解释成“全发”。

### B04-08｜P2｜订单原本没有交期时，交期变更不会平移已有批次计划日

- **位置**：`order/schedule.py:140`、`166-172`、`191-195`
- **触发条件**：手工订单/历史订单 `delivery_date` 为空，但已有批次填了 `planned_date`；发起交期变更设置新交期。
- **后果**：`old_ship=None` → `delta=None`，`preview` 对已有批次的计划日直接跳过，`confirm` 也只改订单交期和节点，批次计划日保持原值。订单显示新交期，批次还按旧日期排，逾期提醒和“最后一批 vs 交期”都会错。
- **证据代码**：
  ```python
  delta = (new_ship - old_ship).days if old_ship else None
  ...
  for batch in await _batches(...):
      if batch.planned_date is None or delta is None:
          continue
  ```
  `create_change` 只要求 `before != after`，不会因此拒绝。
- **建议**：旧交期为空时，不能按 `delta` 平移；要么在预览里明确列出“批次计划日无法自动平移，请手工确认”，要么以新交期 + 批次相对偏移重算；至少不要静默跳过。

### B04-09｜P3｜已完成订单无法通过取消接口取消，接口也没有理由入参

- **位置**：`order/router.py:911-1023`；`order/service.py:637-643`
- **触发条件**：订单 `completed`、无已确认回款/已签合同，调用 `POST /orders/{id}/cancel`。
- **后果**：`cancel_order` 调 `change_status` 时没传 `remark`，`change_status` 对“completed → 非 completed”要求理由，直接 422；取消接口没有 reason 字段，用户无法完成这个纠错动作。
- **证据代码**：
  ```python
  await svc.change_status(session, order, new_status="cancelled", operator_id=user.id, allow_cancel=True)
  ```
  没有 `remark`。
- **建议**：取消接口增加可选 `reason` 并透传给 `change_status`；或明确“completed 是终态，不允许取消”，返回专门文案与替代路径。

### B04-10｜P3｜取消订单不撤动态批次跟单节点

- **位置**：`order/router.py:1024-1034`；`order/service.py:1138-1164`；`order/milestones.py:463-485`
- **触发条件**：订单有第 2 批及以上的动态节点（`shipment_batch_N`），取消订单时这些批次还是 `planned`。
- **后果**：批次被置 `cancelled`，但 `drop_batch_node` 没被调用，跟单页仍显示“第 N 批发货”待办/逾期节点；虽然逾期提醒按订单状态过滤不会推送，页面与数据仍残留一个不存在的发货计划。
- **证据代码**：取消订单只做 `batch.status = "cancelled"`，而 `cancel_shipment_batch` 才会调用 `milestones_svc.drop_batch_node`。
- **建议**：取消订单时对每个被取消的批次调用 `drop_batch_node`（已发货批次保留）；或统一走 `cancel_shipment_batch` 的同一段逻辑。

### B04-11｜P3｜手工建单明细没有条数上限

- **位置**：`order/schema.py:133`
- **触发条件**：`POST /orders` 的 `items` 传任意长度数组。
- **后果**：每行都要查 SKU 可用性、算金额、插库；没有上限时单请求可放大数据库负载，前端也可能误传几千行。
- **证据代码**：`items: list[OrderItemInput] = Field(min_length=1)`，无 `max_length`。
- **建议**：加 `max_length`（如 200）并 422；与 `OrderDraftCreate.items` 的 200 上限保持一致。

### B04-12｜P3｜手工订单没有应收计划，“收款”节点永远不会完成

- **位置**：`order/service.py:370-382`；`order/milestones.py:297-342`
- **触发条件**：手工建单（不生成应收计划），之后登记并确认回款，再打开跟单页。
- **后果**：`sync_payment_milestones` 的 `settled` 要求 `planned > 0` 且逐期结清；手工单 `plan_rows` 为空，`planned=0`，即使有确认回款，“收款”节点也永远不完成。
- **证据代码**：
  ```python
  settled = bool(count) and planned > 0 and not unsettled
  ```
  ```python
  # create_order 手工路径没有 session.add(ReceivablePlan(...))
  ```
- **建议**：手工单要么也生成一条“全款”应收，要么在里程碑里对“无应收但有确认回款”的订单用实际到账额判定；不要留一个永远不完成的事实节点。

### B04-13｜P3｜转单成功后重试返回 409，不是幂等回放

- **位置**：`order/service.py:221-231`；`order/router.py:285-304`
- **触发条件**：转单请求已提交成功，但响应丢失/前端超时，用户再点一次。
- **后果**：第二次请求命中“该报价版本已经转过订单”409；用户看到失败，但订单其实已生成。虽然不会重复建单，失败提示与事实相反。
- **证据代码**：`existing is not None` 直接 `raise AppError(DUPLICATE_CONVERT, ... 409)`，没有返回 `existing.order_id/order_no`。
- **建议**：同用户同版本重复转单返回 200 + 原订单信息（幂等回放），只有“不同用户/不同参数”才 409；或前端把 409 文案明确写成“已存在，订单号 xxx”。

### B04-14｜P3（交 B05）｜回款/应收模型缺少两处结构约束

- **位置**：`payment/model.py:32`、`112`
- **触发条件**：并发生成应收、或历史/外部写入把 `payment_records.receivable_plan_id` 指向别的订单的期。
- **后果**：`receivable_plans` 没有 `(order_id, plan_name)` 唯一约束，重复生成会多一条同期应收；`payment_records.receivable_plan_id` 没有外键，回款可以挂到一个不存在的期，汇总时“这笔钱属于哪期”失真。
- **证据代码**：
  ```python
  __table_args__ = (Index("ix_receivable_plans_order_status", "order_id", "status"),)  # 非 unique
  receivable_plan_id: Mapped[int | None] = mapped_column(BigInteger, nullable=True)  # 无 ForeignKey
  ```
- **建议**：B05 核对应收生成/回款归属的服务层校验；若 `receivable_plan_id` 继续保留，加外键/索引或在服务层强制“plan.order_id == payment.order_id”。

### B04-15｜P3（B06 复核后关闭）｜`ExternalMapping` 写入没有幂等/唯一约束

> B06 复核（2026-11-21）：`integration/model.py:72-83` 已声明 `(system_type,business_type,internal_id)` 与 `(system_type,business_type,external_id)` 两条唯一约束，迁移 `backend/alembic/versions/f7b8c9d0e1a2_external_mapping_unique.py` 也已创建并在升级前检查历史重复。因此“同一内部单可多行映射”不成立，本条关闭；剩余风险是 `sales_orders.erp_order_id` 主表仍无唯一约束，已另记 B06-06。

- **位置**：`order/service.py:1167-1178`（该函数目前已无调用点，属死代码）
- **触发条件**：同一订单多次推送 ERP/MES，或重试回调写入映射。
- **后果**：每次 `record_external_order_id` 都新增一行映射，同一个 `(system_type,business_type,internal_id)` 可能对应多条 `external_id`；对账时无法确定哪条是当前映射。
- **证据代码**：`session.add(ExternalMapping(...))`，没有查重、没有唯一键。
- **建议**：B06 核对 `ExternalMapping` 的唯一约束；同一内部单只保留一条当前映射，历史映射另表或用版本字段。

### B04-16｜P3｜转单并发兜底里的 `session.rollback()` 会回滚整个外层事务

- **位置**：`order/service.py:313-323`
- **触发条件**：两个请求并发转同一版本，后到者在 `flush` 撞唯一索引。
- **后果**：`except IntegrityError` 里 `await session.rollback()` 回滚的是调用方的整个事务，不只是这次插入；如果调用方在同一事务里已经写了别的审计/通知/草稿状态，会一起丢。当前路由在这之前没有别的写，影响有限，但作为库函数不应替调用方回滚整个事务。
- **证据代码**：
  ```python
  except IntegrityError:
      await session.rollback()
      raise AppError(ErrorCode.DUPLICATE_CONVERT, ...)
  ```
- **建议**：用 `begin_nested()` SAVEPOINT 包住插入，撞唯一索引只回滚保存点；或把并发兜底放到路由层，由路由统一决定事务边界。

## 三、待确认（不当作结论）

1. **已发货后取消订单是否允许**：`cancel_order` 只拦已确认回款/已签合同，允许有已发货批次时取消；代码注释说“已发货批次是既成事实，保留原状”。是否应要求退货/冲减发货、是否允许“已发货 + 已取消”终态，需业务确认。
2. **手工订单不生成应收是否符合业务**：`create_order` 明确不建应收；如果手工单也要收款/催收，需 B05 确认回款能否脱离应收计划登记，以及报表如何统计。
3. **报价版本 `total_amount` 与四项组成是否恒等**：本块未复算 `goods + logistics + other - discount == total`；若 quote service 在费用编辑后能保证恒等，则只是防御缺口，B02/B05 复核。
4. **`receivable_plans` 状态 `paid` 是否可能在没有 confirmed 回款时出现**：若可能，取消订单保留 `paid` 计划会与“已收 0”矛盾；B05 核对状态写入路径。
