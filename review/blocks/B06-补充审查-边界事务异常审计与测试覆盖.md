## 一、补充项检查结果

### B06-15｜P2｜采集失败把底层异常原文写进 `last_error` 并返回前端，可能泄露 SQL/表列/连接细节

- **位置**：`backend/app/modules/erp/collection.py:1194`（写入）、`:545`（序列化）、`:1525-1575`（状态返回）；`backend/app/modules/erp/router.py:409-420`（`order:view` 可读）
- **触发条件**：采集过程中任何异常（SQLAlchemy `IntegrityError`/`OperationalError`、适配器解析异常、Pydantic 校验异常）走到 `_fail_quietly`；随后有 `order:view` 权限的人打开采集状态页。
- **后果**：`cursor.last_error = _clip(f"{type(error).__name__}: {error}")` 原样保留异常字符串，`serialize_cursor` 把它放进 `cursors[]`，`GET /integrations/erp/collection/status` 直接返回。SQLAlchemy 的错误字符串常带 SQL 语句、表名/列名/约束名；连接类错误还可能带主机/端口。B06-10 已报“状态接口对 `order:view` 返回全公司数据”，本条是**同一接口上的错误信息泄露**，即使数据范围修好，错误原文仍会泄露内部结构。
- **证据代码**：
  ```python
  # collection.py:1194
  cursor.last_error = _clip(f"{type(error).__name__}: {error}")
  # collection.py:545
  "last_error": row.last_error,
  # router.py:409-420
  user = Depends(require_permission("order:view"))
  return ok(await collect_svc.collection_status(session))
  ```
- **建议**：对外只返回稳定的错误码/中文摘要（如“采集失败，请查看服务端日志”），完整异常只写服务端日志并带 `cursor_id/batch_id`；`last_error` 若必须保留，落库前脱敏（去掉 SQL、连接串、约束名）。
- **测试覆盖**：未覆盖。`backend/tests/test_erp_external_sync.py:808-810` 只断言 `last_error` 含“验收”字样，没有断言“不含 SQL/表名/连接串”。

### B06-16｜P2｜显式“映射重放”接口改完全局映射后没有任何审计

- **位置**：`backend/app/modules/erp/router.py:602-627`；实际写库 `backend/app/modules/erp/collection.py:1465-1492`
- **触发条件**：全量数据范围用户调用 `POST /integrations/erp/external-mappings/replay`，一次最多 5000 条 pending/conflict 映射被重新匹配并覆盖 `internal_id/match_status/match_basis`。
- **后果**：该路由只做权限检查、调用服务、`commit`，**没有 `write_audit`**；被改掉的映射没有逐条记录，也没有一条“谁在什么时候重放了多少条、改了多少条”的批次审计。B06-02 已报“人工匹配顺带全局重放、只审计被点的那一条”；本条是**显式重放入口连批次审计都没有**，两者不重复。映射决定外部事实挂到哪张订单/客户/SKU，是后续对账归属的依据，事后无法回答“这条映射为什么从 A 变成 B”。
- **证据代码**：
  ```python
  result = await collect_svc.replay_pending_mappings(...)
  await session.commit()
  return ok(result, ...)
  # 整个函数没有 write_audit
  ```
- **建议**：重放前后各写一条审计：`before` 记录 `checked/matched/still_pending` 与筛选条件（`system_type/shop_id/object_type/limit`），并对每条 `internal_id` 发生变化的 mapping 写 `mapping_id/old_internal_id/new_internal_id/basis`；至少要有批次审计和操作人。
- **测试覆盖**：未覆盖。`backend/tests/test_erp_external_sync.py:582-610` 只验证“未知 SKU → pending → 重放后 matched”，不读 `AuditLog`；没有任何 ERP 重放审计断言。

### B06-17｜P3｜失败落盘自身失败被 `pass` 吞掉，采集游标可能停在 `running` 且服务端无日志

- **位置**：`backend/app/modules/erp/collection.py:1186-1212`
- **触发条件**：采集异常后 `_fail_quietly` 执行 `rollback`/更新游标/写采集日志时数据库再次失败（连接断开、锁超时、磁盘满）。
- **后果**：`except Exception: pass` 只保留原始异常向外抛；本次“失败落盘也失败”没有任何 logger/告警。游标可能仍是 `running`，`lease_expires_at` 没清，采集日志也没写。运维只看到原始采集错误，不知道状态没落盘；在租约到期前，下一次采集可能被 `running` 状态/租约挡住，或者状态页显示“运行中”但实际没有任务。
- **证据代码**：
  ```python
  try:
      await session.rollback()
      ...
      await session.commit()
  except Exception:  # noqa: BLE001 - 见 docstring：不覆盖原始异常
      pass
  ```
- **建议**：保留“不覆盖原始异常”的语义，但至少 `logger.exception("采集失败落盘失败 cursor=%s batch=%s", cursor_id, lease_token)`；返回/状态里标记“状态未落盘”。若数据库不可用，写本地/内存告警或交给调度器重试。
- **测试覆盖**：未覆盖。`backend/tests/test_review_round8_repairs.py:265-280` 只覆盖“坏数字回滚整页、游标 failed、断点保留”的正常落盘路径，没有注入“落盘本身失败”。

### B06-18｜P3｜推单/人工核对的成功状态先由服务 `commit`，路由随后才写审计；审计失败会留下“已推/已核对但无审计”的窗口

- **位置**：`backend/app/modules/erp/service.py:604`（推单成功 commit）、`:702`（人工核对 commit）；`backend/app/modules/erp/router.py:268-277`、`:300-309`、`:335-345`（审计后再次 commit）
- **触发条件**：外部系统已经建单/已经核对成功，服务内 `commit` 成功；随后 `write_audit` 或路由的第二次 `commit` 失败（审计表锁、磁盘、连接中断）。
- **后果**：外部动作已生效、订单 `erp_order_id`/映射已落库，但接口返回 500，审计没有记录。推单重试会走 `already_synced` 并补写审计，通常可恢复；人工核对重试会再插入一条 `status=success` 的 `IntegrationLog`，产生重复成功日志。当前 `after` 也只有 `{"pushed":..., "erp_order_id":...}`，没有本次推送的金额/币种/行数，审计不能独立说明“推了什么金额”。
- **证据代码**：
  ```python
  # service.py:604 / :702
  await session.commit()
  # router.py:268-277
  await write_audit(..., after={"pushed": result["pushed"], "erp_order_id": ...})
  await session.commit()
  ```
- **建议**：把审计放进服务同一次事务（服务只 `flush`，路由统一 `commit`），或在服务 commit 前写审计；`after` 补 `total_amount_exact/currency/item_count`（不要 float）。若保留两段提交，至少在审计失败时记录“已成功但审计失败”的服务端日志并用幂等键去重。
- **测试覆盖**：未覆盖。ERP 测试没有审计断言，也没有“服务 commit 后审计失败”的故障注入。

### B06-P4｜采集金额/数量允许负数与 0，是否需要按对象类型拒绝未定义

- **位置**：`backend/app/modules/erp/collection.py:153-171`、`:303-309`
- **证据**：`_external_decimal` 只校验 `max_digits=18, decimal_places=4`，没有 `ge=0`/`gt=0`；`quantity` 和 `amount` 都允许 `-1`、`0`。`normalize_item` 也不按 `object_type` 区分“订单金额必须为正、退款/红冲可以为负”。
- **需要业务确认**：ERP 的外部订单事实是否允许负数（退货单、红冲单、调整单）？如果允许，应把负号作为业务类型/`kind` 明确落库并在对账里区分；如果不允许，应在采集时逐条拒绝并进异常队列，而不是让负订单参与“本期销售总额”。当前代码两种都没做，故只记待确认，不定级。

## 三、补充项“没发现问题”的结论

- **负数/0/超大值/小数位（入口）**：`CollectRequest.page_size` 1-200、`max_pages` 1-1000；`MappingReplayRequest.limit` 1-5000；`ReconcileRequest.external_id` 1-128；`DiffConfirmRequest` 金额 `ge=0/max_digits=16/decimal_places=2`。除 B06-P4 的采集金额符号外，未发现新的越界入口。
- **事务边界（采集）**：每页“事实 + 映射 + 游标”同一事务提交，失败时 `rollback` 当前页并保留 `page_token`；未发现“事实已写但水位没推进”或“水位推进但事实没写”的确定性缺陷。推单主链路有订单行锁 + 独立会话 `sending` 日志，外部失败会落 `failed/unknown`；B06-18 是审计提交边界，不是金额半成品。
- **异常/日志**：`collect_once` 的 `except Exception` 是“失败必须留断点”的设计，不是吞异常；`_fail_quietly` 自身失败被吞是 B06-17。`service.py` 没有把 SQL/堆栈拼进用户提示；`build_order_payload` 不在日志里打印，`IntegrationLog.request_data` 存完整报文（含客户名/税号/金额），但读取按订单范围过滤，属于业务留痕，不另列。
- **审计（已有）**：人工匹配单条、来源核实、对账 run、差异核定、推单/核对都有审计；缺口是显式重放（B06-16）和推单/核对审计字段/提交边界（B06-18）。B06-02 的“顺带全局重放无逐条审计”仍是 P1，不重复。
