### F14-01（P2）AI 会话详情失败被显示成“这段对话还没有消息”

- 文件:行号：`frontend/src/modules/agent/AgentPage.tsx:77-81、501-516`
- 触发条件：`getAgentSession(sessionId)` 返回 500/403/超时，或打开一个已被删除/无权限的会话。
- 后果：`detailQuery.data` 为空，`messages=[]`、`actions=[]`；页面在 `!detailQuery.isPending` 后显示“这段对话还没有消息”，不显示加载失败。用户会以为会话真的空，可能重新发问；如果原本有待确认的 L2/L3 动作，也看不到确认卡片。
- 证据代码：

```tsx
const detailQuery = useQuery({
  queryKey: ['agent-session', sessionId],
  queryFn: () => getAgentSession(sessionId!),
  enabled: Boolean(sessionId),
})
...
{messages.length === 0 && (!sessionId || !detailQuery.isPending) && (
  <div className="agent-empty">
    <h2>{sessionId ? '这段对话还没有消息' : '开始新对话'}</h2>
```

- 建议：增加 `detailQuery.isError` 分支，显示“会话读取失败，点击重试”，并区分 403/404/500；错误态不要显示“还没有消息”或快捷发送入口。
- 测试覆盖：未覆盖（无前端 AgentPage 错误态测试；后端 `test_agent_action_rejection.py` 不覆盖前端空态）。

### F14-03（P2）AI 流式发送没有请求键，断流重试会重复一轮对话

- 文件:行号：`frontend/src/modules/agent/AgentPage.tsx:206-230`、`frontend/src/shared/api/agent.ts:124-140`
- 触发条件：用户发送后网络中断/浏览器刷新/网关超时，服务端已经写入用户消息并执行了只读工具；用户在客户端重试同一条问题。
- 后果：`streamAgentMessage` 只发送 `{ content }`，没有 `request_key`/消息客户端 id；服务端无法判断这是同一次发送的重试，会再写一条用户消息、再跑一轮工具，产生重复消息、重复动作候选。动作虽仍需人工确认，但用户会看到两套相同的待确认卡片，容易重复确认。
- 证据代码：

```ts
const resp = await fetch(`/api/v1/agent/sessions/${sessionId}/messages/stream`, {
  method: 'POST',
  signal,
  headers: { 'Content-Type': 'application/json', ...(token ? { Authorization: `Bearer ${token}` } : {}) },
  body: JSON.stringify({ content }),
})
```

```tsx
const handleSend = (text: string) => {
  const content = text.trim()
  ...
  void runStream(sessionId, content)
}
```

- 建议：发送时生成 `request_key`（同一条输入在失败重试时复用），后端按 `(session_id, request_key)` 幂等；或在消息接口支持客户端消息 id，重复请求回放同一轮结果。创建会话也应带请求键，避免“响应丢失后重试建出两个空会话”。
- 测试覆盖：未覆盖（`ops/request_key.test.mjs` 只测 UUID 生成，不测 Agent 流式接口幂等）。

### F14-04（P2）统一 API 客户端把后端原始 message 直接交给用户

- 文件:行号：`frontend/src/shared/api/client.ts:147-173`
- 触发条件：后端返回外部系统原始错误（如 `WECOM_PUSH_OFF`、`DINGTALK_PUSH_OFF`、上游 SQL/网关错误），或页面直接 `Toast.error(error.message)`。
- 后果：`readableMessage` 只判空、`null`、`undefined`，其余原样返回；全站 80+ 调用点的 `Toast.error(error.message)` 会把技术开关名、外部平台原文、甚至网关细节直接显示给业务员。项目已有 `humanizeBackendText`，但只在通知/企微/部分打样文案里使用，客户端没有兜底。
- 证据代码：

```ts
function readableMessage(raw: unknown, code: number): string {
  const text = typeof raw === 'string' ? raw.trim() : ''
  if (!text || text === 'null' || text === 'undefined') {
    return code
      ? `系统内部错误（错误码 ${code}），请稍后重试或联系管理员`
      : '网络异常，请稍后重试'
  }
  return text
}
```

- 建议：在 `readableMessage` 或 `ApiError` 出口统一调用 `humanizeBackendText`；对 5xx/502/网关错误固定成业务话术，不要把上游原文直接给用户；如果调用方需要原始 message 排查，另放 `technicalMessage` 只进控制台/日志。
- 测试覆盖：未覆盖（`ops/check_ui_text_no_markdown` 不测错误内容；无 API 错误文案测试）。

### F14-07（P3）钉钉授权地址未校验协议

- 文件:行号：`frontend/src/modules/auth/LoginPage.tsx:76-89`
- 触发条件：`dingtalkAuthorize()` 返回的 `authorize_url` 被后端配置/上游污染成 `javascript:` 或其他非 http(s) 地址。
- 后果：`window.location.href = authorize_url` 会直接执行该 URL；虽然来源是后端接口，但缺少协议白名单，属于把“服务端返回的 URL”当成可信 href 的同类风险。`safe-url.ts` 已有 `isSafeExternalUrl`，登录页没有用。
- 证据代码：

```tsx
const { authorize_url } = await dingtalkAuthorize()
try {
  sessionStorage.setItem(DINGTALK_RETURN, returnTo)
} catch { /* ... */ }
window.location.href = authorize_url
```

- 建议：跳转前用 `isSafeExternalUrl(authorize_url)`，不合法就 Toast“钉钉登录地址无效”并停止；同时后端只允许配置 https 的钉钉授权域名。

### F14-08（P3）登录成功后 `fetchMe` 失败被吞，用户可能进入无权限空壳

- 文件:行号：`frontend/src/modules/auth/LoginPage.tsx:54-68`
- 触发条件：`/auth/login` 成功，但紧接着 `/auth/me` 网络失败/500（权限服务短暂不可用）。
- 后果：`setAuth(token, null)` 已建立登录态，`fetchMe` catch 静默，随后 `navigate(returnTo)`。`AppLayout` 的 `user` 为 null，菜单守卫 `hasPermission(null)` 为 false；除工作台和设置外，用户点任何模块都会看到“没有权限”，而不是“用户信息加载失败”。`useCurrentUserSync` 会在挂载后重试，但首屏体验是错误结论。
- 证据代码：

```tsx
const result = await login(username.trim(), password)
setAuth(result.access_token, null)
const epoch = currentAuthEpoch()
try {
  const me = await fetchMe()
  if (currentAuthEpoch() === epoch) setUser(me)
} catch {
  // 用户信息拉取失败不阻塞登录
}
navigate(returnTo, { replace: true })
```

- 建议：`fetchMe` 失败时不要静默进入业务页；显示“登录成功但权限加载失败，重试/退出”状态，或让 AppLayout 在 `user===null && token` 时展示全屏加载/重试，而不是按无权限处理。
- 测试覆盖：未覆盖（无登录后用户信息失败测试）。

### F14-09（P3）北京时间格式化对 `dateStyle/timeStyle` 自定义选项分错组

- 文件:行号：`frontend/src/shared/beijing-time.ts:28-64`
- 触发条件：调用方传 `formatBeijingTime(value, { dateStyle: 'long' })` 或 `timeStyle: 'short'`。

- 证据代码：

```ts
const DATE_PART_KEYS = ['year', 'month', 'day', 'weekday', 'era'] as const
...

  ;(date as Record<string, unknown>)[key] = value
} else {
  ;(time as Record<string, unknown>)[key] = value
}
```

- 建议：把 `dateStyle` 归到日期、`timeStyle` 归到时间；或在入口拒绝这两个复合选项，只允许拆分后的字段；补 `dateStyle/timeStyle/date+time` 单测。
- 测试覆盖：部分覆盖。`ops/check_frontend_utc_dates.py` 只查 `toISOString` 用法；`calendar_day.test.mjs` 不测 `dateStyle`。

### F14-10（P3）页签一次淘汰多个时只提示最后一个被关的标签

- 文件:行号：`frontend/src/shared/store/tabs.ts:112-119、177-183`


### F14-11（P3）AI 动作确认/拒绝共用两个 mutation，按钮状态互相牵连

## 五、正向确认

- `shared/api/client.ts` 的 401 处理按“登录代次”判断，`ops/auth_epoch_401.test.mjs` 覆盖了“旧账号慢请求不能踢掉新登录账号”的纯逻辑；`setAuth/clear` 同时清 React Query 缓存。
- `shared/safe-url.ts` 只放行 `http/https`，并拒绝 `//`、反斜杠、`/login` 返回路径；F14-07 是登录页没有使用它，不是 `safe-url` 本身失效。
- `app/lazyPage.tsx` 用 `loadedRef` 保证“页面已经渲染成功”后旧 chunk 失败不再自动刷新，避免丢用户已填内容；`alreadyReloaded` 按 pathname 各留一次机会。
- `shared/calendar-day.ts` 按本地年月日取日期，`ops/calendar_day.test.mjs` 覆盖跨时区“当地零点早一天”的问题。
- `shared/api/auth.ts` 的 `logout` 显式传 token，避免“先清 store 再发登出”导致服务端拿不到凭据、会话无法作废。
- `modules/common/NotificationBell.tsx` 对 `wecom_error`/`redispatch_hint` 使用 `humanizeBackendText`，说明项目已有可复用的业务话术层；F14-04 的缺口在 `client.ts` 没有统一调用。
