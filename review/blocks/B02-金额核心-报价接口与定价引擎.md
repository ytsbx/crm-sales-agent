## 二、本块发现清单

### B02-01｜P1｜已发送/已被客户接受的报价仍可改运费，总额与客户手里那份不一致

- **位置**：`backend/app/modules/quote/router.py:1426-1519`（新增/删除费用）、`1940-2008`（修改费用）；闸门在 `backend/app/modules/quote/service.py:90-161`
- **触发条件**：报价已发送或客户已接受（`version.accepted_at` 有值、`quote.status` 为 `accepted`），任意 `quote:manage` 用户对“物流”费用做新增、改金额或删除。
- **后果**：`ensure_charge_change_allowed` 只判 `approval_status in (pending, approved)` 或 `sent_at is not None`，对运费一律放行；修改后 `recalc_version` 立即改写 `version.total_amount`，并把 `sent_at` 清空（第 158–161 行），但 **`quote.status` 仍是 `sent/accepted`，`accepted_at` 也不清**。于是：客户手里 PDF 是旧总额，系统里是新的；若之前已转订单，订单金额与报价金额分叉；若尚未转订单，后续转订单会拿改动后的金额，而客户接受的是旧金额。已接受状态没有任何重新确认环节。
- **证据代码**：
  ```python
  if not (version.approval_status in ("pending", "approved") or version.sent_at is not None):
      return
  ...
  if version.sent_at is not None:
      version.sent_at = None
  ```
  路由侧只用 `get_visible_version(... for_update=True)`，从未读 `quote.status` / `accepted_at` / 是否已有订单。
- **建议**：闸门增加“报价主状态与客户结果”判断：`accepted_at` 非空或 `quote.status == accepted` 时禁止任何费用改动，只能新建版本；已转订单同样禁止。若业务确实允许接受后补运费，必须同时回退客户接受结果并要求重新发送/重新确认，且订单金额同步重算并留审计——不能只清 `sent_at`。

### B02-02｜P1｜报价负责人可被改成任意用户，绕过客户数据范围

- **位置**：`backend/app/modules/quote/router.py:403-409`（`update_quote` 只校验“存在 + active”）、`706`（`clone_quote` 直接赋值，连存在性都不校验）；字段来自 `quote/schema.py:160-161`
- **触发条件**：拥有 `quote:manage` 的业务员（数据范围“仅本人”）把某张自己可见的报价 `owner_id` 改成范围外的同事，或复制时指定 `owner_id`。
- **后果**：`list_quotes` 的可见性是 `draft_scope(... Quote.owner_id.in_(owner_ids) ...)`（第 202–203 行），负责人一改，新负责人就凭“本人负责”看到这张报价及其客户名、金额、版本；等于把客户报价数据推给不在该客户数据范围内的人。指派动作本身是显式操作，但是否允许普通业务员改负责人、允许指给谁，后端没有任何边界。
- **证据代码**：
  ```python
  if data.get("owner_id") is not None:
      owner = await session.get(User, data["owner_id"])
      if owner is None or owner.status != "active": ...
  for field, value in data.items():
      setattr(quote, field, value)
  ```
- **建议**：先确认业务规则。若只有主管/管理员能改负责人：加权限或“新负责人的数据范围必须覆盖该客户”的校验；复制同理。若允许业务员移交，至少要求新负责人对客户可见，并写审计“from→to”。

### B02-03｜P2｜改联系人只写 id，不校验联系人存在/属于本客户

- **位置**：`backend/app/modules/quote/router.py:387-438`（`update_quote`）；`quote/schema.py:149-162`

### B02-04｜P2｜已发送/已被客户接受的报价可以被软删除，只拦“已转订单”

- **位置**：`backend/app/modules/quote/router.py:441-476`
- **触发条件**：`DELETE /quotes/{id}`，该报价已发送或客户已接受，但还没有生成订单。
- **后果**：`deleted_at` 一置，列表/详情/发送记录全部消失；客户手里仍有报价 PDF，销售侧却查不到这张单。版本与审计还在库里，但没有恢复入口（`review` 里未见报价回收站）。属于“对外承诺被隐藏”，不是物理丢失，但业务上会表现为“单子不见了”。
- **证据代码**：只查 `SalesOrder.id`（第 454–458 行），没有任何 `quote.status` 判断。

### B02-05｜P2｜多角色价格权限口径不对称：利润率取最宽松，折扣上限取最严格

- **位置**：`backend/app/modules/pricing/service.py:790`（`return min(rows)`）、`812`（`margin = min(...)`）
- **触发条件**：一个用户同时拥有两个角色，且两个角色都配了价格权限，例如业务员（利润率 15%、折扣上限 20%）+ 经理（利润率 0%、折扣上限 30%）。
- **后果**：利润率取 `min(0, 0.15)=0`（最宽松），折扣上限取 `min(0.2, 0.3)=0.2`（最严格）。同一套“角色叠加”在两项权限上方向相反：经理权限带给他 0% 利润率（可报到底价），却不带给他 30% 折扣（20% 以上仍要审批）。要么多触发审批，要么在另一侧放行过度，取决于业务对“角色叠加”的定义。
- **证据代码**：`return min(rows) if rows else None`（折扣）；`margin = min((perm.minimum_margin for perm, _ in rows), ...)`（利润率）。
- **建议**：确认口径后统一：若角色是“叠加授权”，两项都应取最宽松（利润率 min、折扣上限 max）；若按“最严角色约束”，两项都应取最严。当前两种方向并存，至少要在注释和测试里写清为什么。

### B02-06｜已关闭（B03 复核）｜核价服务把成本/保护价/底价原样放进响应，是否泄露取决于路由裁剪

> B03 复核结论：`pricing/router.py:1170-1237` 的 `_sanitize_pricing_result` 已对无 `price:manage` 用户清空成本、保护价、授权底价、硬底、利润及 `inputs` 派生值；`calculate`/`batch-calculate`/`check-permission`/`simulate` 均调用；`lookup`、`price-summary`、成本单条入口也已同口径。未发现泄露，本条关闭。

- **位置**：`backend/app/modules/pricing/service.py:1326-1409`（`cost`、`protection_price`、`minimum_price`、`hard_floor_price`），`1373-1374`（`serialize_price_rule`/`serialize_customer_price` 用默认 `can_see_cost=True`）
- **触发条件**：只有 `price:view`（无 `price:manage`）的用户调用 `POST /pricing/calculate` 或 `check-permission`。
- **后果**：service 层不判权限，成本四项、商品成本、保护价、授权底价、硬底价、利润全部在返回体里；若 `pricing/router.py` 没有按 `price:manage` 整体裁剪，普通销售可据此反推成本。报价详情侧是做了裁剪的（`serialize_item`），核价侧要看路由。

- **建议**：B03 核对 `pricing/router.py` 的 `calculate`/`check-permission`/`simulate` 是否统一裁剪；若没有，按 `price:manage` 隐藏 `cost.*`、`protection_price`、`minimum_price`、`hard_floor_price` 与两个 rule 对象里的 `minimum_price`。

### B02-07｜P2｜外币没有汇率时，仍拿人民币底价和外币报价做比较

- **位置**：`backend/app/modules/pricing/service.py:1153-1158`（缺汇率只 warning、`fx=None`）、`1234-1250`（比较不跳过）
- **触发条件**：`currency != CNY` 且未提供汇率（或汇率为 0），同时传了 `quoted_price`。
- **后果**：`floor_price`、`protection_price` 仍是人民币数值，`check_price` 是外币数值，直接比大小：10 美元 vs 94 元人民币会被判“低于保护价”，100 美元 vs 94 元会被判“没低”——两种结论都没有意义。代码只对绝对底价加了 `not (is_foreign and fx is None)` 的保护（第 1283 行），另外三条没加。草稿阶段会给销售错误的“需不需要审批”信号；若提交侧没有汇率硬闸，还会把错误结论带进审批。
- **证据代码**：
  ```python
  if is_foreign and (fx is None or fx <= 0):
      warnings.append(...)
      fx = None
  ...
  below_protection = protection_price is not None and check_price is not None and check_price < protection_price - ...
  ```
- **建议**：外币且无汇率时，保护价/授权价/利润率/折扣四条一律置 `None`（不可判定），并在响应里明确“汇率缺失，审批判定暂停”；不要给出真假不明的 `approval_required`。

### B02-08｜P3｜退税与运费单价量化仍用默认 HALF_EVEN

- **位置**：`backend/app/modules/pricing/service.py:885`（`unit ... .quantize(Decimal("0.0001"))`）、`1218-1221`（退税 0.0001）
- **触发条件**：运费按数量摊到单件、退税额折算出现半厘/半毫。
- **后果**：与 `core/money.py` 的 `ROUND_HALF_UP` 不一致；单件运费 4 位、退税 4 位，后续汇总到 2 位时可能出现 1 分差，且与报价侧 `convert_cny_to`（同样默认 HALF_EVEN）叠在一起，排查时很难定位是哪一步舍的。
- **证据代码**：`unit = (Decimal(str(chosen["amount"])) / quantity).quantize(Decimal("0.0001"))`
- **建议**：与 B01-03 一并收口到统一的 `quantize` helper，显式指定 rounding。

### B02-09｜P3｜查看历史版本时，`current_version_no/amount` 填的是被查看版本

- **位置**：`backend/app/modules/quote/router.py:1078-1094`
- **触发条件**：`GET /quote-versions/{id}` 查看一个非当前版本（V1，而当前是 V3）。
- **后果**：`quote.current_version_id` 是 V3 的 id，但 `serialize_quote(quote, version=version)` 把 `current_version_no`/`current_version_amount` 填成 V1 的号与金额；前端若用这两个字段显示“当前版本”，会出现“当前版本 V1、id 指向 V3”的自相矛盾。
- **证据代码**：`svc.serialize_quote(quote, version=version, ...)`，`version` 是请求的历史版本。
- **建议**：详情页单独用请求版本渲染时，把 `version` 字段改名成 `viewed_version_*`，或另取 `quote.current_version_id` 对应的版本填 `current_version_*`。

### B02-10｜P3｜邮件发送记录可重复登记，没有请求键/去重

- **位置**：`backend/app/modules/quote/router.py:2158-2221`
- **触发条件**：用户重复点击“发送邮件”，或前端重试。
- **后果**：每次调用都插入一条 `QuoteSendLog(status="logged")`，`sent_at` 各不相同；台账上会出现多条“已登记未投递”，无法区分哪次是真实尝试。因为不写 `version.sent_at`，不会造成重复入账，只是噪音与排查干扰。
- **证据代码**：直接 `session.add(QuoteSendLog(...))`，无 `request_key`、无唯一约束。
- **建议**：给邮件登记加 `request_key` 幂等，或按 `(version_id, receiver, 时间窗口)` 去重；重复点击返回原记录。

### B02-11｜P3｜路由文件尾部遗留 `__all__ = ["date", "QuoteItem"]`

- **位置**：`backend/app/modules/quote/router.py:1826`
- **触发条件**：任何 `from ... import *`（当前没有）。
- **后果**：导出的是 `date` 与 `QuoteItem`，不是路由对象，属于旧代码残留；会误导后续维护者以为这里有公共导出。
- **证据代码**：`__all__ = ["date", "QuoteItem"]`，位置在 `download_pdf` 之后、别名接口之前。
- **建议**：删除。

### B02-12｜P2｜版本有效期可被显式置空，报价从此永不失效

- **位置**：`backend/app/modules/quote/router.py:1144-1161`；`quote/schema.py:36`
- **触发条件**：`PATCH /quote-versions/{id}` 传 `{"valid_until": null}`。
- **后果**：`valid_until_snapshot` 与主单 `valid_until` 都被写成 `None`；`quote_is_expired` 对空值返回“未过期”，发送与过期判断从此永远放行。报价可以无限期对外有效，且没有提示。
- **证据代码**：
  ```python
  valid_until = data.pop("valid_until", None)
  ...
  if valid_until is not None:
      quote.valid_until = valid_until
      version.valid_until_snapshot = valid_until
  ```
  注意：`exclude_unset` 下“显式 null”与“没传”被合并成同一个 `None`，两者无法区分。
- **建议**：显式 null 应报 422 “有效期不能为空”；若要允许“长期有效”，单独加 `valid_until=None` 的显式语义与审计，不要让清空字段静默变成永久有效。

### B02-13｜P3（观察）｜成本版本同日重复只能等到核价时才报 409

- **位置**：`pricing/model.py:35`（无唯一约束）；`pricing/service.py:212-222`（读取时才发现同日多条）
- **触发条件**：成本维护/导入在同一 SKU、同一 `effective_from` 写两条。
- **后果**：写入成功，直到某次核价/提交才 409“无法确定用哪一条”，此时报价流程已被打断；用户很难把“核价报错”与“两周前多建了一条成本”联系起来。
- **建议**：写入端用与取价同一判据拦截（同一 SKU + 同一生效日只能一条），或加部分唯一索引；至少返回里带上冲突行 id 与入口链接，而不只是 409。
