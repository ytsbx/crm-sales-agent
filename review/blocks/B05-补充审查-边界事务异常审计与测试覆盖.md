## 一、补充项检查结果

### B05-19｜P2｜确认/驳回回款的审计只记 comment/status，不记金额、币种、订单与期次

- **位置**：`backend/app/modules/payment/router.py:1170-1178`（confirm）、`1204-1214`（reject）
- **触发条件**：财务确认或驳回一笔回款。
- **后果**：`confirm` 审计的 `after` 只有 `{"comment": payload.comment}`；`reject` 审计的 `before/after` 只有 `status` 与 `comment`。没有 `received_amount_exact`、`currency`、`order_id`、`receivable_plan_id`、分配结果。回款确认是入账动作，审计本身不能证明“确认了多少钱、挂哪张单、哪一期”；只能再按 `business_id` 去 `payment_records` 表 join。若记录被归档/迁移，审计就只剩“确认过”。
- **证据代码**：
  ```python
  # confirm
  await write_audit(session, operator_id=user.id, action="confirm",
      business_type="payment", business_id=record.id,
      after={"comment": payload.comment}, ip=client_ip(request))
  # reject
  await write_audit(session, operator_id=user.id, action="reject",
      business_type="payment", business_id=record.id,
      before={"status": "pending"},
      after={"status": "rejected", "comment": payload.comment}, ...)
  ```
- **建议**：两处审计补 `received_amount_exact/currency/order_id/receivable_plan_id`，以及 `allocations`（plan_id/amount）摘要；confirm 的 `before` 可记 `status=pending`，reject 同理。金额用 Decimal 字符串，不要 float。
- **测试覆盖**：未覆盖。`backend/tests/test_payment_consistency.py:390-416` 只断言确认的锁序/汇总，不断言审计字段；`test_batch15_financial_lifecycle.py:213` 只断言订单取消驳回回款的 `comment`，恰好证明当前审计只有 comment。

### B05-20｜P3｜逾期刷新按订单逐笔 commit，调度中途失败会留下“部分订单已刷新、部分没刷”的半批次

- **位置**：`backend/app/modules/payment/service.py:437-466`（`commit_per_order`）；调用方 `backend/app/core/scheduler.py:78`
- **触发条件**：定时任务调用 `refresh_overdue_plans(commit_per_order=True)`，处理到第 N 张订单时数据库/连接异常。
- **后果**：前 N-1 张订单的状态已经提交，后面的没处理；`run_step` 失败后任务会记录失败，但数据不是原子批次，也没有“本次刷新到哪张订单”的断点/审计。重跑能补齐（幂等），但失败窗口内应收状态一半新一半旧，财务看到的逾期口径不一致。
- **证据代码**：
  ```python
  for oid in order_ids:
      ...
      if commit_per_order:
          await session.commit()
  ```
- **建议**：保留分批提交以控制锁时间，但增加批次进度记录（最后处理的 order_id）和每次提交后的计数日志；或在失败时把已处理订单 id 写入任务结果，便于重跑核对。若业务要求强一致，改成单事务 + SAVEPOINT 的权衡需人工决定。
- **测试覆盖**：未覆盖。没有调度中途失败的用例；`test_payment_consistency.py` 只测单请求内的锁序/状态。

## 二、补充项“没发现问题”的结论

- **负数/0/超大值/小数位**：`PaymentCreate.received_amount` 与 `PaymentUpdate.received_amount` 都是 `gt=0, max_digits=16, decimal_places=2`；`ReceivableCreate/Update.amount`、`PaymentAllocationItem.amount` 同为 2 位；`ratios` 的 float 问题仍是 B03-15，不重复。未发现新的金额边界入口。
- **事务边界**：登记/改回款/确认/驳回/分配调整/应收增改删都是“业务写 + 审计 + 一次 commit”；锁序为订单→节点→回款→分配，未发现两笔并发确认各写各的。唯一例外是 B05-20 的调度分批提交。
- **异常/错误信息/日志**：`create_payment`/`generate` 的 `except Exception` 只做 `release` 后 `raise`，不吞异常；`upload_payment_voucher` 对 `Exception` 和 `CancelledError` 都做磁盘补偿；`remove_voucher` 的磁盘删除失败只 warning、不把已成功的解绑返回 500，属明确设计。未发现把 SQL/堆栈返回前端；`logger.warning` 里带 `object_key` 是内部存储键，不含金额/客户字段。
- **审计（已有）**：应收建/改/删/生成/逾期标记、回款建/改/分配调整/凭证挂删都有审计；回款确认/驳回有审计但字段不足（B05-19）。B05-01 的“重平衡无逐笔回款审计”仍是 P1，不重复。
