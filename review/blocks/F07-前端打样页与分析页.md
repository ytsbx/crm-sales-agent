### F07-01 P2：分析页绝大多数查询失败被静默为零/空数据

- **文件:行号**：`frontend/src/modules/analytics/AnalyticsPage.tsx:350-375`（查询）、`:580`（`money`）、`:657-663`（概览 KPI）、`:854-895`（回款 KPI）、`:917-952`（发货 KPI）、`:1076-1157`（发货/风险表）、`:1160-1238`（产品表）、`:1241-1277`（业务员表）、`:1362-1400`（目标区）、`:1677`（下钻合计）。
- **触发条件**：`opportunityQuery`、`receivableQuery`、`paymentQuery`、`deliveryQuery`、`customerQuery`、`leadQuery`、`pricingQuery`、`basesQuery`、`drilldownQuery` 等任一个返回 500/超时/解析失败；页面只在 `targetsQuery` 一处做了 `isError` 重试。
- **后果**：`money(value)` 是 `Math.round(value ?? 0)`，查询失败时 `undefined` 直接变成 **¥0**；`deliverySummary?.late_count ?? 0`、`customer.active_count ?? 0` 等也显示 0。用户会看到“尚未到账 ¥0 / 逾期 0 期 / 延迟 0 单 / 活跃 0 家”，把接口故障当成业务真的为零；产品/业务员/风险表失败则显示“还没有报价数据/暂无数据”。这是管理决策页，误导性比普通列表更大。
- **证据代码**：
  ```ts
  const money = (value?: number) => `¥${Math.round(value ?? 0).toLocaleString('zh-CN')}`
  ...
  <dd>{receivable ? money(receivable.unreceived_amount) : '—'}</dd>
  ...
  <dd>{payment ? money(payment.overdue_amount) : '—'}</dd>
  ```
  ```tsx
  dataSource={(productQuery.data ?? []).filter(...)}
  loading={productQuery.isLoading}
  empty={keyword ? noMatches : '还没有报价数据'}
  ```
- **建议**：给每个区块加 `isError` 错误态（可复用“读取失败，重试”按钮）；不要在错误时回退成 0。`money` 至少区分 `undefined`（未知）和 0；0 用 `¥0.00`，未知用 `—` 或错误条。下钻失败也显示错误而不是“没有明细”。
- **测试覆盖**：未覆盖。`backend/tests/test_analytics_issue_fixes.py` 只覆盖审批摘要利润脱敏，不覆盖前端查询失败；无前端测试。

### F07-04 P2：来源打样请求键在每次编辑时重置，已成功未回执后再改会重复建单

- **文件:行号**：`frontend/src/modules/sample/SampleFromSourceModal.tsx:35`、`:64-67`、`frontend/src/shared/api/sample.ts:318-323`；后端 `backend/app/modules/sample/sources.py:71-94`。
- **触发条件**：从报价/询价来源建打样或订单草稿，第一次请求已在后端成功但响应丢失；用户修改数量/勾选/规格后再点“建立”。或者第一次失败后编辑再重试。

- **证据代码**：
  ```ts
  // SampleFromSourceModal.tsx:35
  const requestKey = useRef(newRequestKey())
  ...
  // :64-67
  function change(id: number, patch: Partial<Draft>) {
    if (sending.current) return
    requestKey.current = newRequestKey()
  ```
- **建议**：请求发出后进入“结果未确认”状态，先提示并刷新来源/最近单据，确认没有成功再允许改；或者把请求键与内容指纹绑定，后端对同内容不同键做短窗口去重。不要一编辑就静默换键。
- **测试覆盖**：部分覆盖。`backend/tests/test_sample_sources.py:19-34` 只测键必填/数量边界，不测前端键生命周期；无前端测试。

### F07-05 P2：运费/打样费用/工时用 JS `Number` 转金额，16 位/小数位边界会丢精度

- **文件:行号**：`frontend/src/modules/sample/SampleListPage.tsx:513-528`（运费）、`:564-589`（打样费用/预计工时）；后端 `backend/app/modules/sample/schema.py:188/200/291`。
- **触发条件**：运费填 `9999999999999.99`、打样费用填 16 位两位小数，或工时填 `1.005`（后端只允许 2 位小数）。
- **后果**：`Number(raw)` 先把十进制文本变成 binary float，再 POST；16 位金额可能差 1 分，3 位工时会被后端 422 或截断。打样费用/运费会进入 OA 申请表和导出 Excel，车间/财务看到的金额可能与用户输入不一致。
- **证据代码**：
  ```ts
  const fee = raw === '' ? 0 : Number(raw)
  ...
  const fee = raw === '' ? null : Number(raw)
  const hours = rawHours === '' ? null : Number(rawHours)
  ```
- **建议**：金额/工时输入保留原始字符串（`parseOptionalDecimal`/string 模式），API 标 `string`；前端校验运费/打样费用 2 位小数、工时 2 位小数且 <=9999，16 位总长由后端兜底但前端也应提示。
- **测试覆盖**：部分覆盖。后端 `schema.py` 有 `Decimal` 约束，`test_sample_application_form.py` 测字段，但没有前端 `Number` 精度用例。

- **后果**：`Number.isFinite(Number(draft.quantity))` 只判正，`1e3` 会通过并原样作为字符串发给后端；后端 `Decimal(16,3)` 会 422，用户看到底层字段错误。`1.0001` 也可能在输入框里被接受，提交才报错。
- **证据代码**：
  ```ts
  const quantityMissing = selected.filter(({ draft }) =>
    !Number.isFinite(Number(draft.quantity)) || !(Number(draft.quantity) > 0))
  ```
- **建议**：用十进制文本校验 `>0`、整数位<=13、小数位<=3，并在行内提示；不要用 `Number` 作为唯一判据。
- **测试覆盖**：部分覆盖。`test_sample_sources.py:21-24` 覆盖后端数量边界，不覆盖前端。

### F07-14 P3：新建打样只校验产品名称，不校验客户/商机必填

### F07-15 P3：目标保存无请求键，弱网重试只能靠 `expected_updated_at`/唯一键兜底

- **文件:行号**：`frontend/src/modules/analytics/AnalyticsPage.tsx:403-433`。

### F07-16 P3：OA 申请资料里的打样费用是自由文本，没有 2 位小数/上限提示

- **测试覆盖**：后端 Decimal 约束覆盖，无前端测试。

## 三、补充维度核对

### 1. 负数、0、超大值、小数位

- 打样运费：前端拒负数、正则限 2 位小数，但 `Number` 会丢 16 位精度（F07-05）。
- 打样费用：前端拒负数，但不限 2 位小数/上限；`saveProdMutation` 用 `Number`（F07-05），OA 资料用自由文本（F07-16）。
- 预计工时：前端拒负数，不限 2 位小数/9999 上限；积分 `Number*10` 有浮点尾数（F07-09）。
- 来源数量：只判正，不判 16 位/3 位小数（F07-13）。
- 分析目标：目标金额/家数只判 NaN，不判负数/上限（F07-12）；0 允许，符合“目标可以为 0”的后端口径。
- 分析金额：概览/图表 `Math.round` 到元（F07-11）；`money(undefined)` 变 0（F07-01）。
- **未发现**：本块没有收款/退款/负金额入账入口；打样费用负数后端有 `ge=0`。

### 2. 事务边界

- 打样新建是后端单事务：`SampleRequest + items + audit + commit`；如果任一条明细失败，整个请求回滚，不会只留单头（未做故障注入，按代码路径判断）。
- 加明细是单事务：`_add_item + flush + audit + commit`；中途失败不会留半条明细。
- 来源创建 `create_from_source` 有请求键/内容摘要和唯一约束，事务内建单+明细；这是本块做得较好的地方。
- 分析页是只读查询；目标保存是单行 upsert，没有跨表半成品。
- **未验证**：commit 后响应丢失的重试、审计写失败、真实 PG 并发；本块未构造。

### 3. 异常吞掉 / 泄露 / 日志敏感信息

- 分析页查询失败被零/空态吞掉（F07-01）；制作依据附件失败被“没有附件”吞掉（F07-06）。
- 打样各 `onError` 用统一 `onError` Toast；`SampleFromSourceModal` 用 `(error as Error).message`，没有把后端堆栈/JSON 直出，但也没有 403/409/422 分类。
- `SampleDingTalkModal` 的 `row.error` 直接显示后端/外部 OA 错误文本；本块没有看到完整堆栈，但外部错误原文是否含敏感信息需后端/集成块确认。
- 日志：本块前端不写日志；未检查后端日志是否含打样费用/客户信息。

### 4. 审计

- 打样创建、加明细、审批、重提、制作、修订后端都有 `write_audit`；本块没有改价/收款/作废操作。

- 分析目标保存/冻结/重算的后端审计不在本块重审；前端只确认无请求键、无 before/after 展示。
