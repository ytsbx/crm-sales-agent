## 二、发现清单

### B03-01｜P1｜同角色可产生两条价格权限，权限解析取最宽松值

- **位置**：`backend/app/modules/pricing/model.py:144-151`；`pricing/router.py:963-970`、`2155-2165`；`pricing/service.py:803-813`
- **触发条件**：两个管理员同时首次给同一角色 `PUT /price-permissions/{role_id}`（或同时 `POST`），两边都查到“没有记录”，各自 INSERT；表上只有普通索引，没有 `role_id` 唯一约束。
- **后果**：同一角色出现两条 `active` 权限。`resolve_price_permission` 取 `min(minimum_margin)` 和 `any(can_approve)`，即**利润率按最宽松、审批权按“任一条为真”**生效；原本 15% 下限 + 不可自审的角色可能变成 0% + 可自审。之后该角色再 PUT 会因 `scalar_one_or_none()` 命中多行直接 500。
- **证据代码**：
  ```python
  # model.py:145
  __table_args__ = (Index("ix_price_permissions_role", "role_id"),)  # 非 unique

  # router.py:963-970
  permission = (await session.execute(
      select(PricePermission).where(PricePermission.role_id == role_id)
  )).scalar_one_or_none()
  if permission is None:
      permission = PricePermission(role_id=role_id, status="active")
      session.add(permission)
  ```
  ```python
  # service.py:812-813
  margin = min((perm.minimum_margin for perm, _ in rows), default=fallback)
  can_approve = any(perm.can_approve for perm, _ in rows)
  ```
- **建议**：加 `role_id` 唯一约束（迁移前先清理重复行）；PUT/POST 对 `role_id` 取 advisory lock 或 `INSERT ... ON CONFLICT`；`resolve_price_permission` 命中多行时显式报错而不是静默取最宽松。

### B03-02｜P1｜草稿 PATCH 把“没传的字段”直接清空，价格/付款条件会静默丢失

- **位置**：`backend/app/modules/order/drafts.py:122-135`；`order/schema.py:220-225`、`242-248`
- **触发条件**：`PATCH /order-drafts/{id}` 只改数量/规格，明细行不带 `unit_price`，或请求不带 `payment_terms`/`delivery_date`/`remark`。这些字段在 schema 里都是可选、默认 `None`，代码不做 `model_fields_set` 判断，直接赋值。
- **后果**：原单价被写成 `NULL`，付款条件/交期/备注被清空；草稿本身不会报错，直到 `confirm` 比对“单价/付款条件必须与客户确认版本一致”时才 422。用户看到的是“保存成功”，再下单时才发现数据没了；若后续有人重新填错价格，还会把错误带进订单。
- **证据代码**：
  ```python
  # drafts.py:124-135
  item.quantity, item.unit_price = selected.quantity, selected.unit_price
  item.specification, item.remark = selected.specification, selected.remark
  ...
  draft.delivery_date, draft.payment_terms, draft.remark = (
      payload.delivery_date, payload.payment_terms, payload.remark
  )
  ```
  ```python
  # schema.py:242-248
  class OrderDraftUpdate(PatchModel):
      revision: int = Field(gt=0)
      currency: str | None = ...
      items: list[OrderDraftLine] = Field(min_length=1, max_length=200)
      delivery_date: date | None = None
      payment_terms: str | None = None
      remark: str | None = None
  ```
- **建议**：用 `payload.model_fields_set` 区分“没传/显式 null”；对 `items` 里没传 `unit_price` 的行保留原值，显式 null 才清空并返回明确提示；`payment_terms`/`delivery_date` 同样按字段是否出现来更新。

### B03-03｜P1｜非人民币草稿/订单存在绕过 CNY-only 的路径

> B05 复核（2026-11-21）：`core/trade_mode.py:153-157` 的 `CURRENCY_GATE_SITES` 明确只列三个入口，注释把“订单继承报价版本、回款继承应收节点”等继承路径排除；同一文件又承认历史外币可能来自 export/ERP。因此这不是“漏写一个 if”，而是“是否允许历史外币继续流转”的规则缺口。按项目规则仍记 P1，状态改为“待决策”：需业务确认是强制改 CNY，还是允许存量继续。

- **位置**：`backend/app/modules/order/drafts.py:96-98`、`131-134`；`backend/app/modules/order/service.py:305`、`474-476`
- **触发条件**：从一条历史外币报价版本创建草稿（`preview` 把 `version.currency` 原样写入 `source['currency']`，`create` 直接落库），或该外币版本已客户接受后走转单。手工建单入口有 `ensure_currency_allowed`，但“报价版本 → 草稿 → 订单”这条链路没有。
- **后果**：草稿和订单以 USD/EUR 落库，违反“只支持 CNY、非人民币明确拒绝”的口径；后续应收、收款、对账会沿用一个系统不支持的币种，金额口径无法统一。
- **证据代码**：

  ```python
  # drafts.py:131-134（只有显式改币种时才判）

      draft.currency = await ensure_currency_allowed(...)
  ```
  ```python

  # 同一文件 474-476：手工建单才判

  ```
- **建议**：`preview`/`create`/`confirm` 与 `create_order_from_quote` 都调用 `ensure_currency_allowed`；历史外币数据要转单时明确报“该系统已停用外币，请新建人民币版本”，不要静默放行。

### B03-04｜P2｜成本页面写入口没有同日重复校验，脏数据会让核价整体 409

- **位置**：`backend/app/modules/pricing/router.py:96-150`、`153-204`；`pricing/model.py:35`；`pricing/service.py:191-220`
- **触发条件**：同一 SKU、同一 `effective_from` 连续新增两条成本；或把一条成本的 `effective_from` PATCH 成与另一条同日。写入端没有任何冲突查询（导入端会查并拒绝）。
- **后果**：两条同日成本落库成功；之后该 SKU 的任何核价/报价提交都会在 `get_effective_cost` 报 409“无法确定用哪一条”，整个 SKU 的报价流程被堵住；用户很难把“今天核价报错”与“之前多建了一条成本”联系起来。B02-13 的“只能到核价才报”在页面写入端得到确认。
- **证据代码**：
  ```python
  # router.py:137-139（create 直接落库，之前只校验了四项非空/日期倒置）
  cost = ProductCost(**values, sku_id=sku_id, created_by=user.id)

  ```
  ```python
  # service.py:212-216
  top_day = rows[0].effective_from
  ```

### B03-05｜P2｜运费金额经 float 往返后落库，金额链路不是全程 Decimal

### B03-17｜P3｜删除运费费率不拿增改用的 advisory lock
