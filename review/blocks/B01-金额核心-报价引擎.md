## 二、本块发现清单

### B01-01｜P1｜审批分档用 float 比较，边界单可能落到低一档审批人

- **位置**：`backend/app/modules/quote/service.py:2399-2405`、`2768`
- **触发条件**：外币报价（总额按快照汇率折算成人民币）或人民币大额单，折算结果恰好落在 `approval_levels` 的 `max_amount` 边界附近（例如 USD 10000 × 7.123456 = 71234.56，档位上限正好 71234.56）。
- **后果**：`total_amount_cny` 先被 `float()` 转换，再与 `float(max_amount)` 比较；二进制舍入可能把 71234.56 变成 71234.559999…，判定为“未超过”，进入低一档（金额更小、权限更低的审批人）。审批层级错位，等于把该由更高层批的单放给低层。
- **证据代码**：
  ```python
  total_amount_cny = (
      float((version.total_amount or 0) * fx)
      if currency_code != "CNY"
      else float(version.total_amount or 0)
  )
  ...
  if max_amount is None or amount <= float(max_amount):
      node = level
      break
  ```
- **建议**：`total_amount_cny` 保持 Decimal（`(version.total_amount or ZERO) * fx`，按分 `quantize(ROUND_HALF_UP)`），`max_amount` 用 `Decimal(str(max_amount))` 比较；仅在写审计 JSON 时才转 float/str。

### B01-02｜P2｜报价读接口把金额转成 float 输出，分位精度依赖前端是否改用 `*_exact`

- **位置**：`backend/app/modules/quote/service.py:242-243`（`_f`），被 `serialize_item/serialize_charge/serialize_version/serialize_quote/amount_summary` 广泛使用；具体如 `980`、`2890-3003`。
- **触发条件**：金额较大（接近 `Numeric(16,2)` 上限）或成本为 4 位小数；前端用 `amount`、`cost_snapshot`、`charge_amount` 等 float 字段做二次汇总/比较，而不是用 `amount_exact`/`total_amount_exact`。
- **后果**：float64 在 1e14 量级的分辨率约 0.015，无法稳定表示“分”；四位成本（如 33.3333）转 float 也会带尾差。页面汇总、What-if 试算、复制/对比可能与后端 Decimal 结果差 1 分，严重时影响审批边界判断。
- **证据代码**：
  ```python
  def _f(value: Decimal | None) -> float | None:
      return None if value is None else float(value)
  ```
  `serialize_version` 只给了 `total_amount_exact`，`subtotal_amount/charge_amount/discount_amount/logistics_amount/other_charge_amount` 都没有 exact 版本（第 411–420 行）。
- **建议**：金额字段统一 `str(Decimal)` 输出（或同时提供 exact）；至少给所有参与汇总的金额补 `*_exact`。前端侧在 F01/F03 块核对是否真的用 float 做运算。

### B01-03｜P2｜舍入模式不统一：逐行用 `ROUND_HALF_UP`，底价/换算/合计有多处使用默认 `ROUND_HALF_EVEN`

- **位置**：`backend/app/modules/quote/service.py:709`（`convert_cny_to` 量化 0.0001）、`1307-1311`（定制项底价）、`1635`（重建底价）、`1932-1939`（版本各合计 `quantize(0.01)`）。
- **触发条件**：被量化的值恰好是“半分/半厘”的 ties，例如定制项 `basis_cost / (1 - min_ratio)` 得到 94.125，或汇率折算结果落在 0.00005。
- **后果**：默认上下文舍入是 `ROUND_HALF_EVEN`，与 `core/money.py` 的 `ROUND_HALF_UP` 不一致。底价可能差 0.01：94.125 在 HALF_EVEN 下是 94.12、HALF_UP 下是 94.13；报价恰好 94.12 时，一个判“需审批”、一个判“免审”。金额合计因为源数据已是两位，目前多为无操作，但属于同一类隐患。
- **证据代码**：
  ```python
  minimum_price = (
      (basis_cost / (Decimal(1) - min_ratio)).quantize(Decimal("0.01"))
      ...
  )
  ...
  fresh_floor = max(floors).quantize(Decimal("0.01")) if floors else None
  ```
- **建议**：定义 `CENT = Decimal("0.01")` 与统一 `quantize(CENT, rounding=ROUND_HALF_UP)`，所有金额/底价/汇率量化走同一处；汇率可按 6 位但同样显式指定舍入。

### B01-04｜P3｜生产代码残留 `probe` 调试日志

### B01-05｜P3｜定制项审批理由把“除法底价”写成了“乘法加价”，误导审批人

- **位置**：`backend/app/modules/quote/service.py:1368-1370`（文案），实际算法在 `1307-1308`
- **触发条件**：任意定制项低于保护价、生成审批理由时。
- **后果**：理由写“成本 ¥X×(1+15%)”，实际底价是“成本 ÷ (1−15%)”。按文案复算会得到更低的底价（92 vs 94.12），审批人可能误判“只差一点”，也可能据此质疑系统算错。
- **证据代码**：
  ```python
  f"（成本 ¥{cost}×(1+{min_ratio})），需审批"
  ```
- **建议**：文案改为“成本 ¥X ÷ (1−15%)”，与 `floor_from_margin` 同一措辞。

### B01-06｜P3｜版本对比的毛利率差额用 `round(float, 6)`

- **位置**：`backend/app/modules/quote/service.py:3184`
- **触发条件**：任意两版对比。
- **后果**：`margin_delta` 先由两个 Decimal 相减得到 Decimal，再 `round(..., 6)` 转成 float；展示精度与“六位小数”的存储口径不完全一致，且与同结构里的 exact 字符串风格不统一。
- **证据代码**：`"margin_delta": round(current["margin"] - previous["margin"], 6)`
- **建议**：用 `Decimal` 相减后 `quantize(Decimal("0.000001"), ROUND_HALF_UP)`，输出时再转字符串。

### B01-07｜待确认｜整单加权硬底只剔除运费、不剔除其他附加费用，可能被“服务费”抬高加权均价

- **位置**：`backend/app/modules/quote/service.py:2443-2451`
- **触发条件**：明细单价低于硬底、但整单附加了一条大额“其他费用”（非运费、非折扣），且逐行检查没有命中（例如折扣把净价压到硬底以下，再用服务费把总额拉回）。
- **后果**：`revenue_cny = total_amount - logistics_amount` 仍包含 `other_charge_amount`；`avg_price` 被服务费抬高，可能不低于 `avg_floor`，于是整单硬底检查放行。是否算“绕过”取决于业务是否认可“服务费属于产品收入”。
- **证据代码**：
  ```python
  revenue_cny = (version.total_amount * fx) if foreign else version.total_amount
  if not cost_includes_freight:
      revenue_cny -= (version.logistics_amount * fx) if foreign else version.logistics_amount
  avg_price = revenue_cny / total_qty
  ```
- **建议**：先确认口径——硬底是否只针对“产品货款”（`subtotal + discount`）。若只针对产品，收入侧应剔除 `charge_amount` 全部，而不仅是运费；若认可服务费计入，则在注释里写清并补测试。

### B01-08｜待确认｜同数据范围的他人可代提交草稿，并按自己的价格权限判定

- **位置**：`backend/app/modules/quote/service.py:2377`（用调用方 `user_roles` 解析底价/折扣），路由 `quote/router.py:1530-1544`

- **后果**：系统按提交人（主管）的 `min_margin`/`discount_limit` 重判，可能直接 `approved`，不产生主管的“审批”记录。主管本身有该价格权限，但这是“代提交即免审”，不是显式审批动作。
- **证据代码**：`min_margin, can_approve = await pricing_service.resolve_min_margin(session, user_roles)`
- **建议**：确认业务是否允许代提交。若不允许，提交时要求 `version.created_by == user.id` 或报价负责人；若允许，至少把“提交人 ≠ 创建人”写进审批摘要/审计，避免看起来像创建人自审。
