## 一、补充项检查结果

### B04-19｜P2｜取消订单的审计只记“驳回了几个/取消了几个”，不记金额和具体应收期次

- **位置**：`backend/app/modules/order/router.py:1054-1066`
- **触发条件**：主管取消一张已有应收计划、待确认回款或未发货批次的订单。
- **后果**：取消审计的 `after` 只有 `rejected_pending_payments`（数量）、`cancelled_receivable_plans`（数量）、`opportunity_id` 和一句 note：
  ```python
  after={
      "status": "cancelled",
      "rejected_pending_payments": len(pending_payments),
      "cancelled_receivable_plans": sum(1 for p in plans if p.status == "cancelled"),
      "opportunity_id": order.opportunity_id,
      "note": "商机成交状态未自动回退，如需撤销请人工评估",
  }
  ```
  没有订单总额、已收/未收、被驳回回款的金额/币种、被取消应收期次的 id/期次/金额。事后只能知道“取消时有 2 笔待确认、3 期应收被取消”，无法从审计复算财务影响；应收计划的状态变化也没有逐条审计（只有待确认回款的 `reject` 有逐笔审计）。
- **建议**：取消审计补 `total_amount_exact/currency/received_amount_exact/unreceived_amount_exact`，以及 `rejected_payments`（id、金额、币种）、`cancelled_plans`（id、plan_name、amount、due_date）的明细；批量改应收状态时逐条写 `receivable_plan:cancel` 审计，或写一个带明细的父审计。
- **测试覆盖**：未覆盖。`backend/tests` 没有订单取消审计断言；`test_payment_rebalance_order.py` 只测应收重排与审计，不测取消订单的审计字段。

### B04-20｜P2｜排发货批次的 `request_key` 可选，不带键双击会生成两条相同计划批次

- **位置**：`backend/app/modules/order/schema.py:165-170`（`request_key: str | None = None`）；`backend/app/modules/order/router.py:1275-1290`
- **触发条件**：客户端不传 `request_key`、也没带 `X-Request-Key`，双击“排发货批次”或网络重试；两次都通过 `order.status != cancelled` 与计划量校验。
- **后果**：`idempotency.reserve` 只在 `if request_key:` 时执行；没有键时直接 `create_shipment_batch`，生成两个不同 `batch_no` 的计划批次。两批都带相同计划量，跟单页出现两条重复计划；后续如果分别实发，第二次会被累计超订购拦住，但重复批次已经污染计划/交付统计，需要人工取消。
- **证据代码**：
  ```python
  # schema.py:165-166
  class ShipmentBatchCreate(BaseModel):
      request_key: str | None = Field(default=None, max_length=128)
  # router.py:1277-1287
  request_key = idempotency.request_key_from(request, payload.request_key)
  if request_key:
      reservation = await idempotency.reserve(...)
      if reservation.should_replay: ...
  # 没有键时继续往下，直接 create_shipment_batch
  ```
- **建议**：把 `request_key` 改为服务端必填（或由 `order_id + planned_date + items 排序后的哈希`生成确定性键），前端漏传也不会重复；至少在没有键时拒绝写批次，返回“请刷新后重试/缺少幂等键”。`ShipmentBatchCreate.items` 也可加 `max_length`，避免超大计划一次性锁单太久。
- **测试覆盖**：未覆盖。`backend/tests` 没有排发货批次的“无键双击”用例；B04 报告只验证了带键的重放路径。

### B04-21｜P3｜普通状态变更审计只写新状态，旧状态与理由只在 `order_status_history` 里

- **位置**：`backend/app/modules/order/router.py:893-900`；`backend/app/modules/order/service.py:640-651`（`OrderStatusHistory` 写入）
- **触发条件**：调用 `POST /orders/{id}/status` 做任意履约状态变更，尤其是“已完成”回退。
- **后果**：`write_audit` 的 `after` 只有 `{"status": payload.status}`，没有 `before` 状态、`remark`、`source`。完整流转在 `OrderStatusHistory`（`old_status/new_status/remark/source/operator_id`），所以业务留痕不算丢；但通用审计表本身不能独立回答“从什么状态改到什么、为什么”，和“审计是唯一可查证据”的预期不一致。若历史表被归档/清理，审计只剩一个目标状态。
- **建议**：`change_status` 审计补 `before={"status": old_status}`、`after={"status": new_status, "remark": remark, "source": source}`；`OrderStatusHistory` 保留，两者用同一份状态值，避免口径漂移。
- **测试覆盖**：未覆盖。没有状态流转审计断言；B04 报告的 B04-03 只测状态闸门，不测审计。

## 二、补充项“没发现问题”的结论

- **负数/0/超大值/小数位**：`OrderItemInput` 的数量 3 位、单价 4 位，`ShipmentBatchItemInput.planned_qty` 3 位，`ShipmentShipItem.shipped_qty` 3 位，`OrderCreate` 金额由明细计算、不收前端总额；金额范围有 `_assert_money_in_range`。补充复核没有发现新的边界缺口。`OrderCreate.items` 无 `max_length` 属既有 B04-11，不重复。
- **事务边界**：手工建单/转单/发货批次/实发/取消都在路由层一次 commit；service 内部只有 `flush`，没有提前 commit。转单的 `IntegrityError` 分支会 `session.rollback()`（B04-16 已记 P3，属外层事务被整体回滚）；排批次用 SAVEPOINT 兜唯一键。没有发现“订单建了明细没建”的半成品路径。
- **异常/日志/错误信息**：`sync_erp` 捕获 `ErpError` 后回滚并转通用文案，不把 ERP 原始报文返回；订单正常路径未发现 `except Exception: pass`。取消时逐笔驳回回款写审计，未发现静默改状态。
- **审计（已有）**：建单/转单/改单/里程碑/交期变更/状态/取消/ERP 推送/复购/批次创建/实发/批次取消都有审计；订单金额序列化同时带 `*_exact`。问题集中在取消审计缺金额（B04-19）和状态审计缺旧值/理由（B04-21）。
