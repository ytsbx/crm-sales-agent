## 三、发现

### F03-01 P1：价格表单用 `parseOptionalNumber` 转 number，16 位边界价/数量被改写

- **位置**：`PriceCenterPage.tsx:744-756`（成本）、`789-822`（价格规则）、`842-869`（客户特殊价）、`987-1017`（运费费率）；`number-input.ts:30-35、51-56、63-67`；后端 `pricing/service.py:42-48`。
- **触发条件**：价格管理员输入接近后端列上限的金额或数量。后端列分别是成本 `Numeric(14,4)`、价格规则/客户特殊价 `Numeric(16,4)`、数量 `Numeric(16,3)`；前端 `parseOptionalNumber`/`parseQuantity`/`requiredNumberOrThrow` 先转 JS `number`。
- **后果**：用户填的十进制文本在提交前就被改写，后端拿到的已不是原值；价格规则、客户专属价、费率、成本全部可能偏一个最小单位。价格中心是报价的取价依据，错误会一路带到报价/订单。
- **证据代码**：
  ```tsx
  purchase_cost: parseOptionalNumber(costForm.purchase_cost),   // :745
  standard_price: parseOptionalNumber(ruleForm.standard_price), // :792
  agreed_price: parseOptionalNumber(customerPriceForm.agreed_price), // :845
  unit_price_per_kg: requiredNumberOrThrow(rateForm.unit_price_per_kg, '公斤单价'), // :994
  ```
  Node 实测：
  ```text
  Number('999999999999.9997') => 999999999999.9998
  Number('9999999999999.999')  => 9999999999999.998
  ```
  项目已经有 `parseOptionalDecimal`（`number-input.ts:38-43`）专门保留十进制文本，但 PriceCenter 没有 import 它。
- **建议**：价格规则/客户特殊价/费率/成本的金额字段一律用 `parseOptionalDecimal`，提交字符串；数量用 `requiredQuantityText` 或返回字符串的解析器。后端出参补 `*_exact`，前端不要从 `number` 回填。不能只在提交前 `Number`，也不能只靠后端 Decimal “兜底”。
- **测试覆盖**：**部分覆盖**。`backend/tests/test_pricing_simulation_precision.py` 测的是模拟接口的 `quoted_price_exact`/`amount_exact`，不测 PriceCenter 表单；没有前端精度测试。

### F03-02 P1：客户特殊价/运费费率编辑从 `_f` float 回填，不改直接保存也会改价

- **位置**：`PriceCenterPage.tsx:948`（客户特殊价回填）、`969`（费率回填）、`845-846`、`994-996`；后端 `pricing/service.py:42-48、106-125、150-164`。
- **触发条件**：客户特殊价或运费费率的价格是 16 位边界值（例如 `999999999999.9997`），用户打开“编辑”，不修改任何字段直接点“保存”。
- **后果**：后端 `serialize_customer_price` / `serialize_logistics_rate` 已经用 `_f` 把 Decimal 转成 float；前端 `String(row.agreed_price)` / `String(row.unit_price_per_kg)` 回填，保存时又 `parseOptionalNumber`。原值 `.9997` 在往返中变成 `.9998`，客户专属价/费率被无声改掉，审计里还会记成一次“修改”。
- **证据代码**：
  ```tsx
  agreed_price: String(row.agreed_price ?? ''),                 // :948
  unit_price_per_kg: String(row.unit_price_per_kg ?? ''),       // :969
  // 保存
  agreed_price: parseOptionalNumber(customerPriceForm.agreed_price), // :845
  unit_price_per_kg: requiredNumberOrThrow(rateForm.unit_price_per_kg, '公斤单价'), // :994
  ```
  `pricing/service.py:42-48`：
  ```python
  def _f(value: Decimal | None) -> float | None:
      return None if value is None else float(value)
  ```
- **建议**：serializer 增加 `agreed_price_exact` / `unit_price_per_kg_exact` / `minimum_price_exact`，编辑弹窗只用 exact 字符串回填；保存时原样回传。若暂不改后端，至少在编辑态不把 number 再 `String` 后提交，改为从列表原始 `exact` 字段保留。
- **测试覆盖**：**未覆盖**。没有“打开编辑→原样保存→价格不变”的后端/前端测试。

### F03-03 P2：客户查价数量走 number，跨阶梯边界可能查错档；“加入商机需求”把 number 写进商机

- **位置**：`PriceCenterPage.tsx:608-609`（`parseQuantity`）、`1155`（`lookupPrice` 提交）、`1353-1356`（`createItem`）；`number-input.ts:63-67`；`pricing.ts:495-520`。
- **触发条件**：查价数量接近 `Numeric(16,3)` 上限，或“加入商机需求”使用查价结果的 `quantity`/`unit_price`。
- **后果**：`parseQuantity` 返回 number；数量 `9999999999999.999` 变成 `9999999999999.998`，可能落到不同数量区间，查到相邻档的价格；随后 `createItem` 又把 number 数量/目标价写进商机需求，错误继续向下游传。
- **证据代码**：
  ```tsx
  const lookupQuantity = parseQuantity(lookupQty)                    // :608
  lookupMutation.mutate({ ..., quantity: lookupQuantity })          // :1155
  await createItem(lookupOpp.id, {
    quantity: lookupResult.quantity, target_price: lookupResult.unit_price, // :1355-1356
  })
  ```
  `lookupPrice` 的参数类型本身允许 `number | string`，但页面只给 number。
- **建议**：查价数量改用 `requiredQuantityText` 保留字符串；`createItem` 也传数量/单价的 exact 文本；`PriceLookupResult.quantity`/`unit_price` 补 exact 字段。
- **测试覆盖**：**未覆盖**。

### F03-04 P2：成本表强制两位小数，4 位成本/合计成本被截成 2 位

- **位置**：`PriceCenterPage.tsx:521-522`（`money`）、`1452-1460`（成本表）；`CostRecord` 类型 `pricing.ts:4-19`；`money.ts:24-35`。
- **触发条件**：成本是 4 位小数（后端 `CostCreate` 就是 `max_digits=14, decimal_places=4`），例如采购成本 `33.3333`。
- **后果**：成本表把 `33.3333` 显示成 `¥33.33`，`total_cost` 也截到 2 位；价格管理员看到的成本与核价实际用的成本不一致，人工核价/对账会按错误口径判断。
- **证据代码**：
  ```tsx
  const money = (value?: number | null) =>
    value == null ? '-' : formatMoney(toTwoDecimals(value), 'CNY') // :521-522
  // 成本列
  { title: '采购', dataIndex: 'purchase_cost', render: money }       // :1452
  ```
  `toTwoDecimals` 对 number 走 `toFixed(2)`，直接舍到两位。
- **建议**：成本列改用 `formatUnitPrice(value, 'CNY')`（4 位保真），合计成本同样；只有“最低收费/金额”这类钱才用两位。
- **测试覆盖**：**未覆盖**。

### F03-05 P2：新增成本无 `request_key`，超时重试多一条同生效日成本

- **位置**：`PriceCenterPage.tsx:738-756`；后端 `pricing/router.py:97-149`。
- **触发条件**：新增成本 POST 已在服务端提交，响应超时；用户再点“保存”。
- **后果**：`create_cost` 只锁 SKU、只校验“四项不能全空/日期”，没有请求幂等，也没有“同 SKU 同生效日唯一”约束；第二次会再插一条成本。取生效成本时两条同日期记录谁胜出取决于排序/ID，价格可能随机命中一条。
- **证据代码**：
  ```tsx
  const costMutation = useMutation({
    mutationFn: () => createCost(costSkuId!, { ...costs, effective_from: ... }), // :752
  })
  ```
  后端 `create_cost` 没有 `idempotency.reserve`，直接 `session.add(cost)`。
- **建议**：给新增成本加 `request_key`；后端至少加“同 SKU + 同生效日 + 同四项成本”重复拦截，或唯一约束 + 友好 409。
- **测试覆盖**：**未覆盖**。`test_batch7_cost_lifecycle.py`/`test_cost_completeness.py` 测生命周期与完整性，不测重复 POST。

### F03-06 P2：停用/恢复价格规则、删除客户特殊价无 `catch`

- **位置**：`PriceCenterPage.tsx:1618`、`1630`、`1758`。
- **触发条件**：恢复价格规则时与现有启用规则区间冲突（后端 40901）；停用/删除时后端 500/网络失败。
- **后果**：`disablePriceRule(...).then(refreshAll)`、`restorePriceRule(...).then(refreshAll)`、`deleteCustomerPriceRule(...).then(refreshAll)` 都没有 `catch`/`onError`；`Popconfirm` 关闭后页面无 Toast、无错误 Banner，用户以为操作成功或没生效，可能反复点。恢复失败时规则仍停用，取价继续少一条规则。
- **证据代码**：
  ```tsx
  onConfirm={() => disablePriceRule(record.id).then(refreshAll)}   // :1618
  onConfirm={() => restorePriceRule(record.id).then(refreshAll)}   // :1630
  onConfirm={() => deleteCustomerPriceRule(record.id).then(refreshAll)} // :1758
  ```
- **建议**：改成 `mutateAsync` + `try/catch` 或统一 mutation，`onError` 展示后端业务消息并保留弹窗；恢复冲突时明确提示“与规则 X 区间重叠”。
- **测试覆盖**：**部分覆盖**。`backend/tests/test_config_rule_conflicts.py:85-94` 测费率/规则冲突，不测前端是否显示错误。

### F03-07 P3：价格表单缺 0..1/负数/16 位/4 位小数校验，主要靠后端 422

- **位置**：`PriceCenterPage.tsx:750`（成本提示）、`792-796`（规则）、`845-846`（客户价）、`881-887`（权限）、`994-998`（费率）、`2271-2283`（客户价提交前）。
- **触发条件**：用户输入负数成本/费率、`minimum_margin=1.5`、`target_margin=1.5`、17 位价格、5 位小数。
- **后果**：前端只判“是不是数字”，这些值都会放行到后端；后端 422 的原始 `error.message` 直接 Toast。不会写错账，但用户不知道具体是“不能为负”“最多 4 位”还是“利润率必须 ≤1”；成本提示还写“最多 2 位小数”，与后端 4 位不一致。
- **证据代码**：
  ```tsx
  const bad = invalidNumberMessage(costs, '只能填数字（最多 2 位小数）') // :750
  const margin = parseOptionalNumber(permissionForm.minimum_margin)     // :881
  if (typeof margin === 'number' && Number.isNaN(margin)) throw ...    // 只判 NaN，不判 >1
  ```
  后端 `PricePermissionUpdate.minimum_margin` 是 `ge=0, le=1`，`PriceRuleCreate.target_margin` 是 `gt=0, le=1`。
- **建议**：复用 schema 边界做前端校验：利润率 0..1、成本/费率/价格 `>=0`、整数位/小数位按列精度；错误提示点名“哪一项、为什么”。
- **测试覆盖**：**部分覆盖**。后端 schema 有边界，前端没有对应测试。

### F03-08 P3：列表/查价失败显示空表或原始 error，用户把“加载失败”当成“没有数据”

- **位置**：`PriceCenterPage.tsx:677-726`、`1155-1167`、`1454-1460`、`1643-1663`、`1768-1787`、`1848-1852`、`1949-1953`、`2046-2058`。
- **触发条件**：价格规则/客户特殊价/权限/费率/历史/成本列表请求 500 或网络失败。
- **后果**：表格 `empty` 文案会显示“还没有价格规则/还没有客户特殊价/还没有变更记录”，用户会误以为数据不存在；`lookupMutation` 和多数 mutation 直接把 `error.message` 显示出来，可能暴露内部字段/原始异常。`customersQuery`/`lookupOppQuery` 失败时下拉为空，没有“加载失败，重试”。
- **证据代码**：
  ```tsx
  empty={ruleKeyword.trim() ? `没有匹配…` : '还没有价格规则'} // :1660-1663
  <p role="alert">查价失败。{lookupMutation.error.message} 可再次点「查价」。</p> // :1165-1166
  ```
- **建议**：每个列表补 `isError` 分支和重试按钮；错误文案按错误码脱敏，不直接展示 `error.message`；空态与错误态分开。
- **测试覆盖**：**未覆盖**。

### F03-09 P3：`toTwoDecimals` 数字四舍五入、字符串截断；`formatUnitPrice` 截第 5 位；金额显示口径不一致

- **位置**：`money.ts:24-35`、`52-68`、`76-102`。
- **触发条件**：同一个 3 位小数值既有 number 形态（表格/Float）又有 string 形态（exact 出参/审计快照）。
- **后果**：`toTwoDecimals(2.345)` 得到 `"2.35"`，`toTwoDecimals('2.345')` 得到 `"2.34"`；同一个金额在不同页面/同一页不同列可能差一分。`formatUnitPrice` 对第 5 位 `slice(0,4)` 是截断不是四舍五入。`formatMoney` 的 number 路径不补两位小数，出现 `¥1,234.5` 与 `¥1,234.50` 混排。
- **证据代码**：
  ```ts
  if (typeof value === 'number') return value.toFixed(2)     // :30
  if (fraction.length >= 2) return `${whole}.${fraction.slice(0, 2)}` // :34
  const trimmed = fraction.slice(0, 4).replace(/0+$/, '')    // :64
  ```
- **建议**：统一“先精确化、后舍入”的规则：字符串用四舍五入到目标位数，number 只在确定安全时用；`formatUnitPrice` 对第 5 位做 HALF_UP/HALF_EVEN 明确规则；金额函数统一固定两位。
- **测试覆盖**：**未覆盖**。没有 `money.ts` 单元测试。

### F03-10 P3：核价主结果/权限 verdict 用 float 数字和 raw `quoted_price` 展示，深链价格用 `Number` 回填

- **位置**：`PricingPage.tsx:54-67`（深链 `paramNumber`）、`137-140`（`money`）、`376`（verdict 原样）；`pricing.ts:185-235`（`PricingResult` 无 exact）、`495-520`（`PriceLookupResult` 无 exact）。
- **触发条件**：核价结果包含 4 位单价，或深链 `/pricing?quoted_price=999999999999.9997`。
- **后果**：主结果的价格/成本/利润都从 float 数字走 `formatUnitPrice`，可能显示邻近值；权限 verdict 的 `quoted_price` 甚至不做格式化，直接 `报 {number} 元`；深链 `Number` 把 16 位回填价改成 float。试算本身不落库，但用户会按这个数去报价。
- **证据代码**：
  ```tsx
  const paramNumber = (key: string) => ... Number(raw) ... // :54-56
  const money = (value?: number | null) => formatUnitPrice(value, 'CNY') // :137-138
  报 {verdict.quoted_price ?? '-'} 元 · {verdict.currency} // :376
  ```
  `PricingScenario` 有 `quoted_price_exact`/`amount_exact`，但 `PricingResult`/`PricePermissionVerdict` 没有对应的 exact。
- **建议**：后端 `calculate`/`check-permission` 出参补 `quoted_price_exact`、`recommended_price_exact`、`minimum_price_exact` 等；前端优先 exact；深链保留原始字符串，不要 `Number` 后再 `String`。
- **测试覆盖**：**部分覆盖**。模拟场景 exact 有测试（`test_pricing_simulation_precision.py`），主核价/权限 verdict exact 没有。

| 金额是否全程 Decimal | 后端核心是 Decimal，但价格中心出参 `_f` 转 float、前端表单 `parseOptionalNumber` 转 number；只有模拟场景有 `quoted_price_exact`/`amount_exact` | **没有全程 Decimal**，F03-01/02/04/10 |
| 负数、0、超大值、小数位超限 | 成本/费率/规则/权限表单只判“是否数字”；客户约定价判 >0；数量 3 位小数；后端 schema 有 `ge/le/max_digits/decimal_places` 兜底 | 负数/0/位数主要靠后端 422；前端提示不完整（F03-07） |
| 事务边界（半成品） | 成本/规则/客户价/费率都是单请求单记录；前端没有“先建头再补明细”的写路径；后端 create 都是单事务 | 本块未见半成品；真正风险是成本重复（F03-05） |
| 异常是否被吞 | 停用/恢复规则、删客户特殊价无 `catch`；列表 query 无 `isError` 分支；查价/Mutation 多处只 Toast 原始 `error.message` | 有静默失败/误判空数据（F03-06/08） |
| 错误信息泄露内部细节 | `error.message` 直接 Toast/段落展示；历史变更内容展示内部字段名（有中文映射但兜底仍可能英文） | 有泄露/误导风险（F03-08） |
| 关键钱操作审计 | 成本/规则/客户价/费率/停用/恢复后端点都有 `write_audit`；前端不采集“为什么改价/为什么停用”的原因，删除客户价无二次原因 | 审计有记录，原因质量不足；本块不重审审计正文 |
