#### F11-01 数量/目标价非法输入被静默变成 `null`

- 严重度：P1（数据丢失/金额字段丢失）
- 位置：`frontend/src/modules/knowledge/KnowledgePage.tsx:911-915`、`335-342`；`frontend/src/shared/number-input.ts:30-35`
- 触发条件：用户在“记录定制询价”或“修订”里把数量/目标价填成 `abc`、`1.2.3`、`8.5元` 等非纯数字；或 `parseOptionalNumber` 返回 `NaN` 后直接提交。
- 后果：`NaN` 被 `JSON.stringify` 变成 `null`；后端 `CustomInquiryUpdate/Create` 把 `null` 当“未填/清空”，数量和目标价从这条需求上消失。用户看到“保存成功”，但关键数量/目标价没有了。后续转报价若依赖需求数量，会取不到值或落到默认，直接影响金额链路。
- 证据代码：

```ts
// KnowledgePage.tsx:913-914
quantity: form.quantity.trim() ? parseOptionalNumber(form.quantity) : null,
target_price: form.target_price.trim() ? parseOptionalNumber(form.target_price) : null,

// KnowledgePage.tsx:340-341
quantity: reviseForm.quantity ? Number(reviseForm.quantity) : null,
target_price: reviseForm.target_price ? Number(reviseForm.target_price) : null,
```

```ts
// number-input.ts:30-35
export function parseOptionalNumber(raw: unknown): number | null {
  const text = String(raw ?? '').trim()
  if (text === '') return null
  const n = Number(text)
  return Number.isFinite(n) ? n : NaN
}
```

- 建议：`saveForm`/`reviseMutation` 对 `NaN` 明确 `Toast.error` 并中止；或改用 `parseOptionalDecimal` 保留十进制文本，后端只接收字符串/Decimal。不要用“`null` 代表非法输入”和“`null` 代表未填”共用同一个值。
- 测试覆盖：**未覆盖**。`backend/tests/test_inquiry_draft.py` 只测创建/更新草稿与历史保护；`test_inquiry_submit_required.py` 只测空/0 数量；没有非数字文本输入用例。

#### F11-03 转报价的成本/报价/数量用 JS `number`，16 位金额会丢分

- 严重度：P1（金额精度）
- 位置：`frontend/src/modules/knowledge/KnowledgePage.tsx:184-188`、`240-242`、`1535-1559`；`backend/app/modules/inquiry/schema.py:77-81`

### 事务边界

- Cases：新建/更新案例与 `sync_evidences` 在同一个后端请求内；前端没有“先建案例再建证据”的跨请求流程。未发现“案例建了但证据没建”的半成品；但未做故障注入验证。
- Knowledge：`saveMutation` 是多个 HTTP 请求（创建/更新询价 → 照片上传 → 附件上传 → 更新 oa_draft → 发起 OA），不是数据库事务。中途失败会留下已保存的询价草稿（可重试，`savedInquiry` 防重复创建），不会留下半张报价/订单。这个半成品是业务可接受的草稿态，不按 P0/P1 计；但“响应丢失重复创建”见 F11-09。
- Insight：新建/更新是单请求；转需求是单请求，后端在同一事务内创建询价并更新洞察状态；没有前端跨请求的半成品。未做故障注入验证。
- 询价转报价：后端 `create_quote_from_inquiry` 在同一事务内创建报价/版本/明细并写审计；前端只发一次请求。未发现“报价建了明细没建”的前端路径。

### 异常吞掉 / 错误泄露 / 日志

- 已确认吞异常：`CasesPage.openDetail` 的空 `catch`（F11-16）；证据/时间线查询无 `isError`（F11-07）；审批/历史无 `isError`（F11-11）；评审历史无 `isError`（F11-15）；状态汇总/客户搜索无 `isError`（F11-19/20）。

- 日志敏感信息：F11 前端没有日志调用；后端审计/日志不在本块范围。未发现前端把密码/Token/完整 JSON 写入日志。
- 建议统一错误文案：对外用固定中文，详细原因交给后端日志/错误码，不直接展示 `error.message`。

### 审计

- Cases：后端 `cases/router.py` 在创建、更新、提交、审核、撤下/删除等动作调用 `write_audit`；前端不写审计。未发现关键状态动作绕过审计。

- Insight：`product_insight/router.py` 在创建、更新、提交、审核、转需求时 `write_audit`；未发现缺失。
- 结论：前端不承担审计写入；本次未发现“关键钱操作没有审计”的后端证据，但重复提交造成重复审计记录，应按幂等修复。
